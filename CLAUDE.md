# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

bitnsbot is a Bitcoin network events notification bot for Telegram. It's a single Go binary built almost entirely on the standard library — the exceptions are `go.etcd.io/bbolt` (embedded KV store, for persisting watches) and, for talking to a `btcd` node, `github.com/gorilla/websocket` + `github.com/sourcegraph/jsonrpc2` (no other option exists in the standard library for any of these). It receives updates via a Telegram webhook (not long polling).

## Commands

- Build: `go build ./...`
- Run: `go run . -bot-token <token> -webhook-url http://localhost:8080/bot -api-base-url http://localhost:8081`
- Test all: `go test ./...`
- Test one: `go test -run TestWatchFlow -v` (other tests: `TestInfoFlow`, `TestUnwatchFlow`, `TestWatchesFlow`, `TestWatchNotification`, `TestShutdown*`, `TestMessageLogging`, `TestLoggingLevels`, `TestWatchStore*`, `TestRate*`, `TestUSDFormat`, `TestUpdateRatesAverages`, `TestAmountLineUSD`, `TestConfig`, `TestBtcd*`). Run the whole suite with `-race` (`go test -race ./...`) — the watch-notification path is concurrent.
- Vet: `go vet ./...`

There is no Makefile or linter config in this repo — `go build`/`go vet`/`go test` are the only checks available (and are exactly what `.github/workflows/ci.yml` runs on every pull request, on Go 1.26). `gofmt -l .` will flag files as unformatted by design; see Style below before "fixing" that.

Flags (all in `main.go`): `-config` (path to a `name=value` properties file to load flag values from — see The config file below), `-verbose` (log level 0/1/2 — see Logging below), `-bot-token` (Telegram bot token, required), `-listen` (address this bot's webhook server binds to), `-webhook-path`, `-webhook-url` (the URL registered via `setWebhook`), `-api-base-url` (Bot API server to call), `-secret-token` (optional), `-register-webhook` (set false to skip calling `setWebhook` on startup), `-db` (path to the bbolt watches database, default `watches.db`), `-btcd-url`/`-btcd-user`/`-btcd-pass`/`-btcd-cert`/`-btcd-insecure-tls` (btcd RPC connection; leaving `-btcd-url` empty skips connecting to btcd entirely).

## Deployment (scripts/)

`scripts/` holds the Raspberry Pi / systemd continuous-deployment helpers (`install.sh`, `update.sh`, `uninstall.sh`, `README.md`) — not part of the Go build. The runtime package is self-contained under `/opt/bitnsbot` (`bitnsbot` binary, `bitnsbot.cfg`, `bitnsbot.db`); the source checkout stays where cloned (default `/home/pi/bitnsbot`). `install.sh` (run as root) builds+tests **as the checkout's owner** (via `runuser`, non-login shell with explicit `HOME`/`PATH` so `go` is found and captured git output stays clean), installs the binary, writes a systemd unit ordered `After=btcd.service` (running as that user), and schedules `/etc/cron.d/bitnsbot` to run `update.sh` every 5 minutes. `update.sh` fetches `origin/master` and acts **only when it is strictly ahead** of the deployed `HEAD` (checked with `git merge-base --is-ancestor` — a plain `HEAD != origin/master` would rebuild-loop whenever the local checkout is ahead); it fast-forwards, rebuilds, runs the full suite, and only on success atomically swaps the binary and restarts — a `flock` prevents overlapping runs. See `scripts/README.md`. These are validated with `bash -n` and by exercising the git decision logic against throwaway repos; the systemd/cron paths can only be verified on the target host.

## Runtime model

The bot is designed to run behind a self-hosted `telegram-bot-api` proxy (https://github.com/tdlib/telegram-bot-api) on localhost, not directly against `https://api.telegram.org`:
- `-api-base-url` defaults to `http://localhost:8081`; `telegram.go`'s `bot.call` builds every outgoing request URL from it.
- The webhook HTTP server is a plain `*http.Server` (via `srv.ListenAndServe` in a goroutine) — no TLS. The local proxy is assumed to own the real HTTPS conversation with Telegram; the hop from proxy to this bot is local/plaintext.
- **Graceful shutdown**: `main()` uses `signal.NotifyContext(…, os.Interrupt, syscall.SIGTERM)` and blocks on the returned context; on SIGINT/SIGTERM it calls `shutdown(srv)`, which tears down **in dependency order — webhook server first, then btcd, then the store**. That order is load-bearing: `srv.Shutdown` blocks until in-flight webhook handlers drain, and those handlers use the watches database and `btcd`, so closing the server first guarantees no handler is mid-request when the connections it depends on are closed. After the first signal `stop()` is called to restore default handling, so a second Ctrl+C during a slow drain force-kills. (Note: the old `defer closeDB()`/`defer btcd.close()` were dead code — `http.ListenAndServe` blocked forever and only ever returned into a `log.Fatal`, i.e. `os.Exit`, which never runs defers; this feature is the first real cleanup path.)
- Two secrets, both flags: `-bot-token` (required) authenticates outbound Bot API calls. `-secret-token` (optional) is passed to `setWebhook` and then checked against the `X-Telegram-Bot-Api-Secret-Token` header on every incoming request (constant-time compare in `main.go`'s webhook handler) — this is the only thing stopping an arbitrary POST to the webhook path from being treated as a real Telegram update. Since both are flags they can be supplied via the `-config` file; prefer that over the command line for real deployments, since command-line args are visible to other users via `ps`.

## Architecture

The bot lives in `package main` in the repo root; five supporting packages sit in subdirectories (`logging/`, `rates/`, `watches/`, `txwatches/`, `miners/`), each with a small simplified API and its own unexported types. Cross-cutting state that used to be package-`main` globals with compound names (`storeRate`/`lastRate`, `addWatch`/`listWatches`, `addTxWatch`/`txWatches`) now reads as `rates.Add`/`rates.Last`, `watches.Add`/`watches.List`, `txwatches.Add`, etc.

Root (`package main`):
- `telegram.go` — the Bot API client: the unexported `bot` type, `newBot`, and `call`/`send`/`setWebhook` methods, plus the wire types (`Update`, `Message`, `User`, `Chat`) decoded from incoming webhook JSON.
- `db.go` — the bbolt connection: the package-level `var db *bbolt.DB`, `openDB(path)`/`closeDB()`, and the shared `itob` big-endian key helper. `openDB` opens the one file, creates the `blocks` bucket, and hands the same handle to `rates.Init`/`watches.Init`/`miners.Init` (which own their own buckets) — one file, one handle, seven buckets (`blocks`, `rates`, `watches`, and the miners package's `miners`/`miners-tag`/`miners-stat`/`miners-block`).
- `btcd.go` — a `btcdClient` for talking to a `btcd` node's JSON-RPC-over-websocket API (see below).
- `blocks.go` — the `blocks` bucket: cached per-block info records (`blockInfo`), `computeBlockInfo` (builds a record from btcd), the startup backfill goroutine, and `formatBlock` (the `/info` block reply). See Block info cache below.
- `config.go` — `applyConfig`, a tiny `name=value` properties-file parser that sets flags from a `-config` file (see below).
- `main.go` — flags, the HTTP webhook server, command dispatch (`update`), the `/watch`/`/unwatch`/`/watches` (`watchesCmd`)/`/fees`/`/mempool`/`/miners` handlers, and the mempool flow-rate tracker.
- `notify.go` — the address-watch notification infrastructure (`notification`/`notifyKey`/`notifyChans`, the `notifies` fan-out map, `startNotifyChat`/`stopNotifyChat`/`notifyAddresses`, the `notifier` jsonrpc2 handler, `broadcast`, `confEstimate`, `startNotify`/`stopNotify`/`reapplyBtcdState`), plus the `watchType` type and `checkConfirmations` (which formats+sends the transaction-confirmation messages using the `txwatches` package). See Watch notifications below.
- `info.go` — the `/info` command: `info` and its per-kind `transaction`/`block`/`address` handlers plus their helpers (`txInputs`, `blockFees`, `addressTxs`/`addressStats`, `compactAddrs`, …) and the `/info` pending-argument state (see The /info lookup below).
- `format.go` — the shared display formatters `when`/`ago`/`short`/`group`/`satoshi`/`metric`/`compactBtc`/`timeCompact`/`periodText`/`durationText`, plus `usd`/`amountLine`/`btcAmount` (which read current prices from the `rates` package).

Packages:
- `logging/` — the leveled helpers `Err`/`Warn`/`Status`/`Fatal`/`Info`/`Net`/`Db` and the verbosity gate (`SetVerbosity`, called once from `main`). Everything in every package logs through these (see Logging below).
- `rates/` — BTC/USD exchange-rate history and the 5-minute averaging updater. Public API: `Init(db)`, `Start()`, `Add(usd)`, `Last() (float64, bool)`, `At(t) (float64, bool)` — prices go in and out as plain USD `float64`; the `rateRecord` type is unexported (see Exchange rates below).
- `watches/` — the **address**-watch bbolt store. Public API: `Init(db)`, `Add(chatID, address, alias)`, `Remove(chatID, address) (int, error)`, `List() ([]Watch, error)`, where `Watch{ChatID, Address, Alias}` is the public view and the internal `watchRecord` is not exposed. Only address watches are persisted — transaction watches live in `txwatches`. See The watches store below.
- `txwatches/` — the in-memory one-shot confirmation-watch list (never persisted). Public API: `Add`/`AddAddrConfirm` (register, deduped by chat+addr), `Remove`/`For` (direct `/watch <txid>` entries only), `RemoveAddrConfirms`, `Confirms(txids) []Confirmed` (removes+returns the watches whose txid is in a new block, for the caller to message), `Any`, `Reset`. See Watch notifications below.
- `miners/` — mining-pool attribution and per-miner statistics, DB-backed (`miners` maps coinbase-output address → pool name, `miners-tag` coinbase tag → pool name, `miners-stat` pool name → aggregate, `miners-block` the collector's cursor). Public API: `Init(db)`, `Start()` (background definitions refresher), `Name(address) string` (address key lookup, "" when unknown), `Attribute(addresses, coinbaseHex) string` (address then tag, "" when unknown), `StartStats(Source)` (the statistics collector) and `Top(n) []Stat`. `miners.go` holds attribution, `stats.go` the collector. See Block info cache and Miner statistics below.

### Logging

Everything logs through the `logging` package — never `fmt.Print*` or the `log` package directly. Its verbosity is set once from `-verbose` via `logging.SetVerbosity(*verbose)` in `main()` (after `applyConfig`, so it's also `-config`-settable), which gates emission:
- `logging.Err`/`logging.Warn` and `logging.Status` (lifecycle lines: "listening on …", "shutting down", "connected to btcd …") always print — verbosity 0.
- `logging.Info` (verbosity ≥ 1): high-level events — an incoming message (`logMessage`), a reply sent (`send`), a subscription added/removed (`watchCmd`/`unwatch`).
- `logging.Net` and `logging.Db` (verbosity ≥ 2): raw external traffic and storage requests. NET is emitted from `telegram.go`'s `bot.call` (request method + body, response body) and the `rates` package's `fetch` (each price-API GET + response), plus `btcd.go` via `jsonrpc2.OnSend`/`OnRecv` hooks that are **only registered when `*verbose >= 2`** (zero overhead otherwise). DB is emitted from each `rates`/`watches` storage function (and `openDB`).
- `logging.Fatal` is `logging.Err` + `os.Exit` for the startup fatals.

Two deliberate redactions in NET logging, both to avoid leaking secrets that a debug log would otherwise capture: the Telegram request URL (which embeds `-bot-token`) is never logged — only the method and JSON body — and the `setWebhook` body is omitted entirely because it carries `-secret-token`. Everything else (including sent message text and btcd payloads) is logged verbatim at verbosity 2.

### The config file

`-config <path>` points at a plain `name=value` properties file whose names are flag names (`btcd-url=wss://localhost:1234/ws`, `listen=:8082`). `applyConfig` (in `config.go`) is called from `main()` immediately after `flag.Parse()`: it reads the file and calls `flag.Set` for each line, so config values land in the same `*flag.Flag` variables the rest of the code already reads — no separate config struct. Blank lines and `#` comments are skipped; names and values are whitespace-trimmed; an unknown name or a malformed (no `=`) line is a fatal error with `path:line` context. Command-line flags win over the file: `applyConfig` first records which flags were already set on the command line via `flag.Visit` and skips those, so precedence is CLI > file > flag default. Because it's driven entirely by the flag set, every flag is automatically config-settable and no per-flag wiring is needed when flags are added.

### The btcd RPC client

`dialBtcd(ctx, btcdConfig{url, user, pass, certFile, insecureTLS}, handler)` dials `btcdConfig.url` with `github.com/gorilla/websocket` (HTTP Basic Auth header for credentials, matching btcd's preferred auth method over the websocket-only `authenticate` RPC command), then wraps the resulting `*websocket.Conn` in `github.com/sourcegraph/jsonrpc2/websocket`'s `ObjectStream` and hands that to `jsonrpc2.NewConn` to get a `*jsonrpc2.Conn`. TLS is only configured when `url` starts with `wss://` (production btcd is TLS-by-default with a self-signed `rpc.cert`; local regtest/dev nodes are commonly run with `--notls` and a plain `ws://` URL, which is what this repo's manual testing used).

**Reconnection**: `btcdClient` is a long-lived handle whose underlying `*jsonrpc2.Conn` lives in an `atomic.Pointer`, so a reconnect swaps the connection *in place* — every `btcd.foo()` call site (each does `c.conn.Load().Call(...)`) keeps working against the same `*btcdClient`, so neither the package `var btcd` nor its ~20 call sites (nor the tests that assign `btcd`) need to change. `supervise(reapply)` (started from `main()` after the initial dial) runs a goroutine that pings (`getblockcount`) every `btcdPingInterval` (10s; a package var so tests shrink it); on failure it `reconnect()`s — `dialConn` a fresh connection, `Swap` it in, close the old one — retrying each tick while btcd is down, and on success calls `reapply`. That callback is `reapplyBtcdState` (in `main.go`): re-`notifyBlocks` for the block cache and re-`loadTxFilter` for the watched addresses, since those subscriptions live on the connection and die with it. `close()` stops the goroutine (`stopOnce`-guarded `close(c.stop)`) and closes the current connection; a reconnect racing shutdown is handled by re-checking `c.stop` after the dial (discarding the new conn if stopping). `dialConn` is the extracted single-connection dialer; `dialBtcd` wraps it into a client. Verified against a real regtest node by killing btcd mid-run: block notifications stall, the supervisor logs reconnect attempts until btcd returns, then reconnects, reapplies, and notifications resume.

btcd/bitcoind's JSON-RPC dialect predates JSON-RPC 2.0 and always uses positional (array) `params`, never named/object params — every method call in `btcd.go` passes `[]interface{}{...}` as the params argument for this reason. Confirmed against btcd source (`btcjson.RPCVersion.IsValid()` accepts both `"1.0"` and `"2.0"`) that sending `"jsonrpc":"2.0"` (what `sourcegraph/jsonrpc2` always sends) doesn't get rejected.

Only a handful of RPC methods are wrapped as typed methods so far (`getBlockCount`, `getRawTransaction`, `getBlockHash`, `getBlockVerbose`, `getBlockTxids`, `validateAddress`, `searchRawTransactions`, `decodeRawTransaction`, `loadTxFilter`, `notifyBlocks`, `estimateFee`) — enough to cover `/watch`, `/info`, and `/fees`'s needs, not the full btcd API surface. (`getBlockVerbose` at verbosity 2 supplies everything the block cache needs — height, time, size, difficulty, and every tx with its size, vin, and vout — so the old `getBlockHeader` wrapper was dropped. `getBlockTxids` is the cheap counterpart at verbosity 1, returning just `{height, difficulty, tx:[txid…]}` — enough for the confirmation check and, with the difficulty, for the miner-statistics collector.) Add more the same way: a thin method on `btcdClient` that calls `c.conn.Call(ctx, "methodname", []interface{}{...}, &result)`. One btcd-specific gotcha (caught against a real regtest node): `getblock` at verbosity 2 returns the full transactions under the JSON key **`rawtx`**, not `tx` (`tx` carries only txids, at verbosity 1) — Bitcoin Core uses `tx` for both, so `btcdVerboseBlock.Tx` is tagged `json:"rawtx"`.

Server-pushed notifications (e.g. `blockconnected`, `relevanttxaccepted` — see `/Users/pin/code/btcd/docs/json_rpc_api.md` for the full list) are delivered to whatever `jsonrpc2.Handler` is passed into `dialBtcd`.

`main()` dials btcd (if `-btcd-url` is set; empty means skip it entirely) right after opening the watches store and before registering the Telegram webhook or starting to listen — the package-level `var btcd *btcdClient` holds the connection, and a dial failure is fatal (matches how the database's open failure is handled). The handler passed in is `notifier` (see Watch notifications below). After `startNotify`/`startBlockCache`, `main()` calls `btcd.supervise(reapplyBtcdState)` to start the reconnection watchdog (see Reconnection above); graceful shutdown's `btcd.close()` both stops that goroutine and closes the connection.

`btcd_test.go` fakes the btcd server with an in-process `httptest.Server` + `websocket.Upgrader` (same philosophy as the Telegram tests — no real btcd node needed to run `go test`). It was additionally verified once, manually, against a real locally-built `btcd --regtest --notls` node; that was throwaway verification, not something reflected in the checked-in tests.

### The /info lookup

`info()` in `main.go` classifies its (non-empty) argument into exactly one of three kinds, checked **in this order**, and dispatches to the matching per-kind function — `transaction()`, `block()`, or `address()` (one-word names, same convention as `info`/`watch`): transaction (`isTxid`: exactly 64 hex characters), then block height (parses as a non-negative base-10 integer via `strconv.ParseInt`), then address (the catch-all). The order matters and is not arbitrary: a 64-character string of all decimal digits (e.g. all zeros) satisfies *both* the txid shape and `ParseInt`, since decimal digits are a subset of hex digits — checking txid first is what disambiguates it correctly. This was a real bug caught by manual testing against a live regtest node, not a hypothetical; don't reorder these checks without re-verifying against a real node.

Each per-kind function calls btcd directly and replies with a multi-line message: `transaction` via `getRawTransaction` reports Status (confirmed + confirmation count, or unconfirmed/mempool), the confirmation time (`Confirmed:` = the block time via `when` — note btcd keeps no broadcast time for a confirmed tx, so the *delay* it took to confirm isn't computable; only the confirmation timestamp is), Block, Amount (summed `Vout[].Value` in whole satoshi, `math.Round(total*1e8)`, space-grouped), Fee, Size, and compact Input/Output address lists. The fee (Σ input prevout values − Σ output values) and the input addresses both need each input's prevout, which `getrawtransaction` omits, so `txInputs` fetches the prevout transactions **concurrently** (same bounded-`sem`-of-16 + `WaitGroup` pattern as `blockFees`) and returns `(fee, addrs, spent, ok)` — `addrs` in input order for this listing, `spent` summed per address for the watch notifier's outgoing detection (see Watch notifications); a coinbase tx shows `Fee: none (coinbase)` / `Inputs: coinbase (newly generated)`, and any prevout-fetch failure degrades Fee/Inputs to `unavailable` (so this too effectively wants `--txindex`). `compactAddrs` shows at most the first three addresses (each `short`-ened) with a trailing `...` when there are more; an output with no address (OP_RETURN, SegWit commitment) renders `(non-standard)`. An unconfirmed tx omits the Confirmed/Block fields. `block` is **served from the cache** — `block()` calls `loadBlock(height)` and, on a hit, replies with `formatBlock(bi)` without touching btcd; on a miss it computes the record live (`computeBlockInfo`), stores it, and replies. See Block info cache below for the record's fields and how it's populated (backfill goroutine + block notifications). `blockFees()` (used by `computeBlockInfo`) computes each non-coinbase tx's fee as Σ(input prevout values) − Σ(output values) for the Lowest/Average/Highest; btcd's getblock omits input values, so it gathers the referenced prevout txids and fetches those transactions **concurrently** (a `sync.WaitGroup` over a bounded `sem` channel of 16, results collected under a mutex). If any prevout fetch fails (txindex disabled, or a genuinely missing prevout) the record's `FeesOK` is false and the reply shows `Fees: unavailable`; a coinbase-only block shows `Fees: none (coinbase only)` (fee distribution effectively requires `--txindex`, same graceful-degradation spirit as `searchRawTransactions`/`--addrindex` — but reward and reward+fees come from the coinbase alone, so they show regardless). And `address` via `validateAddress` (type derived from `IsWitness`/`IsScript`) plus **on-chain history stats** from `addressTxs`, which pages `searchAddressTxs` (searchrawtransactions verbose with `vinextra`, so each input carries its prevout value and addresses) oldest-first up to `addrTxLimit` (10000; `addrTxPageSize`=1000 per page). `addressStats` then sums, over those txs: **Balance** (received − sent), **Total received** (outputs paying the address), **Total sent** (inputs spending from it), **Total flow** (received + sent), **Total fees** (Σ inputs − Σ outputs of each tx the address sends), plus the **Transactions** count and the **First/Last tx** times. Amounts render via `compactBtc` (BTC once the value reaches 0.05 BTC, else sats, each with a USD approximation); times via `timeCompact` ("2 m ago" within the last year, else the exact lowercase date), and the **Activity period** via `periodText` ("3 y 2 d" / "2 m 1 d" — the two most-significant non-zero units). All three messages put a blank line after their header line (`Transaction 32e43e...870b16` / `Block #100` / `Address 1A1zP1...DivfNa`) and space-pad the field labels so values start in one column per message (the pad width is per-message, computed from its longest label — `Confirmed:` for a confirmed transaction, `Reward + fees:` for a cached block, `Activity period:` for addresses). The field block — but not the header — is wrapped in `<pre>...</pre>` so Telegram renders it monospace and the alignment actually holds. To make that work, `bot.send` in `telegram.go` always sets `parse_mode: "HTML"` on every outgoing message, which imposes an escaping obligation: any user-derived text echoed into a reply must go through `html.EscapeString` (Telegram rejects messages with an unescaped `<` that isn't a supported tag). The two echo sites — `watchCmd()`'s confirmation and the invalid-address message — do this; txids skip it because `isTxid` guarantees pure hex, and a validated address is base58/bech32, also HTML-safe. Confirmed-transaction and block times are both rendered by `when(unix)`: relative ("2 days ago", pluralized by `ago`) when within the last 3 months, lowercase absolute ("14 november 2023 22:13", `strings.ToLower` over Go's "2 January 2006 15:04" layout) when older. Txids, block hashes, and addresses are printed shortened by `short(s)` ("32e43e...870b16": first 6 + "..." + last 6, applied only when the string is longer than 15 characters) — except the "doesn't look like a valid Bitcoin address" echo, which keeps the full input because the address branch is the catch-all and that text isn't known to be an address at all. `searchAddressTxs` requires btcd's `--addrindex` (and `--txindex` for the input prevouts). btcd reports both a disabled index and a genuinely-unused address by RPC error, and the unused-address one — `"No information available about address"` — is *also* what paging past the end returns, so `addressTxs` treats it as a clean, complete end (an unused address then simply shows zeroed totals and 0 transactions). Any *other* error before the first transaction degrades the reply to `Activity: unavailable` rather than failing it — deliberate graceful degradation. Hitting `addrTxLimit` (or a lookup timing out mid-paging under `info()`'s 15s budget) yields partial stats, flagged by a trailing `+` on the transaction count; because paging is oldest-first, a capped/partial result's First tx stays accurate while Last tx and the totals cover only the fetched prefix (verified against the real mainnet node — the genesis address capped to `300+` shows First tx `3 january 2009`, and a real spender under the cap shows exact totals with Total fees `1 000 000 sats`).

If the package-level `btcd` is `nil` (not configured via `-btcd-url`), `info()` replies with a fixed "not configured" message instead of dispatching — every kind depends on btcd, so this is checked once up front.

`isTxid` (shared with `watchCmd()`), `when`/`ago`/`short` (shared across the per-kind formatters), and `satoshi` (shared with the watch notifier — `math.Round(btc*1e8)` to whole satoshi with space-grouped thousands) are real multi-call-site helpers. The per-kind functions themselves are single-call-site — they exist because `info()` had grown too big and splitting it was explicitly requested, not as license to extract small single-use helpers.

### Watch notifications

There are **two kinds** of watch with **different delivery models**. An **address** watch (`/watch <address>`) is persisted and, whenever a transaction *pays* the address **or spends from it**, sends a mempool notification (via btcd's `relevanttxaccepted`) **and then a second "confirmed" notification** — with how long it took — once that transaction is mined. Both directions are covered: an incoming payment reports the `Amount`, and an outgoing one reports what left (`Sent`), what returned as change (`Change back`) and the resulting `Net` move, so the message answers "how did this address change" either way (see Detecting spends below). A **transaction** watch (`/watch <txid>`) is a one-shot: it fires once, when that transaction *confirms* (is mined into a block). Both "confirmed" notifications run through the same `blockconnected` → `checkConfirmations` path (see Transaction watches below); the mempool notification is the address-watch fan-out only.

The **address**-watch delivery model is **one goroutine per watch** fed by a broadcast channel fan-out (there is deliberately no address→chats map — an earlier version used `watchersByAddr` and was replaced by this at explicit request):
- **Watchers**: each address watch becomes an entry in the package-level `notifies map[notifyKey]notifyChans` (keyed by `notifyKey{chat, typ, id}`, guarded by `notifyMu`), where `notifyChans{ch, stop}` holds a `chan notification` and a stop channel. `startNotifyChat` inserts the entry and launches a goroutine that `select`s on `ch` and `stop`, messaging its chat only for notifications matching its own address — on **either** side, `notification.received[addr]` or `notification.sent[addr]`, whichever is present (both are, for a spend that returns change). `ch` is **never closed** (so a broadcast can always send without panicking); a watcher is terminated by closing `stop`. `stopNotifyChat(chat, typ, id)` closes+drops one entry (chatID-scoped like the store's `Remove`); `stopNotify` (from `shutdown` and test setup) closes them all and also `txwatches.Reset()`s the confirmation map. Only address watches live here now — transaction-confirmation watches moved to the `txwatches` package — so `notifyKey.typ` is effectively always `watchTypeAddress`.
- **Subscription** (address watches only): `watchCmd()` calls `startNotifyChat`, `btcd.loadTxFilter(reload=false, [addr], nil)` so btcd's connection-wide filter includes the address (`loadTxFilter` is what makes btcd emit `relevanttxaccepted` at all — without it there are no notifications), and then `seedOutpoints([addr])` for the spend side (see Detecting spends below). `notifyAddresses()` recomputes the filter's address set from the map for the reload calls. On startup `startNotify(bot)` re-creates a watcher per `watches.List()` record and reloads the filter once, so watches survive restarts. If btcd isn't configured the watch is still stored/started — it just won't fire until a btcd-connected restart.
- **Broadcast**: `notifier.Handle` switches on the notification method — `relevanttxaccepted` (address-watch fan-out, below) and `blockconnected`, which spawns **two** goroutines from the new tip's hash: `go cacheBlockHash(hash)` (block cache; see Block info cache) and `go checkConfirmations(n.bot, hash)` (transaction watches; see below). All spawn goroutines for the same read-loop-deadlock reason. (`notifier` now carries the `bot` so `checkConfirmations` can message chats; the reconnect supervisor reuses the same handler, so it survives reconnects.) For `relevanttxaccepted` (carrying the raw serialized tx hex, *not* which filtered address matched) it spawns `go broadcast(txHex)`. `broadcast` calls `decodeRawTransaction`, builds one `notification{txid, received: addr→summed Vout value, sent: addr→summed input prevout value}`, and non-blocking-sends it to *every* watcher's channel; each watcher then filters. `received` comes straight off the decoded outputs; `sent` cannot, because a decoded transaction's inputs are bare txid:vout refs carrying no addresses — it comes from `txInputs`, which fetches the prevouts anyway for the fee (hence its `spent map[string]float64` return, alongside the ordered `addrs` that `/info` lists). That is also why the prevout fetch is no longer gated on `full.Vsize > 0`: the fee needs the vsize, but spend *detection* doesn't, and gating both on it would have silently dropped outgoing notifications. Before fanning out it **enriches** the notification (best-effort): `getRawTransaction` for the mempool tx's `vsize` + `txInputs` for its fee (Σ input prevouts − Σ outputs), `feeRate` = fee ÷ vsize in sat/vB, and `confEstimate` buckets that rate against `estimatefee`'s 2- and 6-block targets into `~10-20 min` / `~1h` / `2h+`. The **address** notification (`startNotifyChat`) shows Fee / Fee rate / Confirms below Tx / Amount; any fetch failure just leaves them off (`feeOK` stays false and the message falls back to Tx + Amount). Right after sending it, the watcher calls `txwatches.AddAddrConfirm(n.txid, chat, addr, alias)` to register a one-shot confirmation watch (first-seen = now), so the same transaction being mined later produces the follow-up "confirmed" message (see Transaction watches). Spawning the goroutine inside `Handle` (rather than wrapping in `jsonrpc2.AsyncHandler`) is what avoids the deadlock: `jsonrpc2` calls `Handle` synchronously in its single read-loop goroutine (conn.go's `readMessages`), so the `decoderawtransaction` `conn.Call` must run off that goroutine or it waits forever for a response the blocked loop can't read. The channel sends are non-blocking (`select`/`default`) so one slow or already-stopped watcher can't stall the fan-out.

**Detecting spends (why the filter is seeded with outpoints).** btcd never matches a spend by address. Its `subscribedClients` (in `rpcwebsocket.go`) tests each input with `existsUnspentOutPoint(&input.PreviousOutPoint)` against the filter's **outpoint** set, and tests only *outputs* against the address set — where, on a match, it also does `filter.addUnspentOutPoint(&op)`. So btcd learns an address's outpoints only by watching payments arrive *while the filter is loaded*, and the filter is rebuilt from scratch on every startup and every reconnect. Left alone, that means a spend of any balance the bot didn't personally watch arrive is never reported — the common case, since a user typically adds a watch on an address that already holds coins.

`seedOutpoints(addrs)` closes that hole: for each address `addressOutpoints` replays the history from `addressTxs` oldest-first (every output paying the address adds an outpoint, every input spending one removes it) and the result goes into the filter with `loadTxFilter(reload=false, nil, ops)`, which *adds* to the live filter rather than replacing it. It is called from all three places the filter is (re)built — `watchCmd`, `startNotify`, `reapplyBtcdState` — and runs in a **background goroutine** because it pages the whole history and must not block a command reply or startup. Two honest limitations: it needs `--addrindex` (same as `/info <address>`), and because paging is oldest-first a capped history (`addrTxLimit`) loses the *newest* transactions, which is exactly where live unspent outputs are — both cases log a warning naming the address and are otherwise degraded-but-working (incoming still fine, spends of coins seen arriving still fine). Verified against the real mainnet node on four addresses with 2–468 transactions: the computed unspent set summed **exactly** to the balance `addressStats` derives independently (including a fully-spent address at zero), and btcd accepted every outpoint into the live filter.

**Transaction watches / confirmations** (`txwatches` package + `checkConfirmations` in `notify.go`): confirmations for **both** watch kinds are served from the `txwatches` package's in-memory map (keyed by txid; **not** persisted, so pending confirmations are forgotten on restart — accepted by design). `/watch <txid>` calls `txwatches.Add(txid, chat, alias)` (a **direct** entry, `addr==""`); a watched address's incoming tx calls `txwatches.AddAddrConfirm(txid, chat, addr, alias)` from the watcher goroutine (an **address-derived** entry; see Broadcast above). Neither is added to btcd's `loadtxfilter` — that filter matches addresses/outpoints and `relevanttxaccepted` is mempool-acceptance only, so there is no first-class per-txid confirmation trigger. Instead confirmation is detected off the `blockconnected` notification the bot already receives for the block cache: `checkConfirmations(bot, hash)` (in `notify.go`) early-returns unless `txwatches.Any()`, otherwise fetches the new block's txids via the cheap `getBlockTxids` (getblock verbosity 1) and hands them to `txwatches.Confirms(txids)`, which removes and returns every matching watch as a `Confirmed{Txid, ChatID, Alias, Addr, WatchedAt}`; `checkConfirmations` then formats+sends each. The message depends on `Addr`: a direct watch gets `🔔 Watched transaction <short> (alias) was confirmed in block #N after <elapsed>`; an address-derived one gets `🔔 Transaction <short(txid)> on watched address <short(addr)> (alias) was confirmed in block #N after <elapsed>`, where `elapsed = durationText(now − WatchedAt)` (a `format.go` helper; "12 min" / "2 h 5 min"), which for the address kind is the time from first mempool sighting to confirmation. Registration dedups on (txid, chat, addr) so a re-broadcast can't queue two messages; `txwatches.For`/`txwatches.Remove` (backing `/watches` and `/unwatch <txid>`) act on **direct** entries only, and unwatching an **address** also calls `txwatches.RemoveAddrConfirms` so no confirmation arrives after the user stopped watching. This reuses the very block push the cache already consumes — no new subscription, and it works for any txid without encoding it into a filter. (The old `/watch <txid>` "was accepted to the mempool" message is gone; it was effectively dead, since a txid was never in the filter and so `relevanttxaccepted` only matched a watched txid by coincidence.)

`/unwatch <arg>` reverses a watch. For a **txid** (`isTxid(arg)`) it just drops the in-memory watch via `txwatches.Remove(arg, chatID)` (chat-scoped) — no store, no filter. For an **address** it is `watches.Remove(chatID, arg)` to delete the persisted record(s), then `stopNotifyChat` to terminate the watcher goroutine, then `txwatches.RemoveAddrConfirms(arg, chatID)` to drop any pending confirmation watches for that address, then `loadTxFilter(reload=true, notifyAddresses(), nil)` to rebuild btcd's filter from the addresses that still have watchers. That filter rebuild is an optimization — the real guarantee that notifications stop is that the watcher goroutine is gone. If nothing matched (`watches.Remove` returned 0, or `txwatches.Remove` returned 0) the user is told they weren't watching it.

The whole address-watch path (`/watch` → real signed payment → `relevanttxaccepted` → broadcast → per-watch goroutine → Telegram message) was verified end-to-end against a real `btcd --regtest --txindex` node, including fan-out to two chats watching the same address (throwaway verification; `watch_test.go`'s `TestWatchNotification` covers the same path with a fake btcd server that pushes the notification). Both confirmation paths were verified against the real **mainnet** node (throwaway tests): the direct one by watching a recent block's own coinbase txid, and the address-derived one by registering a real tx from the tip block (paying a real `bc1q…` output) — real `getBlockTxids` (verbosity 1, ~4400 txids) matched in both, producing `…Watched transaction … was confirmed in block #958594 after 10 min` and `🔔 Transaction c9bc67…5f9d46 on watched address bc1qef…2n5us6 (John) was confirmed in block #958594 after 7 min`. In the suite, `TestTxConfirmation` covers the full `blockconnected`→`checkConfirmations` wiring with a fake btcd that pushes the notification, `TestAddrConfirmation` covers the address-derived confirmation message, `TestWatchNotification` asserts the mempool notification also registers the confirmation watch, `TestAddrConfirmDedup` the (txid, chat, addr) dedup, and `TestDurationText` the elapsed formatter. For the outgoing direction, `TestSpendNotification` (whole balance spent — Sent only, no Change back/Net, and a confirmation watch still registered) and `TestSpendWithChangeNotification` (Sent/Change back/Net) drive a fake btcd whose pushed transaction has the watched address in the *prevouts*, and `TestAddressOutpoints`/`TestAddressOutpointsIncomplete` cover the unspent-set replay and the no-`--addrindex` degradation. Note the shared `awaitNotification` helper registers its teardown with `t.Cleanup`, not `defer`: a deferred `stopNotify` would run before the caller's assertions and `txwatches.Reset()` away the confirmation watch under test. The whole outgoing path was also exercised against the real mainnet node (throwaway probe): a real mempool transaction fed through `broadcast` with a watcher on one of its real input addresses produced `🔔 Outgoing transaction from watched address bc1qyr…vuzj9x (Hot wallet) / Sent: 251 005 sats / Fee: 198 sats / Fee rate: 1.1 sat/vB / Confirms: ~1h`. Keep the suite green under `go test -race` — the notification paths are the codebase's only concurrent ones (the broadcast/per-watch goroutines, plus `checkConfirmations` reading the `txwatches` map under its mutex and sending Telegram messages off the read-loop goroutine).

### The watches store

The bbolt connection is a plain package-level `var db *bbolt.DB` (in `db.go`), opened once in `main()` via `openDB(-db path)` and closed during graceful shutdown (`closeDB`, see Runtime model). `openDB` opens the one file, creates the `blocks` bucket, and hands the same handle to `rates.Init(db)`/`watches.Init(db)`/`miners.Init(db)` so those packages share it — one file, one handle, four buckets. Address-watch storage lives in the `watches` package (`Add`/`List`/`Remove`); there is no `watchStore` struct, and the internal `watchRecord` isn't exposed — `List` returns a minimal public `Watch{ChatID, Address, Alias}`.

`/watch <target> [alias]` records the watch — an **address** watch via `watches.Add(chatID, address, alias)` (persisted as an internal `watchRecord{CreatedAt, ChatID, WatchID, Alias}` under an auto-incrementing key, `bbolt.Bucket.NextSequence` + big-endian encoding), a **transaction** watch via `txwatches.Add` into the in-memory map instead (not persisted; see Watch notifications). `watchCmd()` in `main.go` splits `arg` on the first space into the **target** (first token) and an optional **alias** (the remainder, trimmed) — a bare `/watch` prompts for both together in one follow-up message — then classifies the target via `isTxid` (exactly 64 hex characters → transaction, anything else → address) — a heuristic, not real validation, good enough to route the watch. The alias is echoed in the confirmation, appended in parens to the notification header (`…watched address bc1q…dayd2g (John)`), and shown in `/watches`; it's `html.EscapeString`'d at every display site since it's arbitrary user text. `watches.List()` (used by `startNotify`, `/watches`) returns every stored watch; `watches.Remove(chatID, address)` deletes every record matching **both** fields and returns the count — the `chatID` half is the security scoping that stops one chat from removing another chat's watch, and the count lets `/unwatch` distinguish "removed" from "you weren't watching that". It collects keys during a `ForEach` and deletes them after, because bbolt forbids mutating a bucket mid-iteration. Only address watches are persisted, so the record carries no type field (the `WatchID` JSON key is kept for compatibility with records written before the package split).

### Block info cache

`/info <height>` is served from a cache (the `blocks` bucket) so the expensive per-block fee computation happens in the background, not in the user's request. `blocks.go` holds one JSON `blockInfo` per height (big-endian key via `itob`, reusing the rates/watches idiom): height, hash, time, size, tx count, miner, `FeesOK` + fee min/avg/max (BTC), tx-size min/avg/max (bytes), reward, and total (reward + fees = the coinbase output). `computeBlockInfo(hash)` builds a record from one `getBlockVerbose` (verbosity 2 → all txs with sizes, vins, vouts) plus the concurrent prevout fetches `blockFees` needs; reward comes from `subsidy(height)` (50 BTC, halving every 210000 blocks) and total from summing the coinbase outputs, so reward/total never need prevouts — only the fee distribution does. Amounts render in satoshi via `satoshi()`/`group()` (`group(int64)` is the shared space-thousands helper `satoshi` now routes through), sizes via `group`. Confirmations and the old header-only path are gone; `formatBlock` builds the aligned `<pre>` block from label/value pairs.

Three things populate the cache, all funneling through `computeBlockInfo` + `storeBlock`:
- **On-demand**: a `/info` cache miss computes and stores the block (so an old, uncached block is slow once, then instant).
- **New blocks**: `main()`'s block-cache startup subscribes via `notifyBlocks`, and `notifier.Handle` turns each `blockconnected` notification into `go cacheBlockHash(newTipHash)`. Verified against a real regtest node that btcd actually sends the legacy `blockconnected` (`[hash, height, time]`), not only `filteredblockconnected`.
- **Backfill**: `startBlockCache()` (launched from `main()`) loads the mining pools, subscribes to blocks, then walks back from the tip caching `blockBackfillDepth` (var, default 50) recent blocks, skipping any already cached — so history is available immediately and the heavy pass runs once (idempotent across restarts). `storeBlock`/`loadBlock` are nil-`db` guarded, so block lookups still work (compute-only, no caching) in tests that don't open a db.

**Miner attribution** (`miners` package): the `miners` bucket maps each pool's coinbase output address to its name and `miners-tag` maps each pool's coinbase **tag** (the marker pools write into the coinbase scriptSig, e.g. `Mined by AntPool`, `/Foundry USA Pool/`) to the same. `miners.Attribute(addresses, coinbaseHex)` is the single attribution entry point used by both `computeBlockInfo` and the stats collector: it tries every coinbase output address as an exact key lookup first, then falls back to scanning the tag bucket for a tag contained in the (hex-decoded) coinbase script, returning "" when neither matches — callers turn that into "Unknown" (`computeBlockInfo`) or skip the block (the collector).

Both halves of that are load-bearing, and both were established by measurement against the real mainnet node over the same 100 blocks:
- **Every** coinbase address must be tried, not just the first: modern coinbases carry several outputs and the pool's payout isn't reliably output 0. First-address-only attributed **8**/100.
- The **tag** fallback carries most of the attribution: the big pools rotate payout addresses far faster than `pools-v2.json` lists them, so address-only (all addresses) still attributed only **25**/100 and missed *every* major pool — the misses were AntPool, Foundry USA, F2Pool and MARA, each of which names itself in its coinbase tag. With tags: **98**/100, and the ranking matches the real network (Foundry 31%, AntPool 22%, F2Pool 12%). Tag matching is plain **substring** matching, not regex — of the 201 tags in the real file exactly one contains a regex metacharacter and it is a literal `$`. Tags are scanned from the database (a couple hundred rows per block), not from an in-memory copy, so the DB-backed design holds. The shortest tags are 4 bytes (`Kano`, `emcd`, `HHTT`, `EMC `), so a false positive on random coinbase bytes is possible in principle; this is the same heuristic mempool itself ships.

`miners.Start()` (from `main()`, before the block cache) keeps both buckets fresh: an initial fetch of mempool's `pools-v2.json` **only when the address bucket is empty** (a fresh install) — a populated bucket survives restarts, so the definitions are not re-downloaded every start — then a refresh every 24h (`updateInterval`, a package var for tests). `update()` only ever `Put`s the file's addresses and tags, never deletes: the source only adds, so old entries stay valid and no full re-sync is needed. `sourceURL` is also a package var for tests. The real file currently holds 171 pools, 218 addresses and 201 tags. One caveat of the async refresh: on a *fresh* install the initial fetch races the block-cache backfill, so a few of the first-backfilled blocks may cache "Unknown" until re-computed; a populated bucket (any later restart) has no race.

### Miner statistics

`miners/stats.go` keeps a running per-pool aggregate in the `miners-stat` bucket, **keyed by pool name** — so every address and every tag belonging to one pool combines into a single record — and `/miners` prints the top 10 from it. The stored `stat` (unexported) is `Blocks`, `Reward` (BTC, subsidy + fees = the whole coinbase output), `Fees` (BTC), `Work` (Σ difficulty × 2^32, the expected hashes) and `LastWork` (the work of that pool's most recent block).

`StartStats(src)` (from `main()`, only when btcd is configured) runs `collect` immediately and then every `statInterval` (10 min, a var for tests). The `miners` package can't reach btcd — that connection is package `main`'s — so the chain data is injected through the small `Source` interface (`Tip`, `Block`), implemented by `minerSource` in `blocks.go`: per height a `getBlockHash`, a `getBlockTxids` (verbosity 1 → height, **difficulty**, txids — `btcdBlockTxids.Difficulty` was added for this) and a `getRawTransaction` of the coinbase, giving every payout address, the coinbase script (for the tag) and the total output; fees are that total minus `subsidy(height)`.

- **Cursor**: `miners-block` holds one JSON `cursor{Start, Last}` under the key `cursor` — `Start` is the first tracked height (the window the consumption share is computed over), `Last` the last processed. A run resumes at `Last+1`; on a fresh install it starts at `tip − initialWindow + 1` (1000, a var), so `/miners` has about a week of history without walking from genesis.
- **Chunking**: a gap wider than `chunkSize` (1000) is processed in chunks — each chunk aggregates into an in-memory `map[name]*stat` and is then merged into the bucket by `flush` in **one** transaction that also advances the cursor, so catching up thousands of blocks doesn't build one giant transaction and a crash mid-catch-up resumes from the last flushed chunk. `Blocks`/`Reward`/`Fees`/`Work` accumulate; `LastWork` is overwritten (chunks run oldest-first, so the newest write wins).
- **Waiting for the definitions**: `collect` early-returns while the address bucket is still `empty()`, so a fresh install doesn't spend its whole initial window on blocks nothing can be attributed to — it starts once `miners.Start()`'s first fetch lands.
- **A failed block fetch abandons the run** (no flush, cursor untouched) so the next tick retries the same range. Skipping the block and flushing anyway would step the cursor over it and drop it from the aggregate permanently — and a btcd restart mid-catch-up fails *every* block in the chunk, not one. The cost is that a genuinely unfetchable block stalls the collector, which is at least loud: the same warning every 10 minutes.
- A block whose miner can't be attributed (`Attribute` returns "") is skipped rather than counted under "Unknown", so the shares below are shares of the *attributed* blocks. Blocks reorged out after being counted stay counted — not worth correcting in an aggregate this coarse.

**The power estimate.** `Top(n)` returns `Stat{Name, Blocks, Reward, Fees, ConsumptionGW}`, sorted by blocks descending and **tie-broken by name** so a tied list is stable between calls. Consumption is the pool's share of the window's blocks × the *current* network hashrate × an assumed hardware efficiency:

    ConsumptionGW = (Blocks / (Last−Start+1)) × (LastWork / 600) × joulesPerHash / 1e9

`LastWork / 600` is the current network hashrate (that block's difficulty × 2^32 over the 10-minute target), which is why the record keeps `LastWork` at all: it carries the difficulty **in force now**, where dividing the accumulated `Work` by the window's seconds would average in every past difficulty epoch. `joulesPerHash` is `1e-11` — **the most modern mining hardware**, the latest hydro-cooled ASICs at ~10 J/TH (Antminer S23-class). Real fleets mix in older machines, so this is deliberately a lower bound: the "if they ran today's best gear" figure. Note `LastWork` alone can't rank miners (it's network difficulty, near-identical for everyone) — the block share is what differentiates them.

`/miners` (`minersCmd` in `main.go`) sends `Top(10)` as a plain numbered list — `1. AntPool. 22 blocks mined, reward 69.14 BTC, fees 0.39 BTC, consumption 2 GW` — with `trimNum` (a `format.go` helper: fixed decimals, trailing zeros trimmed) at 2 decimals for BTC and 1 for GW, and a singular "1 block". An empty bucket replies "No miner statistics yet — still collecting."

Verified against the real mainnet node over 100 blocks (throwaway probe, not in the suite): 98 attributed across 10 pools in ~7s, Foundry USA 31 blocks / 2.8 GW down to Braiins 1 block / 0.1 GW, the ten summing to 8.9 GW against a 9.1 GW whole-network figure at that difficulty — self-consistent, and about half of published real-world estimates, as the best-gear assumption implies. In the suite, `miners/stats_test.go` drives `collect` through a fake `Source`: `TestCollectStats` (aggregation by name across two addresses of one pool, plus a payout that isn't output 0), `TestTopConsumption` (the formula, pinned so that an accumulated-`Work` version would fail), `TestCollectChunks` (a chunk is flushed to the database before the next begins, asserted from inside the source's next fetch), `TestCollectResumes` (only new heights are fetched, stats accumulate, the window grows), `TestCollectRetriesOnError` (a failed fetch leaves the cursor and the bucket untouched, and the retry picks up the whole range) and `TestCollectWaitsForAddresses`. `TestMinersFlow` in `flow_test.go` covers the command's exact rendering by seeding the buckets directly.

### Exchange rates

The `rates` package keeps a BTC/USD price history in the `rates` bucket (same db file, via `rates.Init(db)` called from `openDB`), so `/info` and notifications can show a rough fiat value. Each internal `rateRecord{Time, USD}` (unexported; the value is always USD) is stored under its `Time.Unix()` big-endian key, so keys sort chronologically. `rates.Start()` (launched from `main()` right after `openDB`) backfills the daily history once (see next paragraph), fetches a current rate immediately, then refreshes every 5 minutes: the internal `update()` hits all price `sources` (CoinGecko, Coinbase, blockchain.info — free, no-auth GETs), **averages the ones that succeed** (a failed source is just skipped; if all fail nothing is stored), and writes one averaged record via `rates.Add(usd)`. The updater goroutine isn't explicitly stopped on shutdown — `main()` returns microseconds after `closeDB`, so a write-after-close is effectively impossible. Each source has a `parse` func tested against real API payloads (blockchain.info returns *every* fiat — we pluck `USD.last` out of it); `sources` is a package var so tests point it at `httptest` servers.

**Historical backfill:** so `/info` on an *old* transaction can show USD from around its block time (not just today's rate), the internal `backfill()` loads the whole daily series once. It's a no-op when the store already holds deep history — `hasHistory()` is true when the oldest sample is older than `historyHorizon` (3y), which live updates alone can't produce on a fresh bot, cleanly distinguishing "backfilled" from "just started". Otherwise it GETs blockchain.info's `market-price` chart (`historyURL`, `timespan=all` — the entire daily series back to 2009 in one no-auth request), parses it with `parseHistory` (skipping the zero-price pre-market days), and writes every day in **one** transaction via `storeMany` (per-record `db.Update`s would be thousands of fsyncs). Backfilled records land at daily 00:00-UTC timestamps, so they never collide with the live `time.Now()` samples. Verified once against the real endpoint (6402 daily samples, 2009→today); `historyURL` is a package var so tests point it at an `httptest` server, and `TestBackfillRates` also asserts the `hasHistory` guard by counting HTTP hits across two calls.

Two reads, **both DB-only, never online**: `rates.Last()` (cursor `Last()` — the newest sample) and `rates.At(t)` (the sample nearest `t` via `Seek`+`Prev`/`Last`, or not-found if the closest is more than the internal `tolerance` = 36h away). That tolerance is deliberately wider than a day so the daily-granularity backfill (samples at 00:00 UTC) still matches a transaction at *any* time of day — with a 1h tolerance `At` missed almost every daily sample and fell through to today's rate, defeating the backfill; live 5-min samples still match far more tightly. Both return the price as a plain `float64` and `(0, false)` when `db == nil` or nothing is stored, so USD is silently omitted in tests that don't open a db — USD is best-effort enrichment, not a hard dependency. `amountLine(btc, at, current)` (in `format.go`) renders `"<sat> sats (≈ $usd)"`, appending the USD part only when a rate is available: `current=true` uses `rates.Last()` (mempool `/info` and **new-transaction notifications**, which have no confirmed time = "now"), `current=false` uses `rates.At(at)` (a confirmed transaction's block time) **but falls back to `rates.Last()` when `At` finds nothing**. With the daily backfill in place `At` resolves almost any historical tx to its period's rate; the `Last()` fallback is the safety net for a tx in a genuine gap. USD only vanishes entirely when there is *no* stored rate at all. `usd(btc, rate)` (also `format.go`) drops cents from $100 up (`"$90,000"`, comma-grouped whole dollars, rounded) and keeps them below $100 (`"$58.23"`), on the logic that cents are noise on large amounts but the whole point on small ones. Both `usd` and `group` split the **sign** off before doing any of that, because the outgoing-watch `Net` line is the one place they see a negative and both used to mangle it — `group` counted back from the end of the whole string and produced `"- 100 010 000"`, `usd` took the below-$100 branch for any negative and produced `"$-29450.00"` (`TestNegativeAmounts` pins both). Only transaction *amounts* get USD — blocks and addresses have no amount.

### Command dispatch and the "pending argument" pattern

`update()` in `main.go` is the single entry point for every incoming Telegram update: pull `Update.Message`, log it (`logMessage`), split it into a command and argument (`parseCommand`), then switch on the command. `/start`, `/watches`, `/fees`, `/mempool`, and `/miners` (see Miner statistics) take no argument and act immediately (`/start` sends a fixed `<b>`-formatted bulleted help listing the commands; `/watches` (`watchesCmd`, renamed off the `watches` package) lists the calling chat's watches — Addresses from `watches.List()` filtered by `chatID`, Transactions from `txwatches.For(chatID)` — and prints each id **un-shortened** inside `<code>…</code>` for Telegram tap-to-copy; ids are `html.EscapeString`'d because address watch ids are arbitrary unvalidated user input, unlike txids).

`/fees` (`fees()`) replies with current network fee estimates for three confirmation speeds — Fast (10-20 min → 2-block target), Medium (~1h → 6 blocks), Slow (2h+ → 12 blocks) — via btcd's `estimatefee`. The three per-tier `estimatefee` calls are fired **concurrently** (one goroutine each, joined by a `sync.WaitGroup`, each writing its own index of a `results` slice so there's no shared-state race — verified under `-race`), multiplexed over the single jsonrpc2 connection, so the reply waits on the slowest call instead of the sum. btcd returns **BTC/kB** (its help text says "satoshis" but the handler returns `float64(BtcPerKilobyte)`, confirmed against source); `fees()` converts to sat/vB by ×1e5 and renders an aligned `<pre>` table. Two graceful-degradation paths, both verified: `btcd == nil` → the same "not configured" message as `/info`; and btcd's estimator returns `not enough blocks have been observed` until the node has seen enough mempool activity (so a per-tier failure shows `n/a`, and all-failed collapses to a short "not available yet" note — this is what a fresh/regtest node returns, confirmed by real-node E2E). Labels deliberately avoid `<`/`>`/`&` (e.g. "2h+" not ">2h") so the fixed field text needs no HTML-escaping and the `len()`-based column padding matches the rendered width.

`/mempool` (`mempoolCmd()`) replies with the mempool's size and transaction count — both cheap from `getmempoolinfo`, rendered with a metric suffix via `metric(f, 1)` ("3.2 M", "6.7 k") — and, when the mempool is small enough to summarize in reasonable time, the summed output **amount** and summed **fees** across every mempool transaction, each in BTC and USD via `btcAmount` (these totals reach thousands of BTC / billions of sats, so BTC not sats; ≥1 BTC shows 2 decimals, a fraction keeps satoshi precision so fees don't round to "0.06"). `metric` is the shared metric-suffix helper `formatBlock`'s difficulty now also routes through. It also shows a `Flow rate` — transactions/sec flowing into the mempool and how that rate is changing (`2.5 tx/sec (+0.5)`): `startMempoolFlow` (from `main()`) polls `getmempoolinfo` every `flowInterval` (10s, var) and feeds each tx count to `updateFlow`, which keeps `flowRate` = Δcount ÷ interval and `flowChange` = Δrate **in memory only** (`flowMu`, never persisted; the goroutine isn't stopped on shutdown, like the rates updater). The rate is **recomputed only when the count rose** — a drop (`delta ≤ 0`) most likely means a block was just mined, which would skew the inflow measurement, so the previous rate/change is kept; the count is still re-baselined so the next rise spans one clean interval. The rate needs 2 samples and the change 3, so both fields are omitted until warm — and the flow line shows even when the totals are skipped, since it's already computed in the background rather than per-command. `mempoolTotals` reads the fees straight from `rawMempoolVerbose` (one `getrawmempool true` call, which also yields the txid list) and computes the amount by fetching every transaction's outputs **concurrently** (bounded `sem` of 16); individual tx churn between the two passes is tolerated (skipped), but a context timeout returns `ok=false` → `Totals: unavailable`. The totals are gated by `mempoolSummaryLimit` (var, default 20000 txs) — above it the reply shows `Totals: skipped (mempool too large)`, since both the verbose fetch and the per-tx fetches scale with the tx count. Measured on the real node: at ~8500 txs the whole thing is ~4s (verbose ~3s + per-tx amount ~1s); getmempoolinfo alone is ~6ms. The `Total amount` is the sum of all outputs, so it's inflated by change — not "value being transferred".

Commands that take a free-text argument (`/info`, `/watch`, `/unwatch`) share one shape: called with an argument (`/info foo`) they act immediately; called bare (`/info`) they reply asking the user to send the text as a follow-up message and mark that chat "pending" for that command. The next plain-text (non-command) message from a pending chat is then treated as the missing argument.

Pending state is tracked per command with its own package-level `sync.Mutex` + `map[int64]bool` (`pendingInfoMu`/`pendingInfoChats`, `pendingWatchMu`/`pendingWatchChats`, `pendingUnwatchMu`/`pendingUnwatchChats`) — there is no shared/generic pending mechanism, and that's intentional: an earlier pass had the opportunity to unify this and deliberately kept it duplicated per command. Follow that precedent for any new argument-taking command rather than generalizing. `update()`'s `case ""` checks the pending maps in order (info, watch, unwatch), each `return`ing after it handles the follow-up.

All three are implemented the same way, short handler names (`info`, `watchCmd`, `unwatch`) with no wrapper functions around their pending-state maps: the lock/set-or-delete/unlock logic is inlined directly into `info()`/`watchCmd()`/`unwatch()` (setting pending) and into `update()`'s `case ""` (checking and clearing pending). There was an earlier pass where `/info` kept named helper functions (`setPendingInfo`, `takePendingInfo`, `clearPendingInfo`) while `/watch` was already inlined — that asymmetry was deliberately removed by request, so treat the current inlined-everywhere shape as the pattern to extend, not something to re-wrap in helpers.

## Style conventions specific to this repo

These diverge from typical idiomatic Go on purpose (established through explicit instruction over this repo's history) — don't "clean them up":
- Indent with 4 spaces, never tabs — this includes running `gofmt`/`goimports` with a post-process step (or an editor setting) to expand tabs, since Go's own tooling always indents with tabs by default.
- Prefer unexported identifiers even for the main API (`bot`/`newBot`/`send`, not `Bot`/`NewBot`/`SendMessage`) — nothing outside `package main` consumes this code.
- One `import "x"` line per import, never a grouped `import (...)` block.
- `var x = expr()` instead of `x := expr()` wherever Go's grammar allows it. It doesn't allow `var` in an `if`/`for` initializer, and a `var` can't redeclare a name already in scope the way `:=` can (e.g. `req, err := ...` when `err` already exists) — those cases keep `:=`.
- No blank lines inside function bodies; blank lines appear only between top-level declarations.
- Minimal comments: none explaining *what* code does, only rare ones for non-obvious *why*.
- Single-line `if err != nil { return nil, err }` where it fits on one line.
- Avoid introducing a helper function for logic used at only one call site — inline it instead. This is about small pieces of logic, not decomposition: a handler that has grown genuinely large may be split (`info()` was deliberately split into `transaction`/`block`/`address` by explicit request).

## Testing approach

Tests (`flow_test.go`, `log_test.go`) never hit real Telegram or a real `telegram-bot-api` proxy. They spin up an `httptest.Server` standing in for the Bot API, build a `bot` pointed at it (`newBot("TESTTOKEN", server.URL)`), and drive behavior by calling `update()` directly with hand-built `Update` values — then assert on the outgoing `sendMessage` request bodies the fake server captured (and, in `log_test.go`, on `log` package output captured via `log.SetOutput`).

Any test that exercises `/watch`, `/unwatch`, or the notifier must open the database first (`openDB(filepath.Join(t.TempDir(), "watches.db"))` + `defer closeDB()`) — `openDB` also hands the handle to `rates.Init`/`watches.Init`, so their package globals are unusable (nil db → panic) until it runs — and should reset the notification state (`stopNotify`, which also `txwatches.Reset()`s the confirmation map) and `btcd` for isolation, since these are package-global and shared across tests, which run sequentially. The storage packages have their own tests: `watches/watches_test.go` and `rates/rates_test.go` open a temp bbolt file via `Init`, and `txwatches/txwatches_test.go` exercises the in-memory map directly; the price-display tests (`usd`/`amountLine`) live in `format_test.go` in `package main` and seed a rate through `rates.Add`. `TestMessageLogging` redirects the global logger with `log.SetOutput(&buf)` and **must restore it with `defer log.SetOutput(os.Stderr)`, not `log.SetOutput(nil)`** — a nil writer makes every later `log.Printf` (e.g. `logMessage` in any subsequent `update()`-driven test) panic. That was a latent bug that only surfaced once a logging-path test was ordered after it.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

bitnsbot is a Bitcoin network events notification bot for Telegram. It talks to a **Bitcoin Core** node (it used to target btcd — see The Bitcoin Core client below for what that change cost and bought). It's a single Go binary built almost entirely on the standard library — the exceptions are `go.etcd.io/bbolt` (the embedded KV store holding watches, the block cache, rates, miner stats and the address index) `github.com/go-zeromq/zmq4` (pure Go, no cgo — Core publishes its notifications over ZeroMQ and the standard library has no ZMTP implementation), and `github.com/pin2t/flagex` (the `-config` properties-file parser — see The config file below). Core's RPC is plain HTTP, so it needs nothing beyond `net/http`. It receives updates via a Telegram webhook (not long polling). Alongside the bot, `tools/` holds small standalone commands in the same module (see Tools below).

## Commands

- Build: `go build ./...`
- Run: `go run . -bot-token <token> -webhook-url http://localhost:8080/bot -api-base-url http://localhost:8081`
- Test all: `go test ./...`
- Test one: `go test -run TestWatchFlow -v` (other tests: `TestInfoFlow`, `TestUnwatchFlow`, `TestWatchesFlow`, `TestWatchNotification`, `TestShutdown*`, `TestMessageLogging`, `TestLoggingLevels`, `TestWatchStore*`, `TestRate*`, `TestUSDFormat`, `TestAmountLineUSD`, `TestCore*`, `TestParseTx*`, `TestAddrIndex*`, `TestAba*`, `TestMenu*`, `TestMarket*`, `TestButtons*`, `TestAddrStats*`). Run the whole suite with `-race` (`go test -race ./...`) — the watch-notification path is concurrent.
- i18n check: `go build -o /tmp/i18n-vet ./tools/i18n-vet/ && /tmp/i18n-vet .` (see Internationalisation below)
- Vet: `go vet ./...`

There is no Makefile or linter config in this repo — `go build`/`go vet`/`go test` plus `i18n-vet` are the only checks available, and are exactly what `.github/workflows/ci.yml` runs on every pull request (on Go 1.26, with `-race -coverprofile`). **`i18n-vet` runs in CI**, so a new translated string with no translation fails the build. `gofmt -l .` will flag files as unformatted by design; see Style below before "fixing" that.

Flags (all in `main.go`): `-config` (path to a `name=value` properties file to load flag values from — see The config file below), `-verbose` (log level 0/1/2 — see Logging below), `-bot-token` (Telegram bot token, required), `-listen` (address this bot's webhook server binds to), `-webhook-path`, `-webhook-url` (the URL registered via `setWebhook`), `-api-base-url` (Bot API server to call), `-secret-token` (optional), `-register-webhook` (set false to skip calling `setWebhook` on startup), `-db` (path to the bbolt watches database, default `watches.db`), `-core-url`/`-core-user`/`-core-pass`/`-core-cookie` (Bitcoin Core's JSON-RPC endpoint and credentials — either user/pass or the `.cookie` file Core writes into its data directory; leaving `-core-url` empty skips connecting to the node entirely), `-core-zmq` (comma-separated ZMQ endpoints publishing `hashblock` and `rawtx` — see The ZMQ notification path below), `-core-rest` (base URL of Core's REST interface, which the address index builds from; empty disables indexing), `-backup`/`-backup-interval`/`-backup-script` (periodic database copies; empty `-backup` disables them — see Database backups below), `-log-no-ts` (omit the date/time prefix from each log line, for journald which timestamps them itself), `-dbui-listen` (address for the database admin web UI, empty disables it — see The database UI below), `-history-file` (path to a JSON file of historical BTC/USD rates in blockchain.info's chart format, so the rates backfill can load from disk instead of the network).

## Deployment (scripts/)

`scripts/` holds the Raspberry Pi / systemd continuous-deployment helpers (`install.sh`, `update.sh`, `uninstall.sh`, `README.md`) — not part of the Go build. The runtime package is self-contained under `/opt/bitnsbot` (`bitnsbot` binary, `bitnsbot.conf`, `bitnsbot.db`); the source checkout stays where cloned (default `/home/pi/bitnsbot`). `install.sh` (run as root) builds+tests **as the checkout's owner** (via `runuser`, non-login shell with explicit `HOME`/`PATH` so `go` is found and captured git output stays clean), installs the binary, writes a systemd unit ordered `After=bitcoind.service` (running as that user), and schedules `/etc/cron.d/bitnsbot` to run `update.sh` every 5 minutes. `update.sh` fetches `origin/master` and acts **only when it is strictly ahead** of the deployed `HEAD` (checked with `git merge-base --is-ancestor` — a plain `HEAD != origin/master` would rebuild-loop whenever the local checkout is ahead); it fast-forwards, rebuilds, runs the full suite, and only on success atomically swaps the binary and restarts — a `flock` prevents overlapping runs. See `scripts/README.md`. The config template it writes is Bitcoin Core-shaped (`core-url`, `core-cookie`, `core-zmq`, `core-rest`) — worth keeping in step with the flag set, since the `-config` parser treats an unknown name as fatal, so a stale template breaks startup rather than degrading. These are validated with `bash -n`, by exercising the git decision logic against throwaway repos, and by booting the emitted template against a real node — every key checked against the binary's actual flags, cookie auth exercised, and a mined block confirmed arriving over ZMQ. The systemd/cron paths can only be verified on the target host.

## Tools (tools/)

`tools/` holds standalone command-line programs that ship with the repo but are no part of the bot: each subdirectory is its own `package main`, so `go build ./...` builds them alongside the bot and `go test ./...` runs their tests.

- `advertise` — announces a Bitcoin node's address to btcd's known peers over the P2P protocol (detailed below).
- `addresses` — scans the chain from genesis to tip and collects every address seen, resuming from its own cursor bucket.
- `top-active` — the same scan, ranking addresses by activity.
- `addrindex` — builds and queries the address index from the command line, driving the same `addrindex` package, buckets and cursor the bot does; `actbuild` adds a second pass that records busy addresses, `richbuild` sums what every address on the chain currently holds into SQLite, `ababuild` ranks the addresses holding coins by how long since those coins last moved, and `list -dbsqlite` reads the SQLite copy `tosqlite` makes instead of the bbolt original (detailed below).
- `addrindex-scan` — an earlier, single-purpose version of `addrindex list`. Largely superseded by it; kept only because nothing has been said about removing it.
- `csvimport` — loads CSV files into the bbolt database, one bucket per file (detailed below). The reverse of the database UI's export, and how a table built elsewhere is handed to the bot.
- `bboltwui` — runs the database admin web UI (the `dbui` package) as its own process, so a bbolt database can be inspected without the bot running. It has a README of its own, screenshots included.
- `tosqlite` — migrates the bbolt database to SQLite (detailed below). It and `addrindex`'s `-dbsqlite` listing are the only things in the repo that need a database driver, and it is the one dependency the bot itself does not link.
- `i18n-vet` — the translation checker CI runs over the Go string tables; see Internationalisation below.
- `i18n-html` — the same idea for the Mini App's translated pages, which are whole second copies of a file rather than a table with an entry missing; see The Mini App's translations below. CI runs it too.

`tools/advertise` announces a Bitcoin node's address to the peers btcd already knows. It reads btcd's `peers.json` (the addrmanager dump: `{"Addresses":[{"Addr":"1.2.3.4:8333","LastSuccess":…}, …]}`), and for every **IPv4** peer performs the P2P version/verack handshake and sends a one-entry `addr` message — which is exactly how a node's address spreads through the gossip layer. Flags: `-peers`, `-advertise` (default `178.46.128.227:8333`), `-workers` (64), `-timeout` (10s), `-limit`, `-live`, `-verbose`. IPv6 and `.onion` entries are skipped: those need a working IPv6 route and a Tor proxy respectively.

The wire format is **hand-rolled on the standard library** rather than importing btcd's `wire` package — the whole job is three message types, against a dependency that would pull in a full node's stack. Only what the handshake and the announcement need is implemented, deliberately: `version`, `verack` and `addr`, and nothing else. `message()` builds the envelope (magic, 12-byte null-padded command, length, and the first four bytes of the double SHA-256 as checksum), and `versionPayload`/`addrPayload` build the two payloads out of the shared 26-byte `netAddress` (services, IPv4-mapped IP, port in network order). The two varint-prefixed fields — the user agent's length and the address count — are written as **plain single bytes**, because the multi-byte varint forms start at 0xfd and neither value can reach it; an earlier version carried a general four-branch varint encoder whose other three branches were unreachable. Incoming messages are read only far enough to see the command: `announce` reacts to `version` and `verack` and ignores everything else (`sendaddrv2`, `wtxidrelay`, `sendheaders`, …) without parsing a single payload, and peer checksums are not verified since nothing is decoded. Our version claims **no services and relay=0**, so a peer doesn't start streaming transactions down a connection about to be closed; the advertised address claims NODE_NETWORK|NODE_WITNESS, which is what makes peers keep and relay it. `TestMessageEnvelope` pins the envelope against the canonical empty-`verack` vector (`f9beb4d9…5df6e0e2`), `TestVersionPayload`/`TestAddrPayload` pin the two hand-written payload layouts (including those single-byte length prefixes), and `TestAnnounce` drives the whole exchange against a fake peer that speaks the protocol — including junk (`sendaddrv2`) before its verack, which must be ignored.

**Most of `peers.json` is dead weight**, which is worth knowing before running it: in a real 7.7 MB file of 34288 addresses, 23276 were IPv4, but only **4016 had ever been dialled by btcd and only 463 ever answered** — the rest is unverified gossip. A first run against the file's leading entries reached **0 of 20** peers, all failing at `dial`. `-live` keeps only addresses with a real `LastSuccess`, and over those the same run reached **14 of 25**. So default (all peers) is what the tool was asked for, but `-live` is the flag to use when you want it to finish quickly.

Verified against the live network: 7 of 7 selected peers completed the handshake and took the `addr`, including this repo's own btcd node at its P2P port. A throwaway probe then sent `getaddr` immediately after the `addr` and got healthy `addr` replies back (30003 bytes from the local node — 1000 addresses), confirming peers do not treat the message as malformed and drop the connection.

### tosqlite

`tools/tosqlite` copies the bbolt database into SQLite — `tosqlite -src bitnsbot.db -dst bitnsbot.sqlite.db`. Seven buckets become six tables: `blocks`, `market`, `rates` and `watches` map one to one, `addrindex` packs its composite key into a column, and the three miner buckets combine.

The driver is **`modernc.org/sqlite`** (cznic's, whose source is gitlab.com/cznic/sqlite): a pure-Go translation of SQLite with no cgo, so the repo still cross-compiles the way the rest of it does. It is the tool's dependency, not the bot's — nothing under `/` imports it — but it is by far the heaviest thing in `go.mod`, pulling in `modernc.org/libc`, `mathutil`, `memory` and five smaller packages, and it bumped `golang.org/x/sys` to v0.47.0 and `x/sync` to v0.21.0.

**Three corrections to the requested DDL, all forced by SQLite**, and one of them silent:
- A table may carry only **one** `PRIMARY KEY` clause. `miners`, `rates` and `watches` each named several, which is a hard error (`table "rates" has more than one primary key`). `miners` and `watches` became composite — `(name, address, tag)` and `(chat, addr)` — while **`rates` keys on `ts` alone**: a bbolt rate is keyed by its timestamp, so the timestamp is already unique and `cents` added nothing to the key. Keying on the bare integer also makes `ts` a rowid alias, which is the cheaper table.
- `blocks` was written `height INTEGER RIMARY KEY`. That does **not** fail: SQLite reads `RIMARY KEY` as the tail of the column's *type name*, so the table would be created with no primary key at all and nobody would be told. Fixed to `PRIMARY KEY`.

Five decisions the mapping rests on:
- **`addrindex.shard` holds the whole bbolt key.** That key is a 2-byte shard plus a 4-byte block-range index, both big-endian; all six bytes read as one integer fit in 48 bits and keep the ordering a lookup's cursor scan depends on (`shard<<32 | rangeIndex`).
- **`blocks.fees` is `total - reward`.** The record stores `reward` and `total`, where total is the whole coinbase output; the difference is the fees, and reward + fees recovers it exactly.
- **`rates` takes its timestamp from the key**, which is the only place it exists — the stored value holds nothing but the price, tagged `json:"-"`. A key still wearing dbui's `hex:` marker (a database rebuilt from a CSV export whose importer never decoded it) is decoded rather than dropped, with a warning naming the count, because otherwise the whole table migrates as zero rows.
- **Money becomes integer cents** — `market`'s price, cap and volume are stored as floating-point USD and land as cents, the unit the `rates` bucket already uses to keep prices off floats.
- **`miners` zips.** A pool's record carries the addresses and the tags it is recognised by, but nothing links an individual address to an individual tag, so the two lists are paired positionally and padded with `""`; a pool carrying no definitions still gets its one row of aggregates. The alternative — a row per address plus a row per tag — repeats the aggregate twice as often for no more information. A database written before the three miner buckets became one is read in its own shape instead (`miners-stat` existing is what tells them apart), since this is pointed at backups as often as at a live file.

**Old-format records are skipped, not converted**, and the count is reported per table. The satoshi migration changed `blockInfo`'s fees/reward/total and the miners package's reward/fees from float BTC to integer satoshi while keeping their JSON keys, so a surviving old record fails to decode — which is exactly how the bot treats it (a cache miss it recomputes; miner aggregates restart from the collector's cursor). Converting them here would mean guessing a unit from the value's magnitude. Measured on the repo's own 130 GB `tools/addrindex/addrindex.db`: 1 block record of 965 003 is pre-satoshi (genesis), against 138 of 157 miner aggregates.

Operationally: the source is opened **read-only with a 5-second timeout**, so a mistake cannot damage the bot's database and a run against a live bot fails with a message naming the fix rather than blocking forever on bbolt's exclusive lock — migrate a `-backup` copy instead. The destination must not already exist, and is **removed** if the run fails partway, since a partial migration that looks complete is worse than no file. `page_size=16384`/`journal_mode=OFF`/`synchronous=OFF` on one connection is what makes the bulk load fast (never WAL); the whole file is built by this run, so a crash means running it again. **`page_size` has to be set before anything creates a page** — it is fixed when the file header is written and a later one is silently a no-op, which is why it leads the list and why `TestPageSizeTakesEffect` reads it back. 16K measured **9% faster and 11% smaller** than the 4K default (5.53s/1265 MB against 6.08s/1425 MB, three runs each, ±0.04s, over a fixed million-row source held in page cache); on the real 130 GB database, where the read is the bottleneck and 11% fewer bytes are written, the gap was wider still. **Raising `cache_size` was measured and rejected**: it was slower at every size tried — 64 MB by 0.5%, 256 MB by 1.3% — because the inserts are sequential by rowid, so there is nothing a bigger cache gets to re-read. Rows are committed in transactions of `-batch` (10000), and tables run **smallest first** so a mistake surfaces in the first second rather than after the address index.

Verified end to end against that real database: 965 003 blocks, 8 616 market snapshots, 14 961 rates and 311 miner rows, with block 965 002's `reward + fees` reproducing the stored `total` exactly, the oldest rate landing at $0.07 on 2010-08-18, and the address index streaming at ~56 000 rows/s (1.68 M rows in the first 30 s), which is what the progress line exists to show — a full pass is hours, and a silent run is indistinguishable from a hung one.

### csvimport

`tools/csvimport` loads CSV files into the bbolt database — `csvimport -db bitnsbot.db active.csv abandoned.csv rich.csv`. Each file carries a `key,value` header and one row per entry, and lands in the bucket **its own file name gives**: `active.csv` into `active`, so a path says nothing about where the rows go. It is the reverse of dbui's `/api/export`, and the way a table built outside the bot — a rich list, an abandoned-coins ranking — is handed to it.

Four things about it are deliberate:

- **An existing bucket is merged into, never replaced.** A key the file names is overwritten and one it does not is left alone, so a partial export tops a bucket up rather than truncating it to its own contents. The status line reports how many keys were already there (`120119 rows into active (0 overwritten)`), which is the one thing this tool can otherwise get silently wrong: a fresh load and a re-import of the same file are indistinguishable from the row count alone.
- **The write is batched, not atomic.** A chain-sized table does not fit in one bbolt transaction, so rows commit every `-batch` (100000). That is safe here precisely because a row is written by key: a run that dies partway is recovered by importing the same file again, and `TestCsvImportKeepsCommittedBatches` pins that the batches before a bad row survive rather than being lost in an aborted transaction.
- **Keys and values are stored as the raw bytes of the CSV text**, with no `hex:` decoding. dbui's marker is a display convention of that UI, and honouring it here would corrupt any value that legitimately began `hex:`. The consequence is that a binary bucket cannot be round-tripped through this tool — the CSV has to hold what the bucket should hold, which is why `tools/addrindex`'s own exports were normalized to plain decimal (`active.csv`'s counts were `hex:`-encoded big-endian, and `rich.csv`/`abandoned.csv` named their columns `addr`/`balance`/`lastTx`).
- **The header is required and a bad one is fatal**, the same way the `-config` parser treats an unknown name: a file whose columns are not `key,value` is a file whose meaning is not known, and guessing at it writes wrong data under right-looking keys. Every named file is stat'd before the database is opened, too, so a mistyped name is reported instead of leaving half the import done.

An empty key is refused — bbolt has no such key — and an empty file still creates its bucket, so the result of an import does not depend on whether there happened to be a row in it.

## Runtime model

The bot is designed to run behind a self-hosted `telegram-bot-api` proxy (https://github.com/tdlib/telegram-bot-api) on localhost, not directly against `https://api.telegram.org`:
- `-api-base-url` defaults to `http://localhost:8081`; `telegram.go`'s `bot.call` builds every outgoing request URL from it.
- The webhook HTTP server is a plain `*http.Server` (via `srv.ListenAndServe` in a goroutine) — no TLS. The local proxy is assumed to own the real HTTPS conversation with Telegram; the hop from proxy to this bot is local/plaintext.
- **Graceful shutdown**: `main()` uses `signal.NotifyContext(…, os.Interrupt, syscall.SIGTERM)` and blocks on the returned context; on SIGINT/SIGTERM it calls `shutdown(srv)`, which tears down **in dependency order — webhook server first, then the store**. That order is load-bearing: `srv.Shutdown` blocks until in-flight webhook handlers drain, and those handlers use the watches database, so closing the server first guarantees no handler is mid-request when the database it depends on is closed. (Core needs no teardown at all: its client is stateless HTTP. Under btcd this step also closed a websocket.) After the first signal `stop()` is called to restore default handling, so a second Ctrl+C during a slow drain force-kills. (Note: the old `defer closeDB()` was dead code — `http.ListenAndServe` blocked forever and only ever returned into a `log.Fatal`, i.e. `os.Exit`, which never runs defers; this feature is the first real cleanup path.)
- Two secrets, both flags: `-bot-token` (required) authenticates outbound Bot API calls. `-secret-token` (optional) is passed to `setWebhook` and then checked against the `X-Telegram-Bot-Api-Secret-Token` header on every incoming request (constant-time compare in `main.go`'s webhook handler) — this is the only thing stopping an arbitrary POST to the webhook path from being treated as a real Telegram update. Since both are flags they can be supplied via the `-config` file; prefer that over the command line for real deployments, since command-line args are visible to other users via `ps`.

## Architecture

The bot lives in `package main` in the repo root; supporting packages sit in subdirectories (`logging/`, `lru/`, `rates/`, `watches/`, `txwatches/`, `miners/`, `addrindex/`, `dbui/`, `app/`), each with a small simplified API and its own unexported types. Cross-cutting state that used to be package-`main` globals with compound names (`storeRate`/`lastRate`, `addWatch`/`listWatches`, `addTxWatch`/`txWatches`) now reads as `rates.Add`/`rates.Last`, `watches.Add`/`watches.List`, `txwatches.Add`, etc.

Root (`package main`):
- `telegram.go` — the Bot API client: the unexported `bot` type, `newBot`, and `call`/`send`/`setWebhook` methods, plus the wire types (`Update`, `Message`, `User`, `Chat`) decoded from incoming webhook JSON.
- `db.go` — the bbolt connection: the package-level `var db *bbolt.DB`, `openDB(path)`/`closeDB()`, and the shared `itob` big-endian key helper. `openDB` opens the one file, creates the `blocks` bucket, and hands the same handle to `rates.Init`/`watches.Init`/`miners.Init`/`addrindex.Init` (which own their own buckets) — one file, one handle, **seven** buckets (`blocks`, `rates`, `watches`, the rates package's `market`, the miners package's `miners`, the addrindex package's `addrindex`, and the shared `cursors` — see The cursors bucket below).
- `core.go` — a `coreConn` for talking to Bitcoin Core's HTTP JSON-RPC API (see below).
- `zmq.go` — the ZMQ subscriber, the local transaction parser, and the watched-script/outpoint matcher that replaces btcd's server-side filter (see below).
- `blocks.go` — the `blocks` bucket: cached per-block info records (`blockInfo`), `computeBlockInfo` (builds a record from Core), the startup backfill goroutine, and `formatBlock` (the `/info` block reply). See Block info cache below.
- `db.go` also holds the periodic database backup goroutine (`startBackup`/`backup`), inlined there when `backup.go` was removed. See Database backups below.
- `dbui/` — the localhost database admin web UI (`Start`, plus the list/get/put HTTP handlers and one embedded HTML page). See The database UI below.
- `app/` — the Telegram Mini App web server (`Start(addr, token, Source)`, the embedded page + HTMX, and the initData validation). It can't reach main's fee cache or formatters, so chain data arrives through the `app.Source` interface (`Fees() app.Fees`), implemented by `appSource` in main. See The Telegram Mini App below.
- `i18n.go` — the translation tables and the per-chat language lookup (`trans`, `langTrans`, `SetChatLanguage`, `i18n`). See Internationalisation below.
- `addrindex_source.go` — `restSource`, which builds `addrindex.Block` values from Core's REST interface (see Address indexing).
- `main.go` — flags, the HTTP webhook server, command dispatch (`update`), the `/watch`/`/unwatch`/`/watches` (`watchesCmd`)/`/fees`/`/mempool`/`/miners` handlers, and the mempool flow-rate tracker.
- `notify.go` — the address-watch notification infrastructure (`notification`/`notifyKey`/`notifyChans`, the `notifies` fan-out map, `startNotifyChat`/`stopNotifyChat`/`notifyAddresses`, `broadcast`, `confEstimate`, `startNotify`/`stopNotify`), plus the `watchType` type and `processConfirms` (which formats+sends the transaction-confirmation messages using the `txwatches` package). See Watch notifications below.
- `info.go` — the `/info` command: `info` and its per-kind `transaction`/`block`/`address` handlers plus their helpers (`txInputs`/`fetchInputs`, `blockFeeStats`, `addressHistory`/`addressStats`, `compactAddrs`, …) and the `/info` pending-argument state (see The /info lookup below).
- `format.go` — the shared display formatters `when`/`day`/`relative`/`ago`/`short`/`group`/`sats`/`metric`/`compactBTC`/`periodText`/`durationText`, plus `usd`/`amountLine`/`btcAmount` (which read current prices from the `rates` package).

Packages:
- `logging/` — the leveled helpers `Err`/`Warn`/`Status`/`Fatal`/`Info`/`Net`/`Db` and the verbosity gate (`SetVerbosity`, called once from `main`). Everything in every package logs through these (see Logging below).
- `lru/` — a small generic LRU with optional per-entry expiry (`New`/`Get`/`Put`/`PutTTL`/`Delete`/`Clear`), the repo's one bounded-cache implementation: Core's block caches, the chat→language map and the Mini App's rendered-card cache all use it. It was `lru.go` in package `main` until the app package needed it too; a second copy was the alternative. **`Get` is a write** — it drops an entry it finds expired — so it needs the same lock `Put` does. `Put` stores an entry that never expires on its own; only `PutTTL` sets a deadline, and it is checked on read and nowhere else, so nothing sweeps in the background and an entry nobody asks for just sits until eviction reclaims it.
- `rates/` — BTC/USD exchange-rate history and the 5-minute averaging updater. Public API: `Init(db)`, `Start()`, `Add(usd)`, `Last() (float64, bool)`, `At(t) (float64, bool)` — prices go in and out as plain USD `float64`; the `rate` type is unexported (see Exchange rates below).
- `watches/` — the **address**-watch bbolt store, keyed `"<chat>,<address>"`. Public API: `Init(db)`, `Add(chatID, address, alias)`, `Count(chatID)`, `SetAlias`, `Remove(chatID, address) (int, error)`, `List() ([]Watch, error)`, where `Watch{Chat, Address, Alias}` is the public view and the internal `watchRecord` is not exposed. Only address watches are persisted — transaction watches live in `txwatches`. See The watches store below.
- `txwatches/` — the in-memory one-shot confirmation-watch list (never persisted). Public API: `Add`/`AddAddrConfirm` (register, deduped by chat+addr), `Remove`/`For` (direct `/watch <txid>` entries only), `RemoveAddrConfirms`, `Confirms(txids) []Confirmed` (removes+returns the watches whose txid is in a new block, for the caller to message), `Any`, `Reset`. See Watch notifications below.
- `cursors/` — the one bucket every scan over the chain keeps its place in, keyed by the scan's own name. Public API: `Init(db)`, `Get(name) (int64, bool)`, `Set(tx, name, v)`, and the four names as constants. See The cursors bucket below.
- `miners/` — mining-pool attribution and per-miner statistics, backed by one bucket: `miners` maps a pool's name to a record holding what it has mined and the coinbase addresses and tags it is recognised by (the collector's place is in the shared `cursors` bucket). Public API: `Init(db)`, `Start()` (background definitions refresher), `Name(address) string` ("" when unknown), `Attribute(addresses, coinbaseHex) string` (address then tag, "" when unknown), `StartStats(Source)` (the statistics collector) and `Top(n) []Stat`. `miners.go` holds attribution and the in-memory mappings, `stats.go` the collector, `migrate.go` the fold that produced the one bucket. See Block info cache and Miner statistics below.

### Amounts are satoshi

**Every Bitcoin amount and every fee inside the bot is an `int64` of whole satoshi.** `float64` survives in exactly three places, and nowhere else:

1. **The parse structs** in `core.go` and `rates/`, because BTC-as-a-JSON-number is what the wire format is. Nothing downstream keeps it: values are converted on the way in.
2. **Quantities that are genuinely fractional** — fee *rates* in sat/vB (`fees.go`, `notify.go`'s `feeRate`), block difficulty, the miners package's `Work`/`LastWork`/`ConsumptionGW`, mempool flow in tx/sec, and every USD figure (`usd`, `price`, `money`, `change`, the `rates` package).
3. **The final formatting step**, via `toBTC`, when a number is about to be printed with decimals.

`toSat(btc float64) int64` is the one boundary between the two, and `toBTC(sat int64) float64` converts back **for display only, never for arithmetic**. `toBTC` is exact for every real amount: the 21M-coin supply is 2.1e15 satoshi, well inside float64's 2^53 integer range.

The reason is accumulation, not representation. 0.1 BTC has no exact float64 value, so summing outputs, inputs and fees drifts — which is why `addrstats_test.go` used to assert a *range* (`balance > 0.0998 && balance < 0.1`) where it now asserts the exact `9990000`. Integer satoshi is also what the protocol actually uses; BTC is only ever a display unit.

Two things to know when changing this:

- **`feeStats` rounds its average deliberately** — `(total + count/2) / count`, not plain integer division. It used to be `math.Round` of a float mean, and truncating instead would shift the displayed average down by up to a satoshi.
- **The persisted records changed type but kept their JSON keys.** `blockInfo`'s `minFee`/`avgFee`/`maxFee`/`reward`/`total` and the miners package's `reward`/`fees` are now integers. Keeping the keys is what makes the change safe: a record written before this reads as `{"reward":6.25}`, which now **fails to decode** — and `loadBlock` already treats a decode failure as a cache miss and recomputes. Renaming the keys instead would have decoded cleanly to a silent **zero**. Deployment consequence: previously cached blocks are recomputed on demand rather than served from the cache, and miner aggregates restart from the collector's cursor.

### Logging

Everything logs through the `logging` package — never `fmt.Print*` or the `log` package directly. Its verbosity is set once from `-verbose` via `logging.SetVerbosity(*verbose)` in `main()` (after the `-config` file is parsed, so it's also `-config`-settable), which gates emission:
- `logging.Err`/`logging.Warn` and `logging.Status` (lifecycle lines: "listening on …", "shutting down", "connected to Bitcoin Core …") always print — verbosity 0.
- `logging.Info` (verbosity ≥ 1): high-level events — an incoming message (`logMessage`), a reply sent (`send`), a subscription added/removed (`watchCmd`/`unwatch`).
- `logging.Net` and `logging.Db` (verbosity ≥ 2): raw external traffic and storage requests. NET is emitted from `telegram.go`'s `bot.call` (request method + body, response body) and the `rates` package's `fetch` (each price-API GET + response), plus `core.go`'s `call`, which logs each request method + body and the decoded result (the Authorization header is never logged). DB is emitted from each `rates`/`watches` storage function (and `openDB`).
- `logging.Fatal` is `logging.Err` + `os.Exit` for the startup fatals.

Two deliberate redactions in NET logging, both to avoid leaking secrets that a debug log would otherwise capture: the Telegram request URL (which embeds `-bot-token`) is never logged — only the method and JSON body — and the `setWebhook` body is omitted entirely because it carries `-secret-token`. Everything else (including sent message text and Core payloads) is logged verbatim at verbosity 2.

### The config file

`-config <path>` points at a plain `name=value` properties file whose names are flag names (`core-url=http://127.0.0.1:8332`, `listen=:8082`), read by **`flagex.ParseFile`** from `github.com/pin2t/flagex` and called from `main()` right after `flag.Parse()`. This used to be a local `applyConfig` in `config.go`; that file is gone, the logic having been extracted into the external package.

The semantics it provides are the same ones the local version had, and they still matter: values land in the same `*flag.Flag` variables the rest of the code reads (no separate config struct), blank lines and `#` comments are skipped, an unknown or malformed name is a **fatal** error rather than a silent skip, and command-line flags win over the file (precedence CLI > file > flag default). Because it is driven entirely by the flag set, every flag is automatically config-settable and adding a flag needs no per-flag wiring — which is also why a stale `scripts/` config template breaks startup outright instead of degrading.

### The Bitcoin Core client

`newCoreClient(coreConfig{url, user, pass, cookieFile})` builds an HTTP JSON-RPC client for Bitcoin Core. **Core has no websocket interface**, so unlike the btcd client this replaced there is no connection to dial, hold open, supervise or reconnect — every call is an independent `POST`. That deleted a whole subsystem: the `atomic.Pointer` connection swap, the `supervise` ping goroutine, `reapplyBtcdState`, and `close()` are all gone, and `shutdown` no longer has a node connection to tear down.

Authentication is HTTP Basic, from either `-core-user`/`-core-pass` or `-core-cookie`. The cookie file is re-read rather than cached forever because Core rewrites it with a fresh password on every restart and the bot outlives node restarts; a 401 triggers a re-read so the *next* call succeeds instead of failing forever.

Core speaks JSON-RPC 1.0 with positional (array) `params` and reports method errors **in the body with HTTP 500** — a non-200 status is therefore not on its own a failure, and `call` decodes the body either way.

Because there is no connection to fail at startup, `main()` makes one deliberate `getblockcount` right after building the client so a bad URL or bad credentials are loud and immediate rather than surfacing on the first user command. That failure is fatal, matching how the database's open failure is handled.

Wrapped methods: `getBlockCount`, `getBlockHash`, `getBlockHeader`, `getBlockTxids`, `getBlockVerbose`, `getRawTransaction`, `decodeRawTransaction`, `validateAddress`, `getMempoolInfo`, `getMempoolEntry`, `rawMempoolVerbose`, `estimateSmartFee`, `scanTxOutSet`, `waitForBlock`. Add more the same way: a thin method calling `c.call(ctx, "methodname", []interface{}{...}, &result)`.

**Differences from btcd that changed the code**, all verified against a real node rather than taken from documentation:

- **`getblock` verbosity 2 already reports each transaction's `fee`.** This deleted `blockFees` outright — its bounded 16-way prevout fan-out existed *only* because btcd made callers compute fees themselves. `blockFeeStats` now just reads the numbers Core supplies.
- **Core puts the full transactions under `tx`; btcd used `rawtx`.** The exact reverse of the old gotcha, so the `json:"rawtx"` tag is gone.
- **`getrawtransaction` verbosity 2 gives `fee` and per-input `prevout` — but only for *confirmed* transactions.** A mempool transaction has no undo data, so Core omits both. `txInputs` therefore has two paths: confirmed transactions read prevouts inline with no extra calls at all, while mempool ones still fetch each input's previous transaction (`fetchInputs`, the old bounded fan-out) and take the fee from `getmempoolentry`.
- **`validateaddress` returns the address's `scriptPubKey`.** This is what makes local transaction matching possible without the bot ever encoding or decoding an address format — see the ZMQ path below.
- **`estimatesmartfee` reports "no data" in-band**, as `{"errors":[…],"blocks":0}` with HTTP 200 and no RPC error, so `/fees` treats a missing/zero `feerate` as unavailable rather than waiting for a call to fail. It returns BTC/kvB, converted to sat/vB by ×1e5.
- **`getblock` verbosity 1 carries a `coinbase_tx` field** holding the coinbase *input* — so a block's miner tag is available without a second call. `minerSource` does not use it yet: it still fetches the coinbase transaction because it needs the payout addresses and total output, which that field does not carry.
- **Core has no address index at all** — nothing replaces btcd's `searchrawtransactions`. That is why `addrindex/` exists; see Address indexing below.
- **Core has no server-side transaction filter** — nothing replaces `loadtxfilter`. Matching moved into the bot; see the ZMQ path below.

### The ZMQ notification path

btcd pushed `blockconnected` and `relevanttxaccepted` down the same websocket that carried RPC. Core instead publishes over **ZeroMQ**, which needs no broker: Core `zmq_bind()`s and the subscriber dials in, point to point. `zmq.go` subscribes with `github.com/go-zeromq/zmq4` (pure Go, no cgo, verified interoperating with Core's libzmq).

`-core-zmq` takes a **comma-separated list** of endpoints, because Core publishes each topic on whatever address its own `-zmqpub*` option names — one port or several. A SUB socket dials them all, and subscribing to a topic an endpoint never publishes simply yields nothing. Messages arrive as three frames: `[topic][body][sequence number]`, the last a per-topic counter for detecting drops.

Two topics are consumed. `hashblock` replaces `blockconnected`, spawning `processBlock` and `processConfirms` exactly as the old handler did. `rawtx` replaces `relevanttxaccepted` — but with a crucial difference: **btcd filtered server-side and only pushed relevant transactions, while Core pushes every mempool transaction and the filtering is ours.**

That is why the bot keeps its own equivalent of btcd's filter, in `zmq.go`: a set of watched scriptPubKeys and a set of watched outpoints, both guarded by `watchedMu`. And it is why a ZMQ transaction is **parsed locally** by `parseTx` rather than sent to `decoderawtransaction`: on mainnet this path runs several times a second and almost nothing matches, so an RPC round trip per transaction would be pure waste. `parseTx` reads only what matching needs — the inputs' outpoints and the outputs' scripts — stopping before the witness and locktime it has no use for. Only on a match does the expensive path run (`broadcast`, which decodes over RPC and enriches).

Matching never decodes an address: a watched address becomes its scriptPubKey once via `validateaddress`, and outputs are compared as raw script bytes. Inputs match by outpoint, which is the only way a spend is visible at all — a spend names the outpoint it consumes, never the address. `recordOutpoints` extends that set whenever a watched address is paid, the bookkeeping btcd used to do inside its own filter.

`parseTx` is tested against real transactions captured from a node (a segwit spend, a three-output send, a coinbase) asserted against what Core itself reported, and was additionally run against the live mainnet mempool firehose: 40 transactions parsed, 8 cross-checked field-by-field against the node's own decoding, zero failures. Note its contract — it stops at the end of the last output, so truncating the trailing witness/locktime is legitimately *not* an error, which `TestParseTxRejectsGarbage` pins explicitly.

### Address indexing

Bitcoin Core has no address index, so `/info <address>`'s history stats needed one built in-repo. `addrindex/` is that index; its package comment carries the layout rationale, and the measurements behind it are below.

Three existing implementations were read for their on-disk design before writing this one, rather than guessed at:
- **btcd's `addrindex.go`**: a 21-byte address key into a doubling "level" merge scheme (level 0 holds 8 entries, each level twice the last), storing 12-byte `{block ID, offset, length}` pointers into btcd's *own* block files. Compact, but only possible because btcd owns its block storage — we talk to Core over HTTP.
- **Fulcrum**: RocksDB, scripthash-keyed, measured at **133 GB for mainnet in August 2023**. Bigger than the ratio below because it also caches full UTXO details to serve Electrum clients without round-tripping to Core, which this bot does not need — and ruled out as a dependency anyway, being a second service to run and keep in sync.
- **electrs' current backend, `bindex-rs`**: the closest reference, by electrs' own author and built for Core 31. One RocksDB row per touch, keyed `scriptHashPrefix(8) + globalTxNum(4)` with an empty value, covering both the funding and spending sides. Reports ~10% of blockchain size.

The short version: it follows electrs/`bindex-rs` — hash each `scriptPubKey`, keep an 8-byte prefix, record one entry per "touch" (an address in an output, or in a spent input) — but **shards** rather than keying per address, because bbolt is a B+tree with per-key page overhead and no compression, where bindex relies on RocksDB's LSM and Zstd. The key is `shard(2 bytes of the hash) + rangeIndex(4)` and the value is the packed run of every touch in that shard and 1000-block range, each `remainder(6) + heightOffset(2) + txIndex(2)` = 10 bytes.

A first attempt keyed by address, expecting per-key overhead to amortize across repeated touches; measured on real mainnet blocks it did not, because **71% of addresses are touched exactly once and 96% at most twice**. That cost ~133 bytes per address and projected to 150–250 GB. Sharding measures **18.15 bytes/touch** over 900 real blocks, projecting to roughly 85–113 GB, and makes writes **append-only** — each shard-range value is written once and never rewritten, which is what let the write-side history cap go away. History is now complete on disk; only `Lookup` stops early (`maxLookup`) to bound a Telegram reply, flagged with the same trailing `+` the btcd path used.

**`tools/addrindex`** is the same index, driven by hand. `addrindex build -db ai.db -url http://127.0.0.1:8332 -cookie ./cookie` catches the index up from its cursor to the tip and **exits**, where the bot's `StartBackfill` is the same call on a loop — both go through `addrindex.Build` (which was the unexported `index`), so both chunk identically and either can resume what the other started. `addrindex list … <address>` prints one line per transaction the index holds and then a summary:

```
21 oct 2021 21:00 bbbbbbbb..bbbbbbb1    20000 sat
1 nov 2022 11:00  cccccccc..ccccccc1   -10000 sat
Summary: Balance 10000 sats, Received 30000 sats, Sent 20000 sats, Transactions 2, Activity: from 21 oct 2021 till 1 nov 2022
```

Three things about it are deliberate. The per-line amount is the **net** effect on that address, signed, so the column reads as a ledger and sums to the balance — a transaction that spends from the address and pays change back shows only the difference, where the summary's Received and Sent are gross. **One `-url` covers both protocols**: the build reads REST and the lookups read JSON-RPC, and Core serves them on the same host:port (only the RPC half needs `-cookie`). And the timestamp column is **padded**, since a single-digit day is a character shorter and would otherwise step the listing in and out.

The tool needs its own small JSON-RPC client — four methods against the bot's twenty — because `core.go` is package `main`'s and cannot be imported. The **REST source is shared**, though: it moved out of main into `addrindex.NewREST`, because the endpoints and their binary formats are *how this index is built*, and a second copy would have been free to drift from the parser that reads them.

**`list -dbsqlite ai.sqlite.db` reads the same index out of SQLite**, for the database `tools/tosqlite` writes — so a migrated index can be queried without keeping the bbolt original, and the two listings can be compared line for line. Only the storage differs: the touches are resolved and printed by exactly the same code, and `TestListFromSQLite` asserts the two outputs are identical rather than merely similar.

It works because the migration is lossless in the way that matters: `addrindex.shard` packs the 6-byte key (a 2-byte shard and a 4-byte block-range index, both big-endian) into one integer, which keeps a shard's ranges together and in order, and `data` is the packed run of touches copied verbatim. So a lookup is `where shard >= s<<32 and shard < (s+1)<<32 order by shard` — the same contiguous scan bbolt's cursor does, over the primary key — and each value is unpacked the same 10 bytes at a time.

Three things about it are deliberate. The **format constants are duplicated** in `sqlite.go` (shard width, remainder width, entry length, `rangeBlocks`) rather than exported from the `addrindex` package: the package's reader was left alone on purpose, so the two must be kept in step by hand — a change to the packing has to be made on both sides. **`-dbsqlite` only reads**, and `build`/`actbuild` refuse it rather than silently writing bbolt, since opening `-db` as well would create an empty index beside the one being read; with it set, the bbolt file is not opened at all. And a **missing file is an error**, checked before the driver sees it, because SQLite would otherwise create an empty database and report "no such table", which reads like a broken migration rather than a mistyped path.

Verified against the repo's own 65 GB migrated database, cross-checked against an independent Python decode of the same rows: 65 538 touches for `1A1zP1…DivfNa` across 832 shard rows, 5 578 for Binance's cold wallet (first at block 546 288, which is when that address was created) and 228 for `12c6DS…rzjrJX`, with identical first and last entries on both sides — 7 ms for the first lookup and 3 ms warm. The whole `list -dbsqlite` pipeline was then driven end to end against that database with a stub node standing in for the (unavailable) local Core, printing all 228 transactions and the summary.

`tools/addrindex/addrindex_test.go` drives the whole tool against one `httptest` server that speaks both halves — REST for the build, JSON-RPC for the listing — over hand-serialized blocks. That is what makes it a real test of the format rather than of the formatting: it builds a genuine index through `addrindex.Build` and reads it back through `Lookup`. Two traps it caught, both worth knowing before writing another fixture: **a zero input count is the segwit marker**, so even a fixture coinbase must carry one input or the parser misreads the whole transaction; and the REST client **reverses** the bytes of `/rest/blockhashbyheight`, so a fake hash has to encode its height at the end to come back at the front.

**`actbuild`** is a second pass over the chain: for every script it sees it asks the index how long that address's history is, and writes anything past `-active` (1000) to the **`addrindex-active`** bucket, keyed by address with the transaction count as its value.

**It reads Core's raw block files**, not its REST interface — `-blocks` points at the directory. One sequential pass over local data replaces a request per block, and it needs no undo data: `addrindex.OutputScripts` takes the outputs only, which is enough to see every address the chain has ever had, since an input can only spend an output that was paid earlier. That is what makes the file path viable at all — Core's `rev*.dat` undo data is in a compressed internal format, and skipping it removes the hardest parsing job.

Three things about the file format, all confirmed against a real 813 GB datadir rather than taken from documentation:

- **The files are XOR-obfuscated.** Since Core v28 the contents of `blk`/`rev` are XORed with the 8-byte key in `blocks/xor.dat`, repeating by absolute file offset. Without it every record reads as garbage — the first eight bytes of `blk00000.dat` looked like noise until the key was applied, at which point they read `f9beb4d9` (the mainnet magic) and `1d010000` (285 bytes, genesis). An absent `xor.dat` is an older node, which an all-zero key expresses.
- **Each record is magic + 4-byte length + block.** Core preallocates, so the written records are followed by zeros; anything that is not the magic ends the file.
- **Blocks are not in height order** and a stale block may sit beside the chain. Neither matters: this pass only needs to see every script, in any order. The cursor therefore counts **files**, under the name `actbuild-file` — deliberately not the old height-based `actbuild`, so a cursor written by the REST version cannot be read as a file number.

Verified by parsing real files: `blk00000.dat` yielded 119 981 blocks whose first hashes to `000000000019d668…`, the genesis block, and three recent files (`blk05720`–`05722`) parsed 248 modern blocks and 1 120 688 output scripts with no failures — segwit and taproot included. Read throughput off that volume measured ~37 MB/s, which puts a full pass over 813 GB at roughly six hours before any index lookups.

**The count comes from the blocks, not from the index.** `addrindex.Lookup` is not called at all: a lookup walks a shard's every range on disk, and there is one address to ask about per script on the chain, which is what made the scan impossibly slow. Instead every transaction's outputs are counted as the blocks go past, so the whole pass is one sequential read of local files and nothing else.

Note what the count then means. The blocks carry outputs, not the undo data a spend would need, so this counts the transactions that **paid to** an address rather than every transaction that touched it. Every address is still seen — an input can only spend an output paid earlier — but a busy spender with few receipts counts lower here than the index would report. It is also **per transaction, not per output**: a transaction paying one address twice counts once, which is why the scan walks `addrindex.OutputsByTx` rather than the flattened `OutputScripts`.

**The counter is a flat sorted run of 11-byte records** — the script's 8-byte index prefix and a 3-byte count — searched by binary search and incremented in place. Measured at 40 M entries it costs exactly **11.0 bytes an entry**, against ~30 for a `map[uint64]uint32`; over ~1.3–1.5 B addresses that is **14–17 GB** rather than 39–45. New prefixes land in a small map and are merged in when it fills, one pass rather than an insert each, and `-addrs` reserves the run's capacity so it never reallocates. The buffer is the one constant on top, capped at `bufferedAddrs` x ~40 bytes, 0.7 GB at 1<<24.

Three bytes hold 16 777 215 and a count that reaches it **saturates** rather than wrapping, which would turn the busiest address on the chain into a quiet one.

**A prefix cannot be turned back into an address** — it is a hash — so the script is kept at the moment a count first crosses the threshold, while it is in hand. Only those few are kept, and the addresses are encoded from them when the scan finishes. A second pass over 813 GB to recover them would have doubled the runtime.

**There is no cursor.** The counts live only in memory, so a partial scan would write partial counts and call them totals; every run reads every file.

Measured over 20 real block files: **194 858 blocks and 14.2 M outputs in 1 min 25 s**, giving 5.83 M distinct addresses and 299 past 1000 transactions, at 452 MB peak. The whole chain is I/O bound at the ~37 MB/s that volume reads, so roughly six hours.

The backfill reads Core's **REST** interface, not RPC:The backfill reads Core's **REST** interface, not RPC:The backfill reads Core's **REST** interface, not RPC: `/rest/block/<hash>.bin` and `/rest/spenttxouts/<hash>.bin` are binary and need no authentication. Measured on mainnet, block + spent outputs is **1.95 MB in 28 ms**, where `getblock` verbosity 3 for the same block is **13.7 MB** of JSON. This is what makes indexing the whole chain tractable at all — roughly 7 hours at the measured rate. It is enabled by `-core-rest` and runs unattended; until it has a cursor, `/info <address>` reports "unavailable (address index is still building)" rather than presenting an empty history as fact.

**Two measurement traps**, both of which produced confidently wrong numbers before being caught — worth knowing before re-measuring:
- **A small sample is meaningless for a sharded index.** Sharded values only reach their steady-state size once a whole range is in them. Measuring 25-block windows reported *exactly* 16.78 MB for every window regardless of touch count, because the cost was entirely per-key overhead against nearly-empty values.
- **Merging per block instead of per chunk measures a different design.** Calling `merge` once per block rewrites all ~65k shard keys every block: 30.89 bytes/touch and 113s for 900 blocks. The batched merge the backfill actually performs gave 18.15 bytes/touch and 26s over the same blocks.

`rangeBlocks` (1000) is the tuning lever, trading three things at once: the number of keys, how much a lookup must read, and how much memory a backfill chunk holds before flushing. It was not tuned beyond confirming the result lands inside budget.

### Balances: addrindex richbuild

`addrindex richbuild -dbsqlite rich.db -url http://127.0.0.1:8332` reads the whole chain and writes what every address holds now:

    create table rich (addr text primary key, balance integer not null)

The arithmetic is the whole job: an output pays its script, spending that output takes the same amount back out of it, and nothing else on the chain moves value. Summed from genesis to the tip, that *is* the UTXO set aggregated by address.

It reads the same two REST endpoints the address index is built from — `/rest/block/<hash>.bin` and `/rest/spenttxouts/<hash>.bin` — because the spent-outputs blob is the only place a spend's script **and amount** are written down; a block says which outpoint an input consumed, never what it was worth. So `addrindex.Balances(blk)` joins `Scripts`/`OutputScripts` in the shared package, and the two parsers there now keep each output's 8-byte value rather than skipping it (`addrindex.Payment` is a script and its satoshi, and `OutputsByTx` hands those back to `actbuild` unchanged). One parser for both jobs: a second copy of the block format, free to drift from the indexer's, is exactly what that package exists to prevent.

**SQLite cannot be the accumulator, and that is what shapes everything else.** Measured here against `modernc.org/sqlite` — the pure-Go driver, which is the repo's only option since it takes no cgo:

- the cheapest row it can write, an append to an unindexed rowid table with the journal off, costs **5.2 µs** (9.1 µs one row per statement, 5.2 at 500 rows per statement, no better above that — the cost is SQLite's own, not the driver's per-statement overhead);
- a realistic merge — 2 M sorted upserts into a 10 M-row `without rowid` table keyed by script, plus deleting the rows that reached zero — measured **24 µs a row** (13.4 s to stage the batch, 12.2 s to merge it, 20.3 s to delete).

The chain creates roughly three billion outputs and spends nearly as many, across something like 1.3 billion distinct scripts. At those rates, *touching each distinct script once* is two hours and a real accumulator, which touches most of them repeatedly, is days.

**So the movements go to disk, split by a hash of the script.** `shards.go` writes one record per movement — the script's length, the script, and the signed amount, all varints, about 31 bytes — into one of `-shards` (128) files, chosen by FNV-1a of the script. Every movement of a given script lands in the same file, so each file can then be added up on its own with only that file's scripts in memory. Nothing chain-sized is ever held: `-batch` (4 M) bounds the movements buffered before they are written out, `-shards` bounds what one summing pass holds, and a full mainnet run measured just over **1 GB resident** from end to end.

Four things about the pipeline are deliberate:

- **The buffer is an aggregator, not just a queue.** Movements are summed by script while buffered, and one that nets to **zero** — an address funded and emptied again before the buffer filled, which is most of what a change address ever does — is dropped rather than written. Adding nothing to a balance is nothing.
- **Blocks are fetched several at a time** (`-fetch`, 4). Each block is three REST requests against a node on the same machine, so a sequential scan mostly waits: measured on this repo's own node, four at a time took recent blocks from **71 to 116 a second, 120 to 197 MB/s**. Order still matters — a balance is a running total — so each height gets a one-slot channel and the results are read back in the order the heights were queued. A failed fetch is retried three times before the run gives up, since abandoning hours of scanning because the node was busy for a moment is the wrong trade.
- **The progress line measures bytes against the node's own `size_on_disk`**, not blocks. A 2011 block is a few hundred bytes and a 2026 one is over a megabyte, so a share of the block count promises the tip in minutes for most of a run that takes hours.
- **The shard files are working state, not a checkpoint.** An interrupted run throws them away and starts from the last stored height; that is why the directory is removed on the way out, whether the run succeeded or not.

**Three mainnet outputs are undone, because Core's UTXO set never held them** — all three confirmed against a live node rather than taken from documentation. The **genesis coinbase** is not in the set at all (`gettxout` on `4a5e1e4b…` returns null), and **BIP-30**: the coinbase transactions of blocks **91722** and **91812** were mined again byte for byte in 91880 and 91842, and the second copy overwrote the first, so 50 BTC of each pair belongs to nobody (the surviving copies are still unspent, 50 BTC each). All three are one rule — outputs that never entered the set — so `voided()` undoes all three the same way, and only when the node says it is on `main`: on regtest or testnet those heights are ordinary blocks.

**One address can be paid by more than one script**, which is why `rich` is built with a `group by addr` rather than copied row for row. An early miner paid by `<pubkey> OP_CHECKSIG` and later by an ordinary pay-to-pubkey-hash holds both under the same address, and on mainnet there are hundreds of thousands of them. This was not foreseen — a real run to block 200000 failed on `rich`'s primary key, which is what a real run is for. Note the related convention: this repo's `scriptAddress` gives a **P2PK** output the P2PKH address of its key, the way explorers do, where Core's own `gettxout` reports no address for one at all.

**A run resumes, and can extend an old database.** The SQLite file keeps two more tables beside `rich`: `balances` (script, addr, balance) is the state the rich table is built from, and `meta` holds two heights — `height`, where the balances stand, and `rich`, the height rich was last built at. A run that finds a stored height carries every balance back in as one movement and scans only what is new — so catching a week-old database up costs the summing and the rebuild, about 35 minutes at the chain's current size, rather than the two hours of reading. The two heights are separate because rich is *rebuilt* from balances rather than accumulated: a run interrupted between committing the state and rebuilding rich finishes the job next time instead of rescanning. The new state is written under a second name and swapped in with its height in one transaction, so a run that dies partway leaves the previous state exactly as it was — which is also why the database is opened WAL with `synchronous=NORMAL` rather than tosqlite's journal-off bulk-load settings: here a committed height has to survive the process.

Two smaller decisions: `balances` carries **no index at all** (nothing looks a row up in it — it is written once and read start to finish), and `SQLITE_TMPDIR` is pointed at the database's own directory before opening, because rebuilding rich sorts every stored balance by address and SQLite would otherwise put gigabytes of scratch in `/tmp`, which on this repo's own machine is memory-backed.

**Measured against this repo's own mainnet node, on the Pi it runs on.** The whole chain, blocks 0..965741, took **2 h 34 min**: 1 h 58 min reading it (1 188 906 848 movements into 33.9 GB of shards), 26 min 31 sec summing the 128 shards (59 547 088 funded scripts, 3 829 179 in the largest), and 8 min 58 sec writing **56 821 355 addresses** into rich, for an 11.1 GB database. Resident memory stayed just over 1 GB throughout, with the default 128 shards, 4 M buffer and 4 fetches at a time. Smaller runs for scale: blocks 0..200000 in about 90 seconds, and carrying those balances forward through 200001..250000 in 3 min 33 sec.

This run held 2 008 026 479 155 096 at 965741; take away the **5 115 832 822 sat** sitting in provably unspendable outputs (an `OP_RETURN` script, or one over 10 000 bytes: Core never puts those in its UTXO set, and this does count them, because a later run has to carry them forward), add the 23 blocks' subsidy of 7 187 500 000, take away the 43 sat those blocks burned to `OP_RETURN`, and the figure is Core's exactly. Neither of the last two was assumed: those blocks were checked to have claimed their full subsidy, and parsing their 270 723 outputs found precisely 43 sat burned.

Against the issuance schedule the balances come to 20 080 264.79 BTC where 965 742 blocks of subsidy less genesis and the two BIP-30 coinbases is 20 080 293.75 — a **28.96 BTC** gap, which is subsidy miners never claimed: coin that was never created rather than coin this misses. And the head of the list is what public trackers show, which is the cheapest sanity check there is: 34xp4vRoCGJym3xR7yCVPFHoCNxv4Twseo with 248 597.59 BTC, and the Mt. Gox address 1FeexV6bAHb8ybZjqQMjJrcCrHGW9sb6uF with 79 957.27.

`-min` (satoshi) keeps small balances out of `rich` — a rich list rather than every address on the chain — while `balances` keeps them regardless, or the next run would carry a wrong total forward. `-to` stops at a height instead of the tip, which is how the partial runs below were checked. `-tmp` puts the shard files somewhere other than beside the database.

### Abandoned coins: addrindex ababuild

`addrindex ababuild -dbsqlite abandoned.db -url http://127.0.0.1:8332` reads the whole chain and writes the addresses whose coins have gone longest without moving:

    create table abandoned (addr text primary key, balance integer not null, lastTx integer not null)

`lastTx` is the block time of the address's **last operation of either kind** — coins received, or coins spent from it, whichever is later. Both count because both are the coins moving: an address paid last year has not been silent for a decade, whoever sent the payment. The other reading — rank by last *spend*, on the grounds that only a signature proves somebody still holds the key — was built first and rejected, because it ranks the famous old addresses that collect tribute payments as the most abandoned on the chain, which is the opposite of what the list is for. `-top` (10000) is how many rows are kept and `-min` (satoshi) the balance an address needs to qualify; changing either rebuilds the table rather than reporting there is nothing to do, since the same state answers a different question.

**It is richbuild with one field added, deliberately.** The chain is read the same way over the same two REST endpoints, the movements go to the same sharded files, the shards are summed the same way and the state is swapped in the same way — see Balances: addrindex richbuild for why none of that can happen in SQLite, and for what `-shards`, `-batch`, `-sum` and `-fetch` each bound. What is added is a block time per movement, which `addrindex.BlockTime` reads out of the serialized header (the little-endian 4 bytes at offset 68) so that the block format is still parsed in exactly one place.

The first version of this carried **two** dates per movement — last spent and last paid — because the last-spend rule needed to tell them apart, and a zero satoshi output means the sign cannot: `addrindex.Movements` existed only to label each movement with its side. Under the rule that shipped neither is needed. The movements come from `addrindex.Balances`, the same call richbuild makes, and each shard record carries one timestamp instead of two — about five bytes a record, which over a chain-sized run is gigabytes of shard file.

Four decisions the result rests on:

- **The date is a max, not the last one seen.** Block timestamps are not strictly ordered — a miner's clock may legitimately run up to two hours behind the block before it — so reading the date off the latest block a script appears in would sometimes report an earlier time than a block before it did.
- **Nothing is dropped for netting to zero**, which is where `spill` parts company with richbuild's `flush`. Dropping would be very nearly safe: a script never paid again holds nothing and is left out of the answer anyway, and one that is paid again is paid in a later block. The exception is that same timestamp skew, which makes "a later block" and "a later time" different things — and which movements share a buffer is an accident of `-batch`, where the answer should not be. The cost of keeping them is a fuller shard file.
- **`balances` is the state and `abandoned` the answer selected from it**, the two-table shape richbuild uses and for the same reason: one address can be paid by more than one script, those scripts hash into different shards, and no shard can rank an address it holds only part of. So every funded script is written down first and the ranking is one `group by addr` over the lot — summing the coins, taking `max(last)`. A script with no address at all is kept in the state and left out of the answer, since it still holds coins the next run has to carry forward.
- **A resumed run is exact**, which the last-spend rule could not manage. Only funded scripts are stored, so a script holding nothing at the stored height is not carried forward — and under this rule that cannot matter: the only way such a script reaches the answer table is by being paid again, and that payment is later than any date the dropped row knew.

**Verified against this repo's own mainnet node, two ways.** Blocks 0..92000 were built in resumable stages, carrying 9 462 balances forward, then 32 035, 45 080 and 57 170 — so the resume path is exercised against real data rather than only by `TestAbaBuildCarriesStateForward`, and one of those stages did in fact resume after the link to the node dropped mid-scan. From block 60000 on there are more than ten thousand qualifying addresses, so `abandoned` holds exactly `-top` rows.

- **The total reconciles with the issuance schedule to the satoshi.** 92 001 blocks of 50 BTC is 4 600 050; take away the genesis coinbase and the two BIP-30 coinbases, none of which Core's UTXO set ever held, and it is **4 599 900.00000000 BTC** — which is what the state holds across its 58 902 funded scripts, with a difference of **0 sat**. That is the whole `voided()` path checked on all three of its cases at once, since 91722 and 91812 and their duplicates at 91842 and 91880 are all inside the range.
- **A second implementation agrees address for address.** A Python script that shares nothing with this one — prevouts from a UTXO set it tracks itself rather than from Core's `spenttxouts` undo data, txids by double-SHA256, its own base58/bech32 — reproduced the whole run: all **58 898 addresses**, on balance and on `lastTx`, with nothing on either side alone, and `abandoned` holding precisely its first ten thousand by `(lastTx, addr)`. Running it over 0..10000 as well is worth knowing about: that range is almost entirely coinbases, so it agreed on all 9 461 addresses while barely touching the spending side. The 92000 comparison is the one that covers it.

The head of the list is the cheapest sanity check there is, and it reads correctly: `12c6DSiU4Rq3P4ZxziKxzrL5LmMBrzjrJX`, the block 1 coinbase, 50 BTC that has not moved since 9 January 2009.

**The whole chain has not been run.** Every measurement above is from a laptop on the same LAN as the node, and that link — not the node — is the ceiling: 1.1-1.6 MB/s for one fetch at a time, 1.9 at sixteen, and still only 2.6-3.1 MB/s re-fetching a block the Pi already has in page cache, with the round trip swinging between 5 and 87 ms. At that rate 874 GB is upwards of eighty hours, against the 2 h 34 min richbuild took reading the same data over loopback on the Pi itself, and a run commits nothing until it finishes. So a full pass belongs on the Pi against `127.0.0.1:8332`; over a network, run it in stages, since each one commits a height the next can carry forward.

### The /info lookup

`info()` in `info.go` classifies its (non-empty) argument into exactly one of three kinds, checked **in this order**, and dispatches to the matching per-kind function — `transaction()`, `block()`, or `address()` (one-word names, same convention as `info`/`watch`): the 64-hex-character shape (`isTxid`), then block height (parses as a non-negative base-10 integer via `strconv.ParseInt`), then address (the catch-all). The order matters and is not arbitrary: a 64-character string of all decimal digits (e.g. all zeros) satisfies *both* the txid shape and `ParseInt`, since decimal digits are a subset of hex digits — checking the hex shape first is what disambiguates it correctly. This was a real bug caught by manual testing against a live regtest node, not a hypothetical; don't reorder these checks without re-verifying against a real node.

**A block hash has exactly the same shape as a txid** — 64 hex characters — so `isTxid` matching does *not* settle which one it is, and nothing local can: only the node knows. So the 64-hex branch first asks `getBlockHeader(arg)`, an O(1) index lookup that errors for a hash the node has no block for; on success `/info` dispatches to `block(header.Height)`, on failure to `transaction(arg)`. Going through the **height** rather than formatting the block from its hash is deliberate: it reuses the block cache and guarantees `/info <hash>` returns byte-for-byte what `/info <height>` returns. The cost is one cheap failed lookup on every `/info <txid>`. Verified against the real mainnet node: `/info 00000000000000000000524afad3a4cc1e4e190e1272de721de6cdb4e889f6aa` resolved to height 958835, produced a reply identical to `/info 958835` (which then came straight from the cache), and a txid from that same block still reached the transaction path. `TestInfoFlow` pins the equality; note its fake btcd **must error on an unknown hash** the way a real node does — an earlier leftover fixture returned a header for *any* hash, which made every txid look like a block.

Each per-kind function calls Core directly and replies with a multi-line message: `transaction` via `getRawTransaction` reports Status (confirmed + confirmation count, or unconfirmed/mempool), the confirmation time (`Confirmed:` = the block time via `when` — note the node keeps no broadcast time for a confirmed tx, so the *delay* it took to confirm isn't computable; only the confirmation timestamp is), Block, Amount (summed `Vout[].Value` in whole satoshi, `math.Round(total*1e8)`, space-grouped), Fee, Size, and compact Input/Output address lists. The fee and the input addresses both need each input's prevout, and where those come from depends on whether the transaction is confirmed: Core supplies them **inline** at `getrawtransaction` verbosity 2 for a confirmed transaction, so `txInputs` makes no extra calls at all, while a mempool transaction has no undo data and falls back to `fetchInputs`, which fetches each input's previous transaction concurrently (bounded `sem` of 16 + `WaitGroup`). Either way it returns `(fee, addrs, spent, ok)` — `addrs` in input order for this listing, `spent` summed per address for the watch notifier's outgoing detection (see Watch notifications). A coinbase tx shows `Fee: none (coinbase)` / `Inputs: coinbase (newly generated)`, and any prevout-fetch failure degrades Fee/Inputs to `unavailable`. `compactAddrs` shows at most the first three addresses (each `short`-ened) with a trailing `...` when there are more; an output with no address (OP_RETURN, SegWit commitment) renders `(non-standard)`. An unconfirmed tx omits the Confirmed/Block fields. `block` is **served from the cache** — `block()` calls `loadBlock(height)` and, on a hit, replies with `formatBlock(bi)` without touching btcd; on a miss it computes the record live (`computeBlockInfo`), stores it, and replies. See Block info cache below for the record's fields and how it's populated (backfill goroutine + block notifications). `blockFeeStats()` (used by `computeBlockInfo`) reads each non-coinbase transaction's own `fee`, which Core reports in `getblock` verbosity 2, for the Lowest/Average/Highest — no prevout fetching, unlike the btcd path that had to derive every fee itself; btcd's getblock omits input values, so it gathers the referenced prevout txids and fetches those transactions **concurrently** (a `sync.WaitGroup` over a bounded `sem` channel of 16, results collected under a mutex). A coinbase-only block shows `Fees: none (coinbase only)` (fee distribution effectively requires `--txindex`, same graceful-degradation spirit as the address index — but reward and reward+fees come from the coinbase alone, so they show regardless). And `address` via `validateAddress` (type derived from `IsWitness`/`IsScript`) plus **on-chain history stats** from the bot's own `addrindex` (Core has no address index — see Address indexing). `addressHistory` looks the address's scriptPubKey up in the index, which returns `(height, txIndex)` touches rather than txids — that is what lets it store 10 bytes per touch — then resolves them: each distinct height's txid list via `getBlockTxids`, then each transaction at verbosity 2, both stages concurrent and bounded. `addressStats` then sums, over those transactions: **Balance** (received − sent), **Total received**, **Total sent**, **Total flow**, **Total fees** (read straight off each transaction's own `fee`, since Core computes it), plus the **Transactions** count and the **First/Last tx** times. Amounts render via `compactBTC`, the **Activity period** via `periodText`, and **First/Last tx** via `day` — `when` without the clock time, since the hour an address was first used says nothing about it. Both share `relative`, so a recent date still reads "2 days ago" either way; only the absolute branch differs, and blocks and transactions keep their `when` with the time. Hitting `addrTxLimit` (10000) yields partial stats, flagged by a trailing `+` on the transaction count, exactly as the btcd path flagged its own cap. Until the index has been built at all, the reply says `Activity: unavailable (address index is still building)` rather than presenting an empty history as fact. All three messages put a blank line after their header line (`Transaction 32e43e...870b16` / `Block #100` / `Address 1A1zP1...DivfNa`) and space-pad the field labels so values start in one column per message (the pad width is per-message, computed from its longest label — `Confirmed:` for a confirmed transaction, `Reward + fees:` for a cached block, `Activity period:` for addresses). The field block — but not the header — is wrapped in `<pre>...</pre>` so Telegram renders it monospace and the alignment actually holds. To make that work, `bot.send` in `telegram.go` always sets `parse_mode: "HTML"` on every outgoing message, which imposes an escaping obligation: any user-derived text echoed into a reply must go through `html.EscapeString` (Telegram rejects messages with an unescaped `<` that isn't a supported tag). The two echo sites — `watchCmd()`'s confirmation and the invalid-address message — do this; txids skip it because `isTxid` guarantees pure hex, and a validated address is base58/bech32, also HTML-safe. Confirmed-transaction and block times are both rendered by `when(unix)`: relative ("2 days ago", pluralized by `ago`) when within the last 3 months, lowercase absolute ("14 november 2023 22:13", `strings.ToLower` over Go's "2 January 2006 15:04" layout) when older. Txids, block hashes, and addresses are printed shortened by `short(s)` ("32e43e...870b16": first 6 + "..." + last 6, applied only when the string is longer than 15 characters) — except the "doesn't look like a valid Bitcoin address" echo, which keeps the full input because the address branch is the catch-all and that text isn't known to be an address at all. ### Watch notifications

There are **two kinds** of watch with **different delivery models**. An **address** watch (`/watch <address>`) is persisted and, whenever a transaction *pays* the address **or spends from it**, sends a mempool notification (via btcd's `relevanttxaccepted`) **and then a second "confirmed" notification** — with how long it took — once that transaction is mined. Both directions are covered: an incoming payment reports the `Amount`, and an outgoing one reports what left (`Sent`), what returned as change (`Change back`) and the resulting `Net` move, so the message answers "how did this address change" either way (see Detecting spends below). A **transaction** watch (`/watch <txid>`) is a one-shot: it fires once, when that transaction *confirms* (is mined into a block). Both "confirmed" notifications run through the same `blockconnected` → `processConfirms` path (see Transaction watches below); the mempool notification is the address-watch fan-out only.

The **address**-watch delivery model is **one goroutine per watch** fed by a broadcast channel fan-out (there is deliberately no address→chats map — an earlier version used `watchersByAddr` and was replaced by this at explicit request):
- **Watchers**: each address watch becomes an entry in the package-level `notifies map[notifyKey]notifyChans` (keyed by `notifyKey{chat, typ, id}`, guarded by `notifyMu`), where `notifyChans{ch, stop}` holds a `chan notification` and a stop channel. `startNotifyChat` inserts the entry and launches a goroutine that `select`s on `ch` and `stop`, messaging its chat only for notifications matching its own address — on **either** side, `notification.received[addr]` or `notification.sent[addr]`, whichever is present (both are, for a spend that returns change). `ch` is **never closed** (so a broadcast can always send without panicking); a watcher is terminated by closing `stop`. `stopNotifyChat(chat, typ, id)` closes+drops one entry (chatID-scoped like the store's `Remove`); `stopNotify` (from `shutdown` and test setup) closes them all and also `txwatches.Reset()`s the confirmation map. Only address watches live here now — transaction-confirmation watches moved to the `txwatches` package — so `notifyKey.typ` is effectively always `watchTypeAddress`.
- **Subscription** (address watches only): `watchCmd()` calls `startNotifyChat` and then `seedOutpoints([addr])`. Under btcd this step also loaded the address into btcd's connection-wide filter; **Core has no such filter**, so there is nothing node-side to load — `seedOutpoints` registers the address's scriptPubKey and current UTXOs with the bot's own matcher instead (see Detecting spends below). On startup `startNotify(bot)` re-creates a watcher per `watches.List()` record and seeds them all, so watches survive restarts. If the node isn't configured the watch is still stored/started — it just won't fire until a restart with a node.
- **Broadcast**: a `rawtx` ZMQ frame reaches `onRawTx`, which parses it locally and drops it unless it touches a watched script or outpoint — almost every mempool transaction is dropped here, without any I/O. Only on a match does it spawn `go broadcast(txHex)`. `broadcast` calls `decodeRawTransaction`, builds one `notification{txid, received: addr→summed Vout value, sent: addr→summed input prevout value}`, and non-blocking-sends it to *every* watcher's channel; each watcher then filters. `received` comes straight off the decoded outputs; `sent` cannot, because a decoded transaction's inputs are bare txid:vout refs carrying no addresses — it comes from `txInputs`. It also calls `recordOutpoints` so the outputs this transaction creates for watched addresses are recognised when later spent. Before fanning out it **enriches** the notification (best-effort): the fee and `vsize` come from **`getmempoolentry`**, not from the transaction — this is a mempool transaction, so it has no undo data and Core reports neither fee nor prevout for it at verbosity 2 — and `confEstimate` buckets the resulting sat/vB rate against `estimatesmartfee`'s 2- and 6-block targets into `~10-20 min` / `~1h` / `2h+`. The **address** notification shows Fee / Fee rate / Confirms below Tx / Amount; any fetch failure just leaves them off. Right after sending it, the watcher calls `txwatches.AddAddrConfirm(...)` to register a one-shot confirmation watch, so the same transaction being mined later produces the follow-up "confirmed" message. A `hashblock` frame spawns `go processBlock(hash)` and `go processConfirms(bot, hash)`. The channel sends are non-blocking (`select`/`default`) so one slow or already-stopped watcher can't stall the fan-out.

**Deduplicating sightings.** Core publishes a transaction on `rawtx` **twice** — once when it enters the mempool and again when it is mined — so a watched payment used to produce three messages: the mempool notification, the confirmation, and then a second "New transaction" from the mined republish (recognisable because it lacked the Fee/Fee rate/Confirms lines, the transaction having left the mempool by then). Verified against a real node: sighting #1 reports `confirmations=0` and is in the mempool, sighting #2 reports `confirmations=1` and is not, and both `rawtx` frames arrive *before* `hashblock`.

`broadcast` therefore keeps a `notified` map of txids (48h TTL, swept on insert) and returns early on a repeat. Deduplicating on the **txid** rather than simply skipping confirmed transactions is deliberate: a transaction whose first sighting is already mined — a coinbase paying a watched address, or anything that arrived while the bot was down — has no earlier notification to duplicate and must still fire. It also collapses rebroadcasts. Only transactions that already matched a watch reach this map, so it stays small. `stopNotify` clears it, as tests depend on that isolation.

**Detecting spends (why outpoints are seeded).** A spend names only the outpoint it consumes — never the address — so recognising one means already knowing which outpoints a watched address owns. This was true under btcd too, but the mechanics have inverted. btcd kept the outpoint set inside its *own* filter, learning an address's outpoints only by watching payments arrive while the filter was loaded; the bot had to replay an address's whole history (`addressTxs`, oldest-first) to derive the set and push it in with `loadTxFilter`. Core has no filter, so **the set lives in the bot** (`watchedOutpoints` in `zmq.go`) — and Core answers the question directly.

`seedOutpoints(addrs)` calls `validateaddress` for each address (registering its scriptPubKey for output matching) and then one **`scantxoutset`** covering every address at once, seeding an outpoint per returned UTXO. That is both a smaller job than the old history replay and an exact one: the old approach's caveat — that a capped history loses the *newest* transactions, which is exactly where live UTXOs are — is simply gone. It is called from `watchCmd` and `startNotify`, and runs in a **background goroutine** because the scan walks the whole UTXO set and takes minutes on mainnet. There is no longer a reconnect path to re-seed from: HTTP is stateless and the ZMQ subscriber resubscribes itself.

**Transaction watches / confirmations** (`txwatches` package + `processConfirms` in `notify.go`): confirmations for **both** watch kinds are served from the `txwatches` package's in-memory map (keyed by txid; **not** persisted, so pending confirmations are forgotten on restart — accepted by design). `/watch <txid>` calls `txwatches.Add(txid, chat, alias)` (a **direct** entry, `addr==""`); a watched address's incoming tx calls `txwatches.AddAddrConfirm(txid, chat, addr, alias)` from the watcher goroutine (an **address-derived** entry; see Broadcast above). Neither is added to btcd's `loadtxfilter` — that filter matches addresses/outpoints and `relevanttxaccepted` is mempool-acceptance only, so there is no first-class per-txid confirmation trigger. Instead confirmation is detected off the `blockconnected` notification the bot already receives for the block cache: `processConfirms(bot, hash)` (in `notify.go`) early-returns unless `txwatches.Any()`, otherwise fetches the new block's txids via the cheap `getBlockTxids` (getblock verbosity 1) and hands them to `txwatches.Confirms(txids)`, which removes and returns every matching watch as a `Confirmed{Txid, ChatID, Alias, Addr, WatchedAt}`; `processConfirms` then formats+sends each. The message depends on `Addr`: a direct watch gets `🔔 Watched transaction <short> (alias) was confirmed in block #N after <elapsed>`; an address-derived one gets `🔔 Transaction <short(txid)> on watched address <short(addr)> (alias) was confirmed in block #N after <elapsed>`; both carry buttons for the txid, the address and the **block height**, so the block it landed in is one tap from an `/info`, where `elapsed = durationText(now − WatchedAt)` (a `format.go` helper; "12 min" / "2 h 5 min"), which for the address kind is the time from first mempool sighting to confirmation. Registration dedups on (txid, chat, addr) so a re-broadcast can't queue two messages; `txwatches.For`/`txwatches.Remove` (backing `/watches` and `/unwatch <txid>`) act on **direct** entries only, and unwatching an **address** also calls `txwatches.RemoveAddrConfirms` so no confirmation arrives after the user stopped watching. This reuses the very block push the cache already consumes — no new subscription, and it works for any txid without encoding it into a filter. (The old `/watch <txid>` "was accepted to the mempool" message is gone; it was effectively dead, since a txid was never in the filter and so `relevanttxaccepted` only matched a watched txid by coincidence.)

`/unwatch <arg>` reverses a watch. For a **txid** (`isTxid(arg)`) it just drops the in-memory watch via `txwatches.Remove(arg, chatID)` (chat-scoped) — no store, no filter. For an **address** it is `watches.Remove(chatID, arg)` to delete the persisted record(s), then `stopNotifyChat` to terminate the watcher goroutine, then `txwatches.RemoveAddrConfirms(arg, chatID)` to drop any pending confirmation watches for that address, then `unwatchScripts(arg)` to drop the address's scriptPubKey and outpoints from the local matcher. That last step is an optimization — the real guarantee that notifications stop is that the watcher goroutine is gone. (Under btcd this rebuilt the node-side filter with `loadTxFilter`; there is no node-side filter now.) If nothing matched (`watches.Remove` returned 0, or `txwatches.Remove` returned 0) the user is told they weren't watching it.

**Verification status after the Core migration.** The btcd-era end-to-end runs (a real signed regtest payment driving `/watch` → notification → fan-out to two chats; both confirmation paths against mainnet; the outgoing/spend path against a real mempool transaction) all exercised btcd's push model and **do not carry over** — the transport, the filter and the fee source have all changed. What has been verified under Core: the client and every read command against the live mainnet node (`/fees`, `/mempool`, `/info` by height and by block hash, block-cache backfill), ZMQ delivery from a node publishing each topic on its own port, and `parseTx` against the live mainnet mempool firehose (40 transactions, 8 cross-checked field-by-field against the node's own decoding, zero failures). **The whole path has now been driven end-to-end against a real Core node**: watching a fresh regtest address, paying it and mining the block produced exactly the two intended messages (mempool notification, then confirmation in block #104 after 5 sec). It is also covered by the suite (`TestWatchNotification`, `TestSpendNotification`, `TestSpendWithChangeNotification`, `TestSeedOutpoints`, `TestTxConfirmation`, `TestAddrConfirmation`, `TestBroadcastDedups`, `TestConfirmationLinksBlock`).

In the suite the notification tests no longer wait for a server push — there isn't one. They call `broadcast(txHex)` or `processConfirms(bot, hash)` directly, which is exactly what `zmq.go` does with a frame, against `newFakeCoreServer` (plain HTTP; the websocket fake is gone). Note the shared `awaitNotification` helper registers its teardown with `t.Cleanup`, not `defer`: a deferred `stopNotify` would run before the caller's assertions and `txwatches.Reset()` away the confirmation watch under test. Keep the suite green under `go test -race` — the notification paths are the codebase's only concurrent ones (the broadcast/per-watch goroutines, the ZMQ receive loop, and `processConfirms` reading the `txwatches` map under its mutex).

### The watches store

The bbolt connection is a plain package-level `var db *bbolt.DB` (in `db.go`), opened once in `main()` via `openDB(-db path)` and closed during graceful shutdown (`closeDB`, see Runtime model). `openDB` opens the one file, creates the `blocks` bucket, and hands the same handle to `rates.Init(db)`/`watches.Init(db)`/`miners.Init(db)` so those packages share it — one file, one handle, seven buckets. **Every bucket-owning package must be Init'd in `openDB`, and forgetting one fails silently**: those packages guard their operations on a nil handle, so the package quietly does nothing rather than erroring. The address index shipped that way once — it fetched and parsed the chain over REST while storing none of it, logging progress the whole time — so `addrindex.merge` now returns an error on a nil handle instead of no-oping, and `TestOpenDBBuckets` pins the full set of seven. Address-watch storage lives in the `watches` package (`Add`/`List`/`Remove`); there is no `watchStore` struct, and the internal `watchRecord` isn't exposed — `List` returns a minimal public `Watch{ChatID, Address, Alias}`.

`/watch <target> [alias]` records the watch — an **address** watch via `watches.Add(chatID, address, alias)` (see The watches key below), a **transaction** watch via `txwatches.Add` into the in-memory map instead (not persisted; see Watch notifications). `watchCmd()` in `main.go` splits `arg` on the first space into the **target** (first token) and an optional **alias** (the remainder, trimmed) — a bare `/watch` prompts for both together in one follow-up message — then classifies the target via `isTxid` (exactly 64 hex characters → transaction, anything else → address) — a heuristic, not real validation, good enough to route the watch. The alias is echoed in the confirmation, appended in parens to the notification header (`…watched address bc1q…dayd2g (John)`), and shown in `/watches`; it's `html.EscapeString`'d at every display site since it's arbitrary user text. `watches.List()` (used by `startNotify`, `/watches`) returns every stored watch; `watches.Remove(chatID, address)` deletes that chat's watch on that address and reports whether there was one — the `chatID` half is the security scoping that stops one chat from removing another chat's watch, and the count lets `/unwatch` distinguish "removed" from "you weren't watching that".

**The watches key.** A record is keyed `"<chat>,<address>"` as text — `260439275,bc1q5rasj5fedy3f9vgh9x84jqlgtvj964k0xn5z6r` — and the value holds only what is left of it, `{"created":…,"alias":…}`. It used to be an auto-incrementing `NextSequence` key with the chat and address *inside* the value, which meant every read decoded every record to find out whose it was, and nothing stopped a chat holding the same address twice.

Three things follow from the key being the pair:

- **`Count(chat)` is a prefix scan** over that chat's own keys rather than a walk of the bucket decoding each record, and `Remove`/`SetAlias` are a single lookup rather than a collect-then-delete pass. The comma is part of the prefix, which is what keeps chat `26` out of chat `260`'s count.
- **`Add` is idempotent.** Watching an address twice replaces the record instead of adding a second one, and **keeps the original `created`** — it is the same watch, and resetting its age would be a lie. Nothing reads `created` today; it is stored because it is the one fact about a watch that is otherwise unrecoverable.
- **`List` sorts by `created`**, since the keys now sort by chat and then address. Stably, because `created` is a whole second and several watches can share one. The time is carried alongside the watch in the sort, not in a parallel slice — sorting one of two parallel slices silently desynchronises them, which is a bug this had and a test caught.

`tools/tosqlite` reads **both** shapes, taking the chat and address from the key when it parses and from the value when it does not, because it is pointed at backups as often as at a live file.

**`Init` no longer carries the old key form across.** It did for one version — the migration ran on a real start (four old records, one of them a deliberate duplicate, became three under the new key) and there is nothing left to move, so it and its tests are gone. A record still under a numeric key is simply not served: `List` skips a key that does not parse rather than failing on it. `tosqlite` is the way to read one.

**A chat is capped at `maxSubscriptionsPerChat` (500)**, counted across both kinds together (`watches.Count(chat)` plus `len(txwatches.For(chat))`). `watchCmd` checks the count before storing and refuses past the limit with a message telling the user to unwatch something first, logging the rejection at INFO. The cap exists because each address watch costs a live goroutine and a channel in the notification fan-out, and every one of them is woken for every matching transaction — an unbounded chat could quietly make the fan-out the most expensive thing the bot does.

### The cursors bucket

Every scan over the chain resumes where it stopped, so its place is the only thing between a restart and starting over — for the address index, a rebuild measured in hours. Each used to keep that place in a bucket of its own (`blocks-cursor`, `miners-cursor`, `addrindex-cursor`), and each of those held exactly one key, called `cursor`. Those buckets are gone.

Every one of those places is the same thing in the same form — a block height, or a file number, as decimal text — so `cursors/` is one bucket keyed by the scan's own name: `blocks` (the block-info backfill), `miners` (the per-pool statistics collector), `addrindex` (the index build) and `actbuild-file` (tools/addrindex's pass over Core's raw block files, which counts files rather than heights).

- **The names are constants, not string literals at the call sites.** A name that does not match is not an error — it is a scan that silently starts from the beginning, which for the address index is hours of work.
- **`Set` takes the caller's transaction**, which is the whole point of its signature: a scan advances its place in the same commit as the batch that reached it, so a crash between the two cannot skip work or repeat it. `TestSetIsPartOfTheCallersTransaction` pins that a rolled-back batch leaves the cursor where it was.
- **Not found is not zero.** A scan that has never run picks its own starting point — genesis for the block cache, height 1 for the miner statistics — which is not where a scan that stopped at height 0 resumes, so `Get` reports the two separately.
- **`Init` only creates the bucket.** It is called from `blockInit`, `miners.Init` and `addrindex.Init`, so it runs several times a start and has to be safe to repeat. That `addrindex.Init` is one of them matters — it is the *only* setup `tools/addrindex` performs, so it is what gives the tool the bucket at all.

Two versions did the moving, and both are gone from the code: #178 carried the old values across, #180 dropped the three empty buckets they had lived in. **They are the upgrade path**, so a database older than #178 has to pass through it — going straight to a later version leaves every scan without a place and starts it over, which for the address index is hours of work.



### Database backups

`-backup <path>` turns on periodic backups: `main()` calls `startBackup(path, interval, script)` right after `openDB`, which runs a goroutine keeping the copy at `path` no older than `-backup-interval` (default 24h) and running `-backup-script` (default empty = nothing runs) after each copy. It lives in `db.go`.

- **The copy** is `tx.CopyFile` inside a `db.View` read transaction, so it is a consistent snapshot of every bucket taken *without stopping the bot* — bbolt allows one writer alongside many readers, so nothing blocks while it copies.
- **It lands on `<path>.tmp` and is renamed into place.** `CopyFile` writes its destination directly, so a failure partway (a full disk) would otherwise leave a truncated file exactly where the last good backup was. On any error the temp file is removed and the previous backup is left untouched (`TestBackupKeepsPreviousOnFailure` blocks the temp path with a directory to force this).
- **There is one decision, asked repeatedly**: the destination is missing, or its mtime is at least `-backup-interval` old. It is asked at startup and then at least every `backupCheck` (1h, a package var for tests), so the file's own mtime is the whole state — no ticker phase, nothing to persist, and a restart neither repeats a fresh backup nor delays a due one.
- **Hourly rather than once per interval**, because of the deployment setup: `scripts/update.sh` checks for new commits every 5 minutes and restarts the service on each one, and a ticker's phase restarts with the process. A daily ticker left a backup that was merely *not yet* due at the restart waiting a further full interval — up to two days old before being retaken. Checking hourly bounds that at interval + 1h. `TestStartBackupRetakesWhenStale` pins it with a file that starts at 80% of the interval, which is exactly the case the old ticker got wrong.
- **The wait is the smaller of that hour and the time the copy has left**, so a backup is taken *when* it comes due rather than at the next tick. This is not the same as a ticker of the check rate, and the difference was measured on the real binary: with `-backup-interval 10s` checked every 10s, each check landed a few milliseconds *before* the file turned due (the wait starts before the copy that resets the mtime), every other check found nothing to do, and backups came every 20s. Sleeping to the deadline has no phase to drift. The cap at `backupCheck` is what still notices a backup replaced or deleted underneath the bot.
- **The check rate is `min(backupCheck, interval)`**, so a `-backup-interval` shorter than an hour still runs at its own rate rather than being held back to one, and `startBackup` returns that rate for the startup status line — the operator is told what will actually happen rather than a fixed hour a short interval overrides.
- **`startBackup` also returns a stop, and `shutdown` runs it before `closeDB`** — the same dependency order the webhook server is drained in, since a copy in flight is reading the database. The tests need it for a second reason: a loop nothing can stop outlives the test that started it, and the next test to reopen the shared handle races it under `-race`, which is how this was found.
- **The script** runs via `sh -c`, so `-backup-script` can be either a plain path to an executable script or an inline command. The backup's path reaches it both ways — as `$1` and as `$BACKUP_FILE` in the environment — so `/opt/bitnsbot/upload.sh` and `rclone copy "$1" remote:` both work. Its combined output is logged (INFO on success, ERR on failure); a failing script is never fatal. It is bounded by `backupScriptTimeout` (30 min, a package var for tests) because a script that hangs would wedge the goroutine and silently stop every later backup — and making that bound actually hold takes more than a context deadline. The script gets its **own process group** (`SysProcAttr.Setpgid`) and a `cmd.Cancel` that kills the **group**, plus `cmd.WaitDelay` as a backstop. Killing only the shell is not enough: anything it leaves running — a backgrounded upload, a child outliving it — inherits the output pipe, and `CombinedOutput` blocks until every writer to that pipe is gone, so the timeout would expire while the goroutine stayed stuck for as long as the child ran. That is not hypothetical; it is what made `TestBackupScriptTimeout` hang in CI (a `sleep` surviving the shell), and the test now pins both halves — that `backup` returns at the timeout, *and* that the backgrounded child is dead afterwards (with `WaitDelay` alone the first passes and the second fails). Note `Setpgid` is unix-only, which is fine for a bot that targets Linux and macOS.
- Successful backups log at **status** level (verbosity 0) with the path, size and duration, so an operator can confirm backups are happening without raising verbosity.

`backup_test.go` covers all of it against a real bbolt file, reopening each backup independently to prove it is a valid database holding the seeded watch (not merely a file of the right size). Verified for real by running the built binary with `-backup-interval 2s` and a logging script: the startup copy plus one per tick, the script invoked each time with the right path, and the resulting snapshot — taken while the rates backfill was actively writing — passed bbolt's own `tx.Check()` with all seven buckets intact (5815 rate records, 218 miner addresses, 201 tags). The scheduling was re-verified the same way after the hourly change, against a backup file pre-aged to 9s of a 10s interval: nothing at startup, the copy exactly when it came due one second later, then a steady 10s cadence (11:56:53, :57:03, :57:13, :57:23), and a SIGTERM stopping the goroutine before the database closed.

### Block info cache

`/info <height>` is served from a cache (the `blocks` bucket) so building a block's record happens in the background, not in the user's request. (Under btcd the expensive part was computing every transaction's fee from its prevouts; Core reports fees itself, so what remains is one `getblock` at verbosity 2 — still worth caching for a full mainnet block, but no longer a fan-out.) `blocks.go` holds one JSON `blockInfo` per height (big-endian key via `itob`, reusing the rates/watches idiom): height, hash, time, size, tx count, miner, `FeesOK` + fee min/avg/max (BTC), tx-size min/avg/max (bytes), reward, and total (reward + fees = the coinbase output). `computeBlockInfo(hash)` builds a record from one `getBlockVerbose` (verbosity 2 → all txs with sizes, vins, vouts) with every transaction's fee already included, so no prevout fetching happens at all; reward comes from `subsidy(height)` (50 BTC, halving every 210000 blocks) and total from summing the coinbase outputs, so reward/total never need prevouts — only the fee distribution does. Amounts render in satoshi via `sats()`/`group()` (`group(int64)` is the shared space-thousands helper `sats` now routes through), sizes via `group`. Confirmations and the old header-only path are gone; `formatBlock` builds the aligned `<pre>` block from label/value pairs.

**The bucket used to be called `blocks-stat`.** `blockInit` carried a database written under that name across for one version — a record at a time, 10000 per transaction, since bbolt only reuses the pages the old bucket frees once the transaction that freed them has closed, and one transaction over a chain-sized cache would have left a spare copy of the whole thing in the file (measured: 965 003 real records moved in 1.622 s with the file size unchanged, against a single transaction growing a 200 000-record file 166 → 315 MB). That has run, so it and its test are gone. `tools/tosqlite` still reads either name, since it is pointed at backups as often as at a live file — nothing else does, so a database that never passed through that version reads as an empty cache the collector refills.

Three things populate the cache, all funneling through `computeBlockInfo` + `storeBlock`:
- **On-demand**: a `/info` cache miss computes and stores the block (so an old, uncached block is slow once, then instant).
- **New blocks**: a `hashblock` ZMQ frame becomes `go processBlock(newTipHash)` (see The ZMQ notification path). Under btcd this needed a `notifyBlocks` subscription on the connection; Core publishes unconditionally, so there is nothing to subscribe to and nothing to re-establish after a restart.
- **The collector**: `startBlockCache()` (launched from `main()`) runs `collectBlocks()` immediately and then every `blockCacheInterval` (10 min, a var). This is **cursor-driven, not a fixed-depth backfill** — the earlier version walked back a `blockBackfillDepth` of 50 blocks from the tip and stopped. `cursors`/`blocks` holds the last processed height; a run resumes at the next height, and with **no cursor at all it starts from genesis**, so a fresh install fills in the whole chain over successive ticks rather than only recent history. `flushBlocks` writes a batch and advances the cursor in one transaction, so an interrupted catch-up resumes from the last flushed batch. `storeBlock`/`loadBlock` are nil-`db` guarded, so block lookups still work (compute-only, no caching) in tests that don't open a db.

**Miner attribution** (`miners` package): a pool's record lists its coinbase output **addresses** and its coinbase **tags** (the marker pools write into the coinbase scriptSig, e.g. `Mined by AntPool`, `/Foundry USA Pool/`). `miners.Attribute(addresses, coinbaseHex)` is the single attribution entry point used by both `computeBlockInfo` and the stats collector: it tries every coinbase output address as a map lookup first, then falls back to scanning the tags for one contained in the (hex-decoded) coinbase script, returning "" when neither matches — callers turn that into "Unknown" (`computeBlockInfo`) or skip the block (the collector).

Both halves of that are load-bearing, and both were established by measurement against the real mainnet node over the same 100 blocks:
- **Every** coinbase address must be tried, not just the first: modern coinbases carry several outputs and the pool's payout isn't reliably output 0. First-address-only attributed **8**/100.
- The **tag** fallback carries most of the attribution: the big pools rotate payout addresses far faster than `pools-v2.json` lists them, so address-only (all addresses) still attributed only **25**/100 and missed *every* major pool — the misses were AntPool, Foundry USA, F2Pool and MARA, each of which names itself in its coinbase tag. With tags: **98**/100, and the ranking matches the real network (Foundry 31%, AntPool 22%, F2Pool 12%). Tag matching is plain **substring** matching, not regex — of the 201 tags in the real file exactly one contains a regex metacharacter and it is a literal `$`. Tags are scanned from the database (a couple hundred rows per block), not from an in-memory copy, so the DB-backed design holds. The shortest tags are 4 bytes (`Kano`, `emcd`, `HHTT`, `EMC `), so a false positive on random coinbase bytes is possible in principle; this is the same heuristic mempool itself ships.

**It used to be three buckets**, and `miners.Init` folds a database written that way into one, in `migrate.go`, in the two stages the change was asked for: `fold` writes each pool's addresses and tags into its `miners-stat` record, and `move` empties `miners` of the address→name pairs it held, refills it from `miners-stat`, and drops `miners-stat` and `miners-tag`. Those two being gone is the whole signal that there is nothing left to fold, so every later start does nothing.

The stages are **separate transactions**, which is why `fold` sets both lists from the old buckets rather than appending to them: a crash between the stages leaves every address and tag still in the buckets they came from, so the next start folds them again onto the same result instead of doubling them. `TestMigrateResumesBetweenStages` drives exactly that state — and caught the appending version.

**Verified against this repo's own exported buckets** — 218 addresses, 201 tags and 156 aggregates loaded back with `tools/csvimport` and migrated by the binary: 218 addresses and 201 tags folded into **171 pool records**, seven buckets left afterwards with `miners` the only one of the three, and the mappings answering from it (a real AntPool payout address, and Foundry USA off a real coinbase tag) with `Top` ranking AntPool 109 923 blocks, F2Pool 99 082, Foundry USA 73 760. **138 aggregates were pre-satoshi and start again from zero**, which is the same 138 of 157 `tosqlite` reports skipping on that data — the two arrived at it independently. And `tosqlite` produced **identical `(name, address, tag)` rows** from the pre-migration database and the migrated one, 311 both ways.

**Attribution is answered from memory, not from the database.** `loadIndex` builds an address→pool map and a tag→pool list from the bucket at `Init` and again after every `update`, behind an `RWMutex` — the collector, `computeBlockInfo` and the 24h refresher are three goroutines. The tags are a **slice sorted by tag**, not a map: attribution takes the first tag the coinbase script contains, and a map's iteration order would make that a coin toss between two tags that both match, where the bucket cursor it replaces scanned in key order. The reason the definitions are still stored at all is unchanged — a populated bucket is what stops every restart re-downloading them.

`miners.Start()` (from `main()`, before the block cache) keeps the definitions fresh: an initial fetch of mempool's `pools-v2.json` **only when no addresses are loaded** (a fresh install) — a populated bucket survives restarts, so the definitions are not re-downloaded every start — then a refresh every 24h (`updateInterval`, a package var for tests). `update()` merges the file's addresses and tags into each pool's record and never removes one: the source only adds, so old entries stay valid and no full re-sync is needed. It leaves the aggregates in the record alone, and reloads the in-memory mappings when it is done. `sourceURL` is also a package var for tests. The real file currently holds 171 pools, 218 addresses and 201 tags. One caveat of the async refresh: on a *fresh* install the initial fetch races the block-cache backfill, so a few of the first-backfilled blocks may cache "Unknown" until re-computed; a populated bucket (any later restart) has no race.

### Miner statistics

`miners/stats.go` keeps a running per-pool aggregate in the `miners` bucket, **keyed by pool name** — so every address and every tag belonging to one pool combines into a single record — and `/miners` prints the top 10 from it. The stored `record` (unexported) is `Blocks`, `Reward` (satoshi, subsidy + fees = the whole coinbase output), `Fees`, `Work` (Σ difficulty × 2^32, the expected hashes) and `LastWork` (the work of that pool's most recent block), alongside the `Addresses` and `Tags` that pool is attributed by. `flush` reads and writes the record whole, so the definitions in it come through untouched; **a record with no blocks is skipped by `Top`/`Get`**, since a pool the definitions merely name is not a statistic — without that, a fresh install would list ten zero-block pools instead of "still collecting", and the app's miner page would present zeroes as fact.

`StartStats(src)` (from `main()`, only when the node is configured) runs `collect` immediately and then every `statInterval` (10 min, a var for tests). The `miners` package can't reach Core — that connection is package `main`'s — so the chain data is injected through the small `Source` interface (`Tip`, `Block`), implemented by `minerSource` in `blocks.go`: per height a `getBlockHash`, a `getBlockTxids` (verbosity 1 → height, **difficulty**, txids — `coreBlockTxids.Difficulty` carries it) and a `getRawTransaction` of the coinbase, giving every payout address, the coinbase script (for the tag) and the total output; fees are that total minus `subsidy(height)`.

- **Cursor**: `cursors`/`miners` holds the last processed height, as decimal text. A run resumes at that height + 1; with no cursor at all it starts at height 1, and the window the consumption share is computed over runs from there to the tip. (This bullet used to describe a JSON `cursor{Start, Last}` and an `initialWindow` of 1000 — neither exists in the code, which stores the one number and starts from 1.)
- **Chunking**: a gap wider than `chunkSize` (1000) is processed in chunks — each chunk aggregates into an in-memory `map[name]*stat` and is then merged into the bucket by `flush` in **one** transaction that also advances the cursor, so catching up thousands of blocks doesn't build one giant transaction and a crash mid-catch-up resumes from the last flushed chunk. `Blocks`/`Reward`/`Fees`/`Work` accumulate; `LastWork` is overwritten (chunks run oldest-first, so the newest write wins).
- **Waiting for the definitions**: `collect` early-returns while the address bucket is still `empty()`, so a fresh install doesn't spend its whole initial window on blocks nothing can be attributed to — it starts once `miners.Start()`'s first fetch lands.
- **A failed block fetch abandons the run** (no flush, cursor untouched) so the next tick retries the same range. Skipping the block and flushing anyway would step the cursor over it and drop it from the aggregate permanently — and a btcd restart mid-catch-up fails *every* block in the chunk, not one. The cost is that a genuinely unfetchable block stalls the collector, which is at least loud: the same warning every 10 minutes.
- A block whose miner can't be attributed (`Attribute` returns "") is skipped rather than counted under "Unknown", so the shares below are shares of the *attributed* blocks. Blocks reorged out after being counted stay counted — not worth correcting in an aggregate this coarse.

**The power estimate.** `Top(n)` returns `Stat{Name, Blocks, Reward, Fees, ConsumptionGW}`, sorted by blocks descending and **tie-broken by name** so a tied list is stable between calls. Consumption is the pool's share of the window's blocks × the *current* network hashrate × an assumed hardware efficiency:

    ConsumptionGW = (Blocks / (Last−Start+1)) × (LastWork / 600) × joulesPerHash / 1e9

`LastWork / 600` is the current network hashrate (that block's difficulty × 2^32 over the 10-minute target), which is why the record keeps `LastWork` at all: it carries the difficulty **in force now**, where dividing the accumulated `Work` by the window's seconds would average in every past difficulty epoch. `joulesPerHash` is `1e-11` — **the most modern mining hardware**, the latest hydro-cooled ASICs at ~10 J/TH (Antminer S23-class). Real fleets mix in older machines, so this is deliberately a lower bound: the "if they ran today's best gear" figure. Note `LastWork` alone can't rank miners (it's network difficulty, near-identical for everyone) — the block share is what differentiates them.

`/miners` (`minersCmd` in `main.go`) sends `Top(10)` as a plain numbered list — `1. AntPool. 22 blocks mined, reward 69.14 BTC, fees 0.39 BTC, consumption 2 GW` — with `trimNum` (a `format.go` helper: fixed decimals, trailing zeros trimmed) at 2 decimals for BTC and 1 for GW, and a singular "1 block". An empty bucket replies "No miner statistics yet — still collecting."

Verified against the real mainnet node over 100 blocks (throwaway probe, not in the suite): 98 attributed across 10 pools in ~7s, Foundry USA 31 blocks / 2.8 GW down to Braiins 1 block / 0.1 GW, the ten summing to 8.9 GW against a 9.1 GW whole-network figure at that difficulty — self-consistent, and about half of published real-world estimates, as the best-gear assumption implies. In the suite, `miners/stats_test.go` drives `collect` through a fake `Source`: `TestCollectStats` (aggregation by name across two addresses of one pool, plus a payout that isn't output 0), `TestTopConsumption` (the formula, pinned so that an accumulated-`Work` version would fail), `TestCollectChunks` (a chunk is flushed to the database before the next begins, asserted from inside the source's next fetch), `TestCollectResumes` (only new heights are fetched, stats accumulate, the window grows), `TestCollectRetriesOnError` (a failed fetch leaves the cursor and the bucket untouched, and the retry picks up the whole range) and `TestCollectWaitsForAddresses`. `TestMinersFlow` in `flow_test.go` covers the command's exact rendering by seeding the buckets directly.

### The /market command

`/market` (`marketCmd` in `main.go`) reports the current price, market capitalisation and 24h volume, then how the price has moved over 24h, 1w, 1m, 3m, 1y and 5y.

**The changes come from the bot's own rate history, not from a market API.** The `rates` package already holds a daily series back to 2009 plus live 5-minute samples, so `rates.At(now − period)` answers any period without a second dependency, and the figures stay consistent with the USD values shown everywhere else. A period whose baseline falls outside `rates`' tolerance is simply omitted rather than shown as zero — on a fresh install the older rows appear once the backfill lands.

Capitalisation and volume have no local source, so the rates updater fetches them from CoinGecko's free no-auth endpoint (`marketURL`, a package var for tests — one call returns price, cap and volume) **on its existing 5-minute tick** and stores them in the `market` bucket. `/market` reads `rates.LastMarket()`, so like every other command it answers from the database: no third-party call sits between the user and their reply, and an API that is down or rate-limiting costs a slightly stale figure rather than a failed command. Records are keyed by timestamp like the rate series, so the newest is simply the bucket's last key. Until the first snapshot lands those two fields read `unavailable` and the price falls back to `rates.Last()`.

Two formatters exist for this command specifically, both in `format.go`:
- `money` renders large dollar figures as markets quote them — `$1.33 T`, `$31.91 B`. Deliberately **not** `metric`, which is SI and says `G` where finance says `B`; a market cap in gigadollars reads as a units error.
- `price` keeps cents with comma-grouped thousands (`$66,223.00`), where `usd` drops them from $100 up. Cents are noise on a transaction amount and the point on a price quote.

`change(now, then)` renders both the absolute and percentage move, always signed. Note the percentage is measured against the **earlier** price, so the same absolute move reads differently in each direction — `TestChange` pins that asymmetry, since it looks like a bug otherwise.

### Exchange rates

The `rates` package keeps a BTC/USD price history in the `rates` bucket (same db file, via `rates.Init(db)` called from `openDB`), so `/info` and notifications can show a rough fiat value. Each internal `rateRecord{Time, USD}` (unexported; the value is always USD) is stored under its `Time.Unix()` big-endian key, so keys sort chronologically. `rates.Start()` (launched from `main()` right after `openDB`) backfills the daily history once (see next paragraph), fetches a current rate immediately, then refreshes every 5 minutes: the internal `update()` hits all price `sources` (CoinGecko, Coinbase, blockchain.info — free, no-auth GETs), **averages the ones that succeed** (a failed source is just skipped; if all fail nothing is stored), and writes one averaged record via `rates.Add(usd)`. The updater goroutine isn't explicitly stopped on shutdown — `main()` returns microseconds after `closeDB`, so a write-after-close is effectively impossible. Each source has a `parse` func tested against real API payloads (blockchain.info returns *every* fiat — we pluck `USD.last` out of it); `sources` is a package var so tests point it at `httptest` servers.

**Historical backfill:** so `/info` on an *old* transaction can show USD from around its block time (not just today's rate), the internal `backfill()` loads the whole daily series once. It's a no-op when the store already holds deep history — `hasHistory()` is true when the oldest sample is older than `historyHorizon` (3y), which live updates alone can't produce on a fresh bot, cleanly distinguishing "backfilled" from "just started". Otherwise it GETs blockchain.info's `market-price` chart (`historyURL`, `timespan=all` — the entire daily series back to 2009 in one no-auth request), parses it with `parseHistory` (skipping the zero-price pre-market days), and writes every day in **one** transaction via `storeRates` (per-record `db.Update`s would be thousands of fsyncs). Backfilled records land at daily 00:00-UTC timestamps, so they never collide with the live `time.Now()` samples. Verified once against the real endpoint (6402 daily samples, 2009→today); `historyURL` is a package var so tests point it at an `httptest` server, and `TestBackfillRates` also asserts the `hasHistory` guard by counting HTTP hits across two calls.

Two reads, **both DB-only, never online**: `rates.Last()` (cursor `Last()` — the newest sample) and `rates.At(t)` (the sample nearest `t` via `Seek`+`Prev`/`Last`, or not-found if the closest is more than the internal `tolerance` = 36h away). That tolerance is deliberately wider than a day so the daily-granularity backfill (samples at 00:00 UTC) still matches a transaction at *any* time of day — with a 1h tolerance `At` missed almost every daily sample and fell through to today's rate, defeating the backfill; live 5-min samples still match far more tightly. Both return the price as a plain `float64` and `(0, false)` when `db == nil` or nothing is stored, so USD is silently omitted in tests that don't open a db — USD is best-effort enrichment, not a hard dependency. `amountLine(btc, at, current)` (in `format.go`) renders `"<sat> sats (≈ $usd)"`, appending the USD part only when a rate is available: `current=true` uses `rates.Last()` (mempool `/info` and **new-transaction notifications**, which have no confirmed time = "now"), `current=false` uses `rates.At(at)` (a confirmed transaction's block time) **but falls back to `rates.Last()` when `At` finds nothing**. With the daily backfill in place `At` resolves almost any historical tx to its period's rate; the `Last()` fallback is the safety net for a tx in a genuine gap. USD only vanishes entirely when there is *no* stored rate at all. `usd(btc, rate)` (also `format.go`) drops cents from $100 up (`"$90,000"`, comma-grouped whole dollars, rounded) and keeps them below $100 (`"$58.23"`), on the logic that cents are noise on large amounts but the whole point on small ones. Both `usd` and `group` split the **sign** off before doing any of that, because the outgoing-watch `Net` line is the one place they see a negative and both used to mangle it — `group` counted back from the end of the whole string and produced `"- 100 010 000"`, `usd` took the below-$100 branch for any negative and produced `"$-29450.00"` (`TestNegativeAmounts` pins both). Only transaction *amounts* get USD — blocks and addresses have no amount.

### Clickable ids

Every shortened id a reply shows — a txid, block hash or address — also appears as an **inline-keyboard button** under the message, labelled with the same shortened form and carrying the full id as its `callback_data`. Tapping one runs `/info` on it, so browsing from a notification to the transaction to one of its addresses is a sequence of taps.

Buttons rather than links in the text, for a concrete reason: **Telegram does not parse entities inside `<pre>`**, and every reply's aligned field block is `<pre>`. A link there would render as literal text, so making ids clickable inline would mean giving up the column alignment. A button lives outside the message text, so both work at once.

There is also no way to do what one might first reach for — putting `/info <id>` into the user's input field. `switch_inline_query_current_chat` inserts `@botname <query>` (inline mode, not commands), `copy_text` only reaches the clipboard, and tapping a `/info` command in message text sends the command *without* its argument. A `t.me/<bot>?start=<id>` deep link would send a real message and the ids all fit its 64-character limit, but it needs the `<pre>` blocks gone and its behaviour for an already-started bot is undocumented.

`callback_data` is capped at 64 bytes, which a txid hits **exactly**, so the id travels bare — no type prefix, because `info()` classifies its argument anyway. `buttonRows` (in `telegram.go`) drops duplicates, empties, the `(non-standard)` placeholder that unnamed outputs render as, and anything over the limit; it lays buttons out two per row and stops at `maxButtons` (8) so a busy transaction doesn't bury its own message. Call sites pass ids through `sendLinked`, and pass only what the text actually displays — `transaction()` truncates its input/output lists to `shownAddrs`, the same cap `compactAddrs` uses for the text, so there is never a button for an address hidden behind the trailing `...`.

`update()` routes an incoming `CallbackQuery` to `callback()`, which answers the query first — Telegram spins the button until it is acknowledged, so that must happen regardless of what the lookup does — and then calls `info()` with the data.

### Internationalisation

Every user-facing string goes through `i18n(chat)`, which returns a `trans` (a `map[string]string` from English source string to translated string) for that chat's language — `trans.String`/`trans.Sprintf` fall back to the original string when the key is missing, so English is the default by construction and an English source string needs no entry anywhere.

**There are two ways in, and one table behind them.** `i18n(chat)` is the bot's: it looks the chat's language up in `chatLangs` (via `chatLang`) and hands the code to **`i18nl(lang)`**, which is the actual lookup and returns the **`english`** table for `""`, for `"en"`, and for any language there is no table for. `i18nl` is what the Mini App translates through — a page has no chat behind it, its reader's language arrives with the request — and it is why every display helper takes a **`lang string`** rather than a chat id: `when`/`day`/`humSize`/`amountLine`/`periodText`/`durationText`/`money`/`compactBTC`, and the `blockPairs`/`txPairs`/`addrPairs` builders they feed. The bot's own call sites pass `chatLang(chat)` at the point they call one; nothing else changed for them.

**One English word can need two translations, so a call site may use a context key.** `average` is the word both a block's fee distribution and its transaction sizes want, but Russian declines them differently — `средняя` комиссия against `средний` размер — and a single `"average"` key cannot be both. So the size line asks for **`"average-tx"`**, a key that is not itself the word to show.

That is what the `english` table in `i18n.go` is for: it holds the context keys and nothing else (`"average-tx": "average"`), because a key with no English entry would be printed *as the key*. A plain source string still has no entry and still passes through — which is why `i18nl` returning `english` rather than nil changes nothing else. The table sits **outside the `i18n-vet` markers** deliberately: a marked section must carry every translated string, and this one carries only the handful of keys that need it. Name a context key after the thing it qualifies (`average-tx`), and `TestContextKeysAreTranslated` fails the build if one is added to English but not to every other language — the case `i18n-vet` cannot see, since it only checks the strings it finds at call sites.

`langTrans` in `i18n.go` holds one map per language; **ru** and **es** exist today. The chat's language comes from Telegram itself: `update()` calls `SetChatLanguage(chat, msg.From.LanguageCode)` on every incoming message and callback, so it follows the user's client setting with no command to set it. `chatLangs` is an **LRU bounded to 10000** entries (the `lru` package), not a plain map — a bot that anyone can message would otherwise accumulate an entry per one-off chat forever.

The Mini App is translated differently — a whole page per language rather than a string table — because its text lives in HTML, not in Go. See The Mini App's translations below.

**`tools/i18n-vet` enforces coverage, and it runs in CI.** It walks every `.go` file, finds each `i18n(…)`/`i18nl(…)` `.String("…")` / `.Sprintf("…", …)` call, and checks that the string appears in *every* translation section of `i18n.go` — sections being delimited by `// i18n-vet:translation <lang>` … `// i18n-vet:end translation` comments — with the same format verbs in the same order. A new translated string therefore fails the build until every language has it.

The one thing to know before refactoring: **it extracts only string literals** (`*ast.BasicLit`) passed directly to those calls. Moving a translated string into a variable, a slice or a constant silently removes it from the tool's reach — no error, just no coverage. See The command menu for a case where that trade was made deliberately and covered by a test instead.

### The command menu

The menu Telegram shows beside the input field is registered with **`setMyCommands`** (`bot.setCommands` in `telegram.go`), called by `registerMenu` in `main.go` at startup.

**`/start` and the menu are driven off one list**, the package-level `commands` slice of `{name, line}` — that is what makes "the menu lists the same commands as `/start`" a property of the code rather than a convention someone has to remember. `start()` loops over it emitting `i18n(chat).String(c.line)`, and the menu takes each description from the same line via `menuDescription`, which cuts at the `" — "` separator and drops the trailing newline. Keeping the **whole `/start` line** as the translation key (rather than storing the description separately) reuses the existing ru and es translations untouched instead of re-keying and re-translating them.

The cost is that `i18n-vet` no longer sees those nine strings, since they are no longer literals at an `i18n(…)` call site (see Internationalisation). `TestCommandLinesTranslated` covers exactly that ground instead: every line in `commands` must have a translation in every language of `langTrans`. `TestMenuCommandsWithinTelegramLimits` additionally pins that no description comes out empty — which is what a translation using a different dash would silently produce — and that none exceeds Telegram's 256-byte cap, since **one bad entry makes Telegram reject the whole call** and leaves the menu empty.

Registration is **one call per language**: Telegram stores a separate list per `language_code` and falls back to the list registered without one, so English goes up with an empty code and each entry of `langTrans` gets its own. Failures are logged and skipped, never fatal — the menu is a convenience and the bot runs fine without it.

It sits **inside the `-register-webhook` block**. `setMyCommands` is global to the bot token, so a second instance started with `-register-webhook=false` (which already means "do not touch the live bot's Telegram-side state") would otherwise overwrite the live bot's menu.

### The Telegram Mini App

The `app/` package serves a Mini App — a web page Telegram opens in its in-app webview — on `-app-listen` (default `127.0.0.1:8080`, empty disables it). `app.Start(addr, token, src)` builds the routes inline and returns the `*http.Server` so `shutdown` drains it before `closeDB`, exactly like the webhook and dbui servers. `app.html` and the HTMX library are embedded with `//go:embed`, the same self-contained approach `dbui` uses.

Because it is its own package it cannot see main's fee cache or the display formatters (`trimNum`/`usd`/`group`), so the data it renders arrives through the **`app.Source`** interface — `Fees() app.Fees`, returning already-formatted `app.Tier` values — implemented by `appSource` in main. This is the same seam `miners.Source` uses, and it keeps all the amount/price formatting on the main side where the rest of it lives; the app package only arranges strings into HTML.

**Adding this moved the webhook.** `-listen` now defaults to **`:8082`**, freeing `:8080` for the app, because that is the port the Cloudflare tunnel's public hostname is routed to.

**It binds to localhost on purpose.** Nothing here faces the network directly — a Cloudflare Tunnel (`cloudflared`) holds outbound connections to Cloudflare's edge and proxies requests back down them, so the Pi needs no port forwarding, no public IP and no inbound firewall rule. Telegram requires valid public HTTPS for a Mini App, and the tunnel supplies it.

One operational constraint, learned the hard way and not obvious: **cloudflared's default QUIC transport cannot work over the AmneziaWG tunnel.** The link is MTU 1280, leaving 1252 usable bytes against QUIC's 1200-byte floor — only 52 bytes of headroom, which is not enough for cloudflared's handshake, so it crash-loops. The fix is `TUNNEL_TRANSPORT_PROTOCOL=http2` (Cloudflare's own precheck reports `suggested_protocol=http2`). TCP connectivity to the edge is fine throughout; only QUIC fails.

**Card titles are 15px, above the 14px labels.** They were 13px — the *smallest* text in a card while also being uppercase, letter-spaced and in the muted hint colour, three things that each cost legibility. That read fine on a desktop preview and too small on a real phone, where the page is physically smaller and held further away. The tab labels, at 14px in normal case, were the giveaway: they looked fine while the titles did not, which pointed at a relative typographic problem rather than a scaling bug (the viewport meta was correct all along).

**Every font size is in `rem`, and one rule sets the root on phones**:

```css
@media (max-width: 480px) { html.phone { font-size: 18px; } }
```

**Width alone cannot decide this.** Telegram Desktop renders a Mini App in a *phone-width panel*, so it matched a plain `max-width` breakpoint too and came out oversized on a monitor — measured at 375px, the breakpoint matches on both. What separates them is `Telegram.WebApp.platform`, which names the client outright; a head script adds the `phone` class for `android`/`android_x`/`ios` and nothing else. Verified by driving the page against a harness claiming each platform in turn at the same 375px: android → root 18px, tdesktop → root 16px.

**Windows takes the opposite correction** — `html.windows { font-size: 15px }` in the same breakpoint, because Telegram Desktop renders the panel larger there than on the other desktops. Telegram cannot answer this one: **Windows, Linux and macOS all report `tdesktop`**, so the OS comes from the browser instead — `navigator.userAgentData.platform` where it exists, falling back to `navigator.platform`/`userAgent` matching `Win`. The two classes are mutually exclusive (`else if`), since both rules have equal specificity and a device matching each would be settled by stylesheet order rather than by anything meaningful.

Verified by driving the page against a harness faking each combination: `tdesktop`+Windows → 15px, `tdesktop`+macOS → 16px, `tdesktop`+Linux → 16px, `android` → 19px. The fallback expression was checked against representative `navigator` values too — true for `Win32` and a Windows UA, false for macOS, Linux, Android and iPhone.

Three details it depends on:

- **The class is set in `<head>`, not in the script at the end of the page.** It scales every size at once, so setting it after the body had rendered would show a visible jump.
- **The width condition is kept as well.** An Android tablet reports a phone platform on a screen that does not need the bump.
- **A client too old to report a platform falls back to `pointer: coarse`** — a mouse is fine, a finger is coarse. Verified with the SDK removed entirely.

**`?debug=1` prints what the device reports** into the search hint — platform, viewport, device pixel ratio, resolved root size and pointer type. That is how this gets tuned from the phone itself, with no console attached.

That rule is the whole reason the sizes are relative. The original hope was that `rem` would make the page follow the font size the reader chose in their phone's settings — **it does not: Telegram's webview does not pass that setting down to the root**, measured on a real device, where converting every size to `rem` changed nothing visible. What the conversion does buy is this single lever: a phone is held further from the eye than a monitor, and one declaration now moves the entire page (measured at 375px: body 17 → 19.13px, the tier rates 20 → 22.5 — about 12% across the board).

`TestFontSizesAreRelative` pins that every size stays relative, since one `px` slipping back in would silently stop scaling with it; the root's own declaration is the one exception, being the base the rest are fractions of. `TestPhoneBaseFontSize` pins the breakpoint itself.

Verified with **nothing clipped anywhere** at 320 and 375px, across every tab and both details pages — and the design tolerates far more than this: it was checked from a 14px root to a 22px one before the breakpoint was added.

Two sizes cannot simply scale, and both are guarded rather than left to break:

- **The search field floors at 16px** (`max(1.0625rem, 16px)`). rem cuts both ways, and a *smaller* font setting would take it under 16px, which is where iOS WebKit starts zooming the page on focus.
- **The Market percentages yield to the width** (`min(0.75rem, 3.34vw)`). Six columns of `+512.9%` already measure their cells, so they scale with the root only until the width runs out — measured, the row overflowed by 15px at a 1.25x root before this. The `min()` also shrinks them smoothly below 360px, which is what the old `@media (max-width: 359px)` font rules did by hand; only the tighter gap remains there.

`html { text-size-adjust: 100% }` is set so a mobile browser renders what the desktop preview shows rather than auto-adjusting — and, now that sizes are relative, so Chrome does not layer its own inflation on top of the reader's setting and double-count it.

**The Market percentages are the one thing that cannot grow.** Six columns are width-bound: at 13px the row overflows at 360px, which is Pixel-class, so they stay at 12px (11px below 360px). Any change there must be measured at 320, 360 and 375 — raising them is what broke it.

Type sizes were raised roughly 15% across the page after the first mobile test — the original 10-12px labels read too small on a phone. Two constraints hold them in place: the search field must stay **at or above 16px**, below which iOS WebKit zooms the whole page whenever the field is focused; and "20.1 M / 21 M" is the widest value on the Blockchain card, measuring exactly its cell at 320px, so it is what caps any further increase.

The page is four tabs — Home, Blocks, Addresses, Watches (named to match the bot's /watch commands) — with the tab bar at the **bottom**, where a thumb reaches it on a phone, and padded with `env(safe-area-inset-bottom)` for notched devices. Home carries a network-fees card above a centred search field; the other three are the block list, the ranked address lists and the reader's own watches. Colours come from Telegram's `--tg-theme-*` CSS variables with fallbacks, so the page is also usable in an ordinary browser, which is how it gets developed.

**The server renders HTML, not JSON** — the HTMX shape. `/fees` returns the fee card's *contents* as a fragment and the page swaps it in with `hx-get`; there is no client-side templating, so the Go formatters the bot already has (`trimNum`, `usd`, `group`) produce exactly what the user sees. HTMX itself is **embedded and served from the binary** at `/htmx.min.js` rather than a CDN, keeping the page self-contained apart from Telegram's own SDK (which must come from telegram.org and should not be vendored).

The three tiers are the ones `/fees` prints, read from the **`cachedFees` background cache** rather than the mempool, so opening the app costs no node round trip. A cold cache renders "fees unavailable" rather than zeros dressed up as estimates.

**The page is rendered server-side, fees included.** `app.html` is an `html/template`, and `/` executes it with the current `Fees` — so the card is painted in the first response and there is no second round trip, no placeholder and no first-paint flicker. The card's markup lives in one `{{define "fees"}}` block that both the page and the refresh endpoint execute, so the version that ships and the version that replaces it cannot drift (`TestInlineAndRefreshMatch` asserts the page literally embeds the fragment `/fees` returns).

**A new block pushes both cards immediately.** `zmq.go`'s `hashblock` handler spawns `go onNewBlock()` alongside `processBlock`/`processConfirms`, which calls `refreshNetwork(false)` and `refreshFees()`. Without this the only `Notify` callers were the two 10-minute tickers, so SSE fired exactly when the `every 10m` fallback did — the push was working but had nothing to announce between ticks, which is indistinguishable from a dead stream.

`refreshNetwork` takes a **withNodes** flag for the one expensive call: `getnodeaddresses` returns tens of thousands of entries and several megabytes, and the count barely moves between blocks. The ticker asks for it; a block does not and carries the last known count forward. Fees are always recomputed on a block — clearing the mempool is exactly what makes the projection stale. `TestBlockRefreshSkipsNodeScan` pins that the block path issues `getblockchaininfo` and `getchaintxstats` but *not* `getnodeaddresses`, and that the previous peer count survives.

**Each card then refreshes when its data actually changes**, not on a timer. `main` calls `app.Notify("fees")` / `app.Notify("network")` right after a background cache is refreshed; the app fans that out over an **SSE stream** at `/events`, and the cards carry `hx-trigger="sse:fees"` / `hx-trigger="sse:network"` so HTMX re-issues its ordinary `hx-get`. Since both caches refresh every 10 minutes, the old 60s poll was re-fetching identical values roughly ten times per change.

**The stream carries event names only — never data.** That is what lets `/events` sit outside `requireInitData`: `EventSource` cannot set custom headers, so a stream that needed the signature could not be opened at all. The signal is worthless on its own ("the fee cache moved"), and the figures still come from `/fees` and `/network`, which remain authenticated because HTMX attaches the header to those. `TestEventStreamCarriesNoData` asserts no figure or markup ever appears in the stream.

Three details the implementation depends on:

- **SSE is a separate extension in HTMX 2** (`htmx-ext-sse.js`), embedded and served from the binary like `htmx.min.js`.
- **A keepalive comment every 30s** (`keepAlive`). An idle SSE connection is dropped by proxies well before two cache refreshes are 10 minutes apart, so without it the stream would die between updates.
- **The stream has to be told when the server is shutting down.** `http.Server.Shutdown` waits for connections to fall idle, and an SSE stream never does — it is holding the connection open on purpose. `Start` therefore makes a `closing` channel, selects on it in the handler, and closes it from `srv.RegisterOnShutdown`, which `Shutdown` runs before it starts waiting. Without it the bot logged `mini app shutdown: context deadline exceeded` on **every** restart, 15 seconds after "shutting down" — reproduced against the real binary and fixed the same way, and `TestShutdownDoesNotWaitForEventStreams` holds a real connection open across a real `Shutdown` so it cannot come back. The channel is per-server, not package-level: the tests start several, and a second `close` of one channel panics.
- **A `every 10m` fallback rides alongside the SSE trigger** (`hx-trigger="sse:fees, every 10m"`). If a proxy ever buffered or stripped the stream, the cards would otherwise freeze silently with nothing on screen to say so; the slow poll bounds that at ten minutes without undoing the point of pushing. Verified that adding it does not disturb the SSE half — an event still swapped the card — though the polling half itself is not measurable in a headless pane, which suspends timers (a plain `every 2s` control fires nothing there either).
- **`Notify` sends non-blocking.** The caller is a background refresh goroutine in main; a page that has stopped reading must never stall it. Same `select`/`default` pattern the watch fan-out uses.

Verified in a browser end to end: firing a server-side event updated the card (3 → 5 sat/vB, blocks 963268 → 963271) via an authenticated GET, and after killing and restarting the server the page **reconnected on its own** and swapped again with no reload — `EventSource` handles that, where a WebSocket would need reconnect logic written by hand. Choosing SSE over WebSockets also kept the dependency list at three: SSE is `net/http` plus `http.NewResponseController(w).Flush()`, whereas Go's stdlib has no WebSocket server.

Two further consequences worth knowing:

- A failed refresh must **not** wipe fees already on screen. HTMX does not swap error responses, but the `htmx:responseError` handler would have replaced the note, so it now bails out when the card already contains a `.tier` — stale numbers beat an error message. Verified in a browser against real data: a 401 refresh left all three tiers and the note untouched.
- The trigger must stay HTMX's own. An earlier version fired a custom event from an inline script, which races HTMX's `DOMContentLoaded` processing: the event was dispatched before HTMX had registered a listener and was lost, leaving the card on "loading…" with **no request ever made**. `TestFeesTriggerIsNotRacy` guards against reintroducing an inline `htmx.trigger()`.

**The Blockchain card** sits between the fees card and the search field: circulating supply against the 21M cap, chain height, on-disk size and active peers. It refreshes on the same every-60s cycle, from `/network`, and is rendered into the page the same way — one `{{define "network"}}` block shared by both, covered by the same `TestInlineAndRefreshMatch` drift guard. Four fields across is unreadable at 375px ("19.7 M / 21 M" alone needs the width), so it is a 2x2 grid of the same cells the fee tiers use.

Its data comes from `startNetworkStats` in main, on a 10-minute refresh, and two of the four numbers deserve care:

**Never put template syntax in a comment.** `html/template` executes actions wherever they appear, including inside a `<style>` block's CSS comment. A stray `{{.Field}}` naming something that does not exist fails the render *mid-page* — and since everything above it has already been written, the response is a **silently truncated page**, not an error. `TestPageRendersToCompletion` asserts the page ends in `</html>`.

Size uses `humSize`, which now takes a **decimals** argument: the bot's `/info` and `/mempool` messages keep two, the card takes none ("869 GB"). That flushed out a latent bug in `metric` — its trailing-zero trim ran on the whole string, so with `decimals=0` it turned "870" into "87", dropping an order of magnitude. Both formatters now share `trimZeros`, which leaves an integer alone; `TestMetricWholeUnits` pins it.

- **Coins is the issuance schedule, not a UTXO total.** `circulatingSupply(height)` sums the subsidy one halving epoch at a time (at most 33 iterations, not one per block), so burned and lost coins are still counted, as are the few blocks whose miners under-claimed. `gettxoutsetinfo` would be exact but walks the whole UTXO set and takes minutes — far too slow for a card that refreshes every ten. `TestCirculatingSupply` pins the epoch boundaries, which is where a per-epoch sum can go wrong.
- **Transactions** is `getchaintxstats`'s `txcount` — the whole chain's transaction count, one cheap call. It renders through `bigCount`, which says "1.4 B" where `metric` would say the SI "1.4 G": a count of things is read as billions, and `money` was no use since it prefixes a dollar sign.
- **Addresses is a hardcoded figure** (`"1.5 B"`, set in `startNetworkStats`), not something the node reports. Nothing counts distinct addresses yet: the `addrindex` package records touches per address but keeps no distinct-address total. It renders like the other values, so nothing on the page marks it as an estimate — it will drift from reality until the index can compute it.
- **Active nodes is the node's own address manager, not a reachability scan.** `getnodeaddresses 0` returns every address the node knows — measured on mainnet, **65 007 entries in 0.65s**, several megabytes — filtered to those seen within `activeNodeWindow` (48h), which gave **31 751**. That is gossip the node has heard, so it runs higher than a "reachable nodes" crawl like bitnodes. It is far too heavy for a request path, hence the background cache; and if that one call fails the previous count is carried forward rather than showing a misleading `0`.

**The Blocks tab** lists recent blocks newest first, **twelve to a batch** (measured: twelve rows fill a 360x800 screen exactly), each row carrying height, size, transaction count and the pool that mined it. It **scrolls infinitely** — there are no Prev/Next buttons; batches arrive as the reader reaches them, and new blocks arrive at the top.

**Height and miner are the tappable fields**, carrying Telegram's `--tg-theme-link-color` (a separate variable from `--accent`, which is the *button* colour). They replaced the row's trailing chevron: the chevron marked the whole row tappable, which is wrong now that two specific fields are. An unattributed miner renders as plain text — there is no pool to open — and the template does not compare against the string: `main` owns `"Unknown"`, so it sets `Block.MinerKnown` and the template branches on that. The **height opens the block details page**; the miner has no view to open yet.

**Three details pages — block, transaction and address — share one template and one handler** (`details` in `app.go`), differing only in which container they replace and where Back returns to. `Info{OK, Title, Rows}` comes from main; the handler fills in `Slot` and `Back`, since containers and URLs are the app's business rather than main's. A `Field` with an **empty Value is a heading** (`Fees`, `Tx sizes`), rendered bold rather than as a field with a blank value.

The rows are **literally the bot's**, not a parallel implementation: `blockPairs`, `txPairs` and `addrPairs` were split out of `formatBlock`/`transaction()`/`address()` so both callers build from the same code, and the app calls them with the **reader's language** — the same builders, translated through `i18nl` rather than through a chat (see The Mini App's translations). Titles are whatever the tab does not already say: `Block 963 268`, and for the other two just the shortened id (`32e43e...870b16`, `bc1qxy...hx0wlh`). A transaction opens on the **Blocks** tab, an address on **Addresses**.

**The ids inside a row are tappable**, which is the app's answer to the bot's inline-keyboard buttons: an address in a transaction's Inputs or Outputs, the `#963268` its Confirmations line names, and a block's own Hash. A tap opens that page — an address lands on **Addresses**, a block on **Blocks** — leaving the page it was tapped from where it was.

- **A link is a `/search` handoff, so a part carries no kind.** `/search` already classifies an id the way `info()` does, including the 64-hex ambiguity only the node can settle (a block hash reaches `/tx`, which resolves it to the block), and already answers with the `HX-Retarget` and `showtab` that move the reader to the right tab. Verified in a browser: tapping an address in a transaction's Outputs row switched to Addresses with the address page in `#addrpanel`, the transaction still sitting untouched in the block list's slot.
- **`Field.Parts` is the value cut into the ids it mentions**, built by main's `splitLinks` from the very list of ids the bot gives buttons for — which is already only what the text shows, capped at `shownAddrs`. `Value` still carries the whole line (a row with no ids renders from it, and an empty one still marks a heading), and the parts always reassemble to it exactly, which `TestTxInfoLinksBlockAndAddresses` asserts.
- **The text a part matches is what the row displays**, not the id: an address appears as `short(addr)`, but a block is named by height, as `#963268` — matching a bare `963268` would have found the digits inside some other figure. The block *hash* is in the bot's button list yet appears nowhere in a transaction's text, so it simply matches nothing and stays unlinked.
- **A tapped id carries the page's own origin** (`Info.From`, filled from `origin(r, slot)`), and `/search` now honours a `from` rather than always saying `home`. So Back keeps returning to where the reader started — a transaction opened from Home, then an address tapped inside it, still lands on Home — instead of unwinding one page at a time, which an app with no history stack cannot do anyway.

Records are loaded or computed exactly as `/info` does, so searching an uncached old block works rather than reporting it missing. A failed lookup still titles the page with what was asked for — `Title` is set before the lookup, so the reply reads `Block 99999999 / nothing found` instead of `Block `.

**Back returns the reader where they started**, which the page it belongs to cannot know — so the link that opened it says, as `from=<panel>` in the URL, and the Back button carries that on as `to=<panel>`. Opened from the search field Back lands on **Home**; from the watch list, on **Watches**; from the block list, on **Blocks** at the row that was tapped. Absent or unrecognised, `from` falls back to the tab the page itself lives in, which is the behaviour that predates this.

Back is always *restore the slot, then switch tab*: `/blocks?down=H&to=X` and `/addresses?to=X` re-render the container and answer `HX-Trigger: {"showtab":"X"}`. Two things that took care:

- **`/blocks` emits that header only when `to` is explicitly given.** An empty list also reloads through it, so triggering unconditionally would yank a reader off whatever tab they were on the moment a block arrived.
- **The panel name is whitelisted** (`isPanel`). It arrives in a URL a user can edit and is interpolated straight into the JSON of a response header.

**The miner page** opens from a pool name in the block list — `/miner?name=…` — and shows the `miners.Stat` fields with `/miners`' own formatting (`trimNum` at 2 decimals for BTC, 1 for GW). It needed `miners.Get(name)`, which builds the whole set rather than reading one record: the consumption estimate is a *share* of every tracked block, so it cannot be computed from one pool's row alone. `Top` and `Get` now both sit on a shared `all()`. An unattributed miner stays plain text — there is no pool to open — and a pool with no statistics yet says `nothing found` rather than showing zeros as fact.

Pool names have spaces in them (`SBI Crypto`, `Foundry USA`), so the link runs the name through the template's **`urlquery`**. `html/template` then escapes the resulting `+` as `&#43;`, which the browser sends back as `+` and `r.URL.Query()` decodes as a space — verified end to end in a browser, since an unescaped space would truncate the name.

**Two containers can hold a details page**: `#blocklist` (Blocks) and `#addrpanel` (Addresses). The Addresses tab's content is wrapped in `#addrpanel` precisely so Back has something to restore, served by `/addresses`. Replacing a tab's container *in place* is what keeps that tab selected with no tab juggling.

**`HX-Retarget` is what lets one search field reach three tabs.** The field must name some target, but only the server — having classified the query — knows where the answer belongs, so every details response corrects it. Without the header an address page is swapped into the Blocks tab, wiping the block list: not hypothetical, that is what happened before it was added, and only a browser run caught it.

**The title is centred using a hidden copy of the Back button as the right-hand spacer.** Nothing else makes the two grid columns exactly equal — sized from content they differ by the button's width, and equal `fr` columns squeeze the button out of its own cell — and only equal sides put the title on the true centre. Measured off-centre by 0px on all three pages at 375px, with the title set to ellipsis rather than overlap the button.

**Search hands off through `/search`.** The field carries `hx-trigger="keyup[key=='Enter']"`, and:

- **`/search` is a classifier, not a renderer**: it 303s to `tx?id=`, `block?height=` or `address?a=`, so each details endpoint stays the only place that renders its kind. The `X-Telegram-Init-Data` header survives that same-origin redirect — verified in a browser, since a dropped header would 401 and swap nothing.
- **Each details endpoint answers `HX-Trigger: {"showtab":"<panel>"}`**, and one listener on `document.body` switches the tab. It fires for the list's own links too, where it lands on an already-active tab and does nothing — cheaper than a second code path in `/search`, and the JSON form means a new tab needs no new event name.
- Classification follows the **same order as `info()`**: the 64-hex shape first (a string of 64 digits is also a valid height), then a height, then an address as the catch-all. A **block hash has the same 64-hex shape as a txid** and only the node can tell them apart, so `/search` sends it to `/tx` and main's `TxInfo` resolves it — an id the node has a block header for is shown as that block instead. Both live on the Blocks tab, so the handoff is invisible.
- Only an **empty** query answers 204 (which HTMX does not swap). Anything else reaches a page; a query that is no kind of Bitcoin id lands on the address page saying so, rather than presenting an empty history as fact.

It reads the **`blocks` bucket directly** — no node round trip. The keys are big-endian heights, so walking a bbolt cursor backwards yields descending order with no sorting, `Seek` starts a batch at a given height without stepping over the ones above it, and the cached record already holds every field the row needs. A record that fails to decode is skipped rather than ending the batch early.

**The list is keyed by height, not by an offset** (`app.Range{Before, After, Down}`, at most one field set; all zero is the newest batch). The list grows at the *head*, so with an offset a block mined mid-scroll would shift every boundary down by one and the next append would repeat the row that crossed it. A height cannot shift. It is also cheaper: an offset page had to walk past every earlier record, where `Seek` goes straight there — which is what makes scrolling arbitrarily deep affordable.

**Two sentinels bracket the rows**, and each replaces *itself*, so the list has no state the server has to be told about:

- **Below the rows**, `/moreblocks?before=<lowest height shown>` appends the next batch and a fresh sentinel; when the bucket is exhausted, no sentinel comes back and the list simply ends. Its trigger is **`intersect once`, not `revealed`** — htmx's own docs say `revealed` does not handle content in an `overflow` scroller, which `.rows` is.
- **Above the rows**, `/newblocks?after=<highest height shown>` answers `sse:blocks` (with `every 10m` as the same fallback the cards carry) and prepends whatever was mined, above a fresh sentinel carrying the new height. **Prepending is what keeps the reader's place**: inserting above them leaves the rows they are reading where they are, where re-rendering the container — what the pager used to do — throws them to the top of the list. Nothing new is a legitimate answer: the sentinel comes back watching the same height.

Three consequences worth knowing:

- **A prepend that fills a whole batch replaces the whole list instead** (`HX-Retarget: #blocklist`), because more new blocks than fit would leave a gap between them and the rows already on screen. It costs the reader their place, which is the right trade against a list with a hole in it. Only reachable after the tab has sat open through a couple of hours of missed blocks.
- **`/newblocks` is the one block endpoint that is not cached.** Its answer decides a response header, which a cache hit would not set — and it is keyed by a height that moves with every block, so an entry would be read about once anyway.
- **An empty list keeps its own trigger.** With no rows there is no sentinel to sit above, so the "no blocks cached yet" placeholder carries `sse:blocks` and reloads the container — otherwise a fresh install would sit on that message forever.

**Back restores the list down to the block that was opened**, and scrolls that row back into view: every row's link carries its own height as `down=H`, and the Back button's swap is `outerHTML show:#blk<H>:top`. An infinite list has no page number to return to, and restoring the rows *without* the position would land the reader at the top of a list they had scrolled a long way down. `blocksMaxRows` (20 batches) bounds it, which is also what stops an edited `down=` from asking for every block ever cached; `down=0` is excluded along with the nonsense, so genesis restores to the top like a search does.

**`app.Notify("blocks")` fires from `processBlock`, after `storeBlock` succeeds** — not from `onNewBlock`. The tab reads the cache, and `processBlock` runs in its own goroutine, so announcing from the ZMQ handler would race and have the page re-fetch a list the new block is not yet in.

Every height comes from a URL a user can edit: `down` falls back to the newest blocks, and `before`/`after` are refused with a 400 rather than being read as "from the tip", which would make an edited URL a way to re-render the whole list under an append.

**Verified in a real browser** (headless Chrome at 390x760, driven against a harness serving the app with a 500-block fake chain), because none of this is measurable from the response bodies the tests see:

- **Scrolling appends**: 12 rows chain-loaded to 24 to fill the first screen, then 36 → 48 → 60 → 72 as the scroller was driven to the bottom four times, with exactly one sentinel alive throughout.
- **Prepending keeps the reader's place exactly.** With three blocks inserted above a reader 48 rows down, the row at the top of the viewport **moved 0px** — the browser's scroll anchoring absorbed the insertion, raising `scrollTop` 1076 → 1209 by precisely the new rows' height. This is the whole reason the top sentinel exists; re-rendering the container instead resets the scroller to 0.
- **The overflow path** (68 new blocks) replaced the whole list through `HX-Retarget` — one container, one sentinel, and the fresh list still appended as it was scrolled.
- **Back** landed the tapped row back on screen (opened row 21 of 36, came back with it 440px down a 511px viewport — `show:` clamps when the restored list is not tall enough to lift the row to the very top, and the bottom sentinel then refilled the list as usual).

The alias dialog was verified the same way, driven over CDP against a harness serving the real `app` package with an in-memory watch store: the bell filed a watch and the dialog opened on the server's `askalias` with only Save; Save wrote the name through to the store; the Watches tab's edit icon opened it prefilled, in its two-button shape, with Delete measured red (`rgb(217, 45, 32)`); Update renamed the watch and the row behind the dialog was already showing the new name when it closed; Delete removed it and the list dropped a row — all with no console errors, and the same flow confirmed on a transaction page (`kind=tx`) and for an empty alias, which closed the dialog and changed nothing. Measured at 320, 360 and 390px in all three languages: **`Удалить наблюдение` overflowed the button row at 320px**, which is why the Russian label is now `Удалить` and why `.dbtns button` carries `min-width: 0` — a flex item will not otherwise shrink below its longest word, so any long translation would push the row out of the dialog.

Note the harness had to strip the SSE connection: headless Chrome's `--virtual-time-budget` never finishes while a stream is open, and `--dump-dom` measured nothing useful anyway — IntersectionObserver needs real frames, so the probes report over a live rendering loop instead.

**The Addresses tab** is three ranked lists of addresses — **Active** (busiest first), **Rich** (largest balance first) and **Abandoned** (whose coins have gone longest without moving, oldest first) — chosen by a picker at the **foot of the panel**, right above the tab bar where a thumb reaches it. Each row is the shortened address, tappable, and the one figure that list ranks by: `4 447 003 txs`, `248597.59 BTC`, `3 february 2009`. It opens on Active.

They read the `active`, `rich` and `abandoned` buckets, which **nothing in the bot writes** — `tools/csvimport` loads them from the exports `tools/addrindex`'s `actbuild`, `richbuild` and `ababuild` produce. Values are the decimal text csvimport stores; one that does not parse is skipped the way a block record that fails to decode is, rather than being indexed as something it is not.

**The ranking is the whole problem**, and `addrlists.go` solves it with an index. A source bucket is keyed by address and *ordered* by address, so there is no cursor trick that yields value order the way the block list's big-endian heights do. So each list gets a second bucket — `activeindex`, `richindex`, `abandonedindex` — holding the same rows keyed by the **value**, which a cursor then walks in rank order: `Last`/`Prev` for the two that rank high-to-low, `First`/`Next` for the abandoned dates, which rank oldest first. A batch costs the entries it steps over plus the rows it returns, and nothing else.

**The whole entry is the key** — the value big-endian (8 bytes for a count or a balance, 4 for a unix date) followed by the address, with **nothing stored as the value**. The same shape `addrindex` uses for its own touches, and electrs' `bindex-rs` before it.

That address suffix is load-bearing. bbolt keys are unique, so a bare value key keeps only the last address written under each value — and these values collide heavily. Measured on the real exports: 120 119 active addresses hold just **14 269 distinct counts**, so 88% of that list would have been silently dropped; rich loses 65% and abandoned 34%. With the address in the key all 196 536 rows are indexed, the value still leads so cursor order is still rank order, and the address breaks ties. A read slices the address back out of the key. `TestAddrIndexKeepsCollidingValues` and `TestAddrIndexKeyFormat` pin both halves.

**A goroutine rebuilds all three every hour** — `startAddrIndexes()`, launched from `main` right after `openDB` and stopped by `shutdown` **before `closeDB`**, since a rebuild in flight is holding a write transaction (the same ordering, and the same reason, as `stopBackup`). `addrIndexInterval` is a package var so tests can drive the loop. It rebuilds **once immediately and then on the interval**, the shape every other collector here has (`startBlockCache`, `StartStats`, `miners.Start`); waiting out the first hour instead would leave a freshly imported database showing three empty lists.

Each rebuild is **from scratch** — the index is dropped and written again rather than diffed, because csvimport replaces a whole bucket and there is nothing cheaper to compare against. So a re-import needs nothing done to it: the next hour picks it up, rows added, rows gone, or a bucket emptied altogether.

Three things about the rebuild:

- **Entries are collected, sorted by index key, and only then written.** The source yields them in address order, which is random against the index key, and bbolt rebalances on every such insert. Measured on the real exports, sorting first took the three builds from **3.45 s to 106 ms** — 111/48/14 ms for 120 119, 66 417 and 10 000 addresses in a real run, against **+17 MB** of database (carrying the address as a value as well cost 27 MB, which is what dropping it saved).
- **The drop and the refill are one transaction**, so a reader is served the whole old index or the whole new one, never the empty middle of a rebuild. bbolt's single writer does not block readers, so nothing waits on it either.
- **A source that is missing, or holds nothing indexable, ends with no index at all** rather than a stale one — which is what makes an emptied bucket show as an empty list rather than as whatever was last built from it.

Because it no longer runs on the startup path, the app is **already serving while the first rebuild is in flight** (measured: `GET /` answered 200 in 2.6 ms one second into a start whose indexes were still building), and the address lists simply fill in when it lands.

Note one behaviour change from the scan-and-sort version this replaces: within a group of **equal** values the two descending lists now order addresses the other way round, because the index is walked backwards. Verified against the previous implementation over the real data — the active and abandoned listings are byte-identical, and rich differs only in the order of two addresses inside a group all holding exactly 3000.00 BTC, the same set at the same offsets. Both orders are arbitrary; both are deterministic, which is what offset paging actually needs.

Five things about it are deliberate:

- **Paging is by offset, where the block list needs a height.** The reason the block list cannot use one is that it grows at the head, so a block mined mid-scroll shifts every boundary; nothing is ever inserted above these rows, so an offset is exact. That is also why there is **no sentinel above the rows and no SSE trigger anywhere on this tab** — the buckets are loaded offline, so there is nothing to announce. `TestAddressListDoesNotWaitForEvents` pins that, since a copied `hx-trigger` would look harmless and quietly re-fetch forever.
- **The first batch is 15 rows and each scroll adds 10.** The first has a screen to fill; the rest arrive as the reader reaches them, through the same `intersect once` sentinel the block list uses, and for the same reason (the rows are their own `overflow` scroller, which htmx's docs say `revealed` does not handle).
- **A switch re-renders the whole panel**, buttons included, so which button is lit and which rows are under it cannot drift apart — there is no state in the page to keep in step. The kind then rides in every link the batch renders, and is whitelisted on the way in: it arrives in a URL a user can edit and goes straight back out into those links.
- **Back restores the list the reader was on, at the row they tapped** — `addresses?kind=rich&down=20&to=addresses`, swapped `outerHTML show:#adr20:top`. Row **0** is the top of the list and an ordinary answer, so unlike a block height the value cannot also mean "Back did not ask"; `AddrRange.Restore` says that separately. A page reached any other way — a search, a watch row, an id tapped inside another page — carries neither and lands on the first batch.
- **The restore is bounded separately from the scroll.** `addrsMaxRows` (10000) is how deep the scroll goes — reaching row N steps N entries of the index, so it also bounds what an edited `from=` can ask for; `addrsRestoreRows` (215, the first batch plus 20 more) is what one Back may re-render, because those rows arrive a batch at a time on the way down but all at once on the way back. Without the second bound an edited `down=` is a request for a megabyte of rows.

The lists are **rendered into the shell page** like the block list, so opening the tab costs no round trip, and `TestAddressListIsInThePage` is the same drift guard the cards have. Batches are cached by URL in `addrsCache` (20, like the block list's), and **nothing invalidates it by event**: csvimport needs bbolt's exclusive lock and so cannot run against a live bot, which leaves `cacheTTL` the only expiry these entries need.

Served from the index, a first batch measures **1.1 ms** over the 120 119-row active list, 0.9 ms over rich and 0.7 ms over abandoned — and **1.4 ms at row 9000**, where the scan-and-sort version cost 9.8 ms for a first batch and 20 ms by row 900.

The rebuild loop was driven end to end against a live bot with those buckets, at a 15-second interval, writing through the bot's own database UI: a new richest address added to `rich` was at the top of the list **14 s** later, and removing it again dropped it **16 s** later — both inside one interval, with the index count moving 66 417 → 66 418 and back.

Verified in a real browser (headless Chrome at 390x760, driven over CDP against the running bot with the real 120 119 / 66 417 / 10 000-row buckets): scrolling appended **15 → 25 → 35 → 45 → 55** with exactly one sentinel alive throughout; each button lit its own list and loaded it (`248597.59 BTC` for `34xp4v...4Twseo`, `3 february 2009` at the head of Abandoned — both matching the figures `richbuild` and `ababuild` are documented against); tapping row 20 of a 35-row Rich list opened the address page and Back came back to Rich with that row on screen, the bottom sentinel refilling as usual. Two traps worth knowing before repeating it: the **real Telegram SDK loads from telegram.org and replaces an injected `window.Telegram`**, taking the signed initData with it, so every request 401s until `telegram.org` is blocked; and Chrome inherits the machine's locale, which on this one is Russian, so `Accept-Language` has to be overridden or the unauthenticated shell page comes back in it.

Measured at 320, 360 and 390px in all three languages with **nothing clipped and nothing overflowing**. The Spanish `Abandonadas` was the one casualty — it ellipsised at 320px — and is `Olvidadas`, the same word the Russian page uses; `.seg button` also carries `min-width: 0`, since a flex item will not otherwise shrink below its longest word.

**The Market card** sits between the Blockchain card and the search field: the current rate under the title, then one narrow column per period — 1d, 1w, 1mo, 3mo, 1y, 5y — showing only the signed percentage, green up and red down. It refreshes on `sse:market` with the same `every 10m` fallback, and `startMarketUpdates` sends that signal on a ticker.

Unlike the other two cards it keeps **no cache**: the change figures are `rates.Last()` and `rates.At()`, plain database reads, so `appSource.Market()` computes them per request and the ticker only has to send the signal.

Two details:

- **A period with no baseline renders a placeholder, not a missing column.** On a fresh install the older periods have no rate to compare against until the backfill lands; dropping them would reflow the grid from six columns to fewer. The cell shows an em dash in the neutral colour instead.
- **Six columns fit from 360px up**, which covers every current phone. At 320px an extreme five-year figure would overflow the row, so a media query shrinks the type there rather than dropping a period — measured at 320, 360 and 375.

**`html/template` escapes `+` as `&#43;`** (a defence against UTF-7 attacks), so a signed percentage is `&#43;2.5%` in the served HTML even though the browser shows `+2.5%`. Tests that assert on rendered figures must unescape first, or a raw substring search silently fails on every positive change.

**Every response is served from cached HTML** (in `app.go`, above the SSE section), held in three `lru` caches. `cards` keys the single-valued renders by the template block each comes from — `fees`, `network`, `market` and `app` (the whole shell page) — at `cardsCached` (4), exactly the number of them, so nothing is ever evicted for space: that cache is used for its keying and expiry, not its bound. `blocksCache` keys the block list by URL at `blocksCached` (20), and *is* bounded, because a reader scrolling down accumulates one entry per batch and a restored list is deeper still, so the key is what makes scrolling back over ground already covered free, while an edited `before=` parameter is what the bound contains. `addrsCache` is the same again for the Addresses tab, which scrolls the same way — and is the one cache no event ever clears, its buckets being loaded offline. The unit cached is the **rendered HTML**, not the data behind it: a hit skips both the `Source` call and the template execution, and every viewer is served the same bytes.

**Caching `/` is only sound because the page carries no per-user data** — the same rule that already lets it be served without a signature at all (see below). One cached copy goes to every visitor, so anything per-chat must stay behind the `requireInitData` endpoints; this is now a second, harder reason why.

Invalidation is event-driven with a time backstop:

- **`Notify` drops the matching card before it announces the event.** That order is load-bearing — a page reacting to `sse:fees` within milliseconds would otherwise be handed the very copy it was told to replace. `Notify("blocks")` clears *every* page of the list, not just the one showing, because a new block shifts the whole window by one.
- **Any known event also drops the shell page**, which embeds all four cards: whichever one moved, the page the next visitor would get is stale. An event no card is keyed to leaves everything alone (`invalidate`'s `default: return`), so a stray name cannot flush the caches.
- **`cacheTTL` (10 min) belongs to the entry**, stored via `lru.PutTTL` and checked when it is next read — there is no sweeper and no goroutine to start and stop alongside the server. It is not redundant with the `Notify` path: the block collector fills `blocks` in the background without announcing it, so the newest cached block can move with no event at all. Note each entry runs its own clock from when it was rendered, so block pages expire independently rather than all at once, which an earlier single `blocksClearedAt` timestamp did.
- **A failed render is not cached.** `execute` reports whether the template succeeded and the caller stores nothing on failure — caching a half-rendered card would otherwise persist the breakage for the life of the entry.

Note `TestInlineAndRefreshMatch` — the drift guard asserting the page embeds the exact fragment `/fees` returns — still holds with both sides cached, because both execute the same `{{define}}` block from the same `Source`. It is weaker than it was (a stale page and a fresh fragment would both have to be wrong in the same way to slip past), but the shared block is what it was really pinning.

`invalidateAll` clears both caches wholesale rather than looping over `invalidate`. The app tests share this package state, and an earlier version that cleared the page only as a *consequence* of card invalidation made the test helper's isolation depend on the very line under test — a mutation of it leaked one test's fixture into the next instead of failing the test that targets it.

`data` is called *outside* `cacheMu`, so a `Source` implementation is never invoked with the cache lock held — main's `appSource` takes `feesMu`/`networkMu` of its own, and the refresh goroutines call `Notify` (which takes `cacheMu`) right after releasing them. Two concurrent misses simply render the same bytes twice, which is cheaper than serialising every request behind one mutex. `TestCacheConcurrentRequests` drives that path under `-race`.

**The watch button** is a bell in the title row of the address and transaction pages — the two kinds that can be watched; a block or a miner has nothing to file. Pushed means watching, and tapping toggles it.

- **The page decides whether it has one, not the URL.** A block hash has a txid's shape, so it arrives at `/tx` and comes back — through main's `TxInfo` — as the *block*. Stamping the request's kind on whatever came back put a bell on that block page offering to watch a block hash as a transaction. So a `Source` may name the page's own `Kind` (main's `BlockInfo` always says `block`), the URL's kind applies only when it does not, and anything that is not watchable carries no kind at all, which is what the template keys the bell off.
- **It loads separately from the page it sits in.** Whether *this* reader watches something is per-user, and the details page around it is one cached copy shared by everyone, so the page ships an empty `<span id="watchbtn" hx-get="watch?…" hx-trigger="load">` and the button arrives from an **uncached** endpoint. Rendering the state into the page would serve one user's watches to the next.
- **`GET /watch` reads the state, `POST /watch?on=1|0` sets it.** The desired state rides in the request rather than being toggled server-side, so a stale button cannot flip a watch the reader did not mean to touch: setting twice is a no-op, not an undo. The response is the re-rendered button, swapped in place.
- **It shares the ghost Back button's grid cell**, positioned at that column's right edge. The ghost is what sets the column's width and keeps the title centred (measured: still 0px off-centre with the bell present), and the bell is smaller, so it fits inside without disturbing it.
- **Hidden outside Telegram** by a `body.tg` class set once at load. It cannot be set per fragment: details pages arrive later by swap, and a script inside one would never re-run. In practice the guard is belt-and-braces — outside Telegram every data endpoint 401s, so no details page loads at all.

**Naming a watch is a second step, in a dialog.** Tapping the bell files the watch immediately — with no alias — and the response asks the page to open a dialog for one; the Watches tab's edit icon opens the same dialog on a watch that already exists. Both are the one `<dialog id="aliasdlg">` in the shell page, in two shapes: naming a new watch offers only **Save**, editing an existing one offers **Delete watch** (red) and **Update alias**.

- **The dialog lives in the shared page, so it knows nothing until something tells it.** It carries hidden `kind` and `id` fields that the opener fills in, which is also what lets its buttons post from inside one form: HTMX sends the enclosing form's values with any non-GET request from an element inside it, so **Delete** posts to the existing `watch?on=0` with the id in the body rather than needing an endpoint of its own. `/watch` therefore reads kind and id from the query **or** the form.
- **The bell asks for the dialog through `HX-Trigger`**, `{"askalias":{"kind":…,"id":…},"watchtab":""}`, built with `json.Marshal` rather than concatenated the way `showtab` is — these carry an id a user chose, where a panel name is whitelisted. `watchtab` is the event the Watches tab already listens for, so every change to a watch makes that list re-fetch itself with no extra wiring; unwatching sends it too, and sends no `askalias`.
- **`POST /alias` is the only new endpoint**, and an **empty alias is a no-op** — Save on an empty field is how a reader dismisses the dialog, so it must not clear a name the watch already has. It answers 204: the dialog swaps nothing and is closed by the page on `htmx:afterRequest`. A long alias is **cut to `aliasMax` (64 runes)** rather than refused; the field carries the same cap, but the endpoint is reachable without the page and nothing else keeps a label small.
- **The edit icon is caught on the way up to the body**, not bound per row: watch rows arrive by swap, so a listener inside one would never be registered. Each row carries `data-kind`/`data-id`/`data-alias`, which is everything the dialog needs.
- **Renaming has to reach three places**, not just the store: `setAlias` in main rewrites the record, **restarts the notifier goroutine** — it holds its alias by value, so a rewritten record alone would leave notifications announcing the old name until the next restart — and renames any confirmation already pending, so one in flight arrives under the new name. `TestSetAliasRenamesALiveWatch` drives all three and fails on each of them alone.

`SetWatch` goes through the same `addWatch`/`removeWatch` that `/watch` and `/unwatch` use — split out of those commands for exactly this — so a watch added from the app starts the same notifier goroutine, seeds the same outpoints and respects the same `maxSubscriptionsPerChat` cap. That is why `appSource` now carries the `*bot`: starting a watcher needs something to send with. A refused or failed set renders the button unpushed (or, on an error, in red) rather than claiming a state the store does not have.

**The Watches tab is the app's only per-user view**, and the only thing here that must never be cached or rendered into `/`. Every cache here is keyed by URL, which is identical for every visitor, and `/` is one copy served to everyone — so `/watches` renders on every request and the shell page ships an **empty** `#watchpanel` for the fragment to replace. That is structural, not a convention: there is no code path that could put a watch into the page.

Every row on that tab carries an **edit icon to the right of its alias**, which opens the alias dialog on that watch; Delete and Update both answer with the `watchtab` event, so the list under the dialog is already correct when it closes.

The chat is `chatOf(initData)` — the `user.id` Telegram **signs**, which for the private chat a Mini App is opened from is the same id the bot files watches under. The same `r.Chat != chat` filter `watchesCmd` applies is what scopes the list, and `TestAppWatchesAreScopedToTheChat` in package `main` pins that line specifically: the app package's tests run against a fake `Source`, so dropping the filter there passes everything else.

Rows reuse the block list's shape — the shortened id as a link, the alias muted on the right — and open the same `/address` and `/tx` pages a search does, so a watched id is one tap from its details. The fetch fires on `watchtab`, an event `showPanel` dispatches when the tab is opened, rather than being kept warm: the list is per-user, uncached, and cheap to rebuild.

**Outside Telegram the tab says so.** There is no `initData`, so `/watches` can only 401 — and HTMX does not swap a failed response, which would leave a placeholder sitting there forever. The page's own script checks `Telegram.WebApp.initData` at load and writes the message itself, so the answer is immediate and does not depend on a request failing. Verified in a browser against a page served without the Telegram SDK.

### The Mini App's translations

The bot translates by looking a string up in a table (`i18n`), but the app's text is in `app.html`, so it translates by **whole page**: `app.ru.html` and `app.es.html` sit beside `app.html`, identical in every tag and attribute and differing only in the words. `//go:embed app.html app.*.html` takes them all, and `parse` parses one `*template.Template` per language into `templates`, each still **named `"app"`** — the page is executed by that name, so naming the root after the language leaves `"app" is undefined` at the first request.

**`language(r)` picks the page, and initData beats the header.** Telegram signs `language_code` into the payload, so when the app is opened from the bot that is the reader's own client setting — the same one the bot's replies follow — and it is exact. A plain browser offers only `Accept-Language`, which is parsed by **quality, not by written order**: `en;q=0.1,ru` asks for Russian, and reading it left to right would answer in English. A malformed `q` keeps the default of 1.0 rather than sinking its language. Only the primary subtag is matched (`pt-BR` is `pt`), since a page is per language and not per region. A user language with no page **falls through to the header** rather than jumping to English — a reader whose Telegram is Japanese on a Spanish phone is better served in Spanish — and English is the last resort. Every response carries `Content-Language`.

**The language belongs in the cache key.** Every cache here is keyed by URL, which is identical for every reader, so without it the first reader's language is served to the next — the same hazard that already keeps per-user data out of `/`. `key(lang, uri)` is that key, `cardsCached` grew to `4 * len(langs)`, and `Notify` deletes each card in **every** language, or the readers of the ones it missed keep a stale card until the TTL runs out.

**Not everything on screen comes from the page.** The details rows (`Hash`, `Miner`, `Reward + fees`), the block list's `Unknown` and `4 000 txs`, and the market card's `1w` are built in `main` and arrive through `Source`, so the page's own words are only half the answer. **The language therefore travels with the request into `Source`**: `Market`, `Blocks`, `Addresses`, `BlockInfo`, `TxInfo`, `AddrInfo` and `MinerInfo` each take a `lang`, `main` translates through `i18nl(lang)` (see Internationalisation), and the values follow the labels — a size reads `1.56 МБ`, a date carries a Russian month, an unknown fee distribution says `недоступно`.

The calls that take no language are the ones with no words of their own: `Fees` and `Network` return numbers whose labels live in the translated page, and `Watches` returns ids. The one **consequence worth knowing** is that the Blockchain card's units are still English (`869 GB`, `1.4 B`) — those figures are formatted once into `cachedNetwork` by the background refresh, where there is no reader to have a language, so translating them means keeping that cache raw and formatting per request.

`/newblocks` reads the language itself (`language(r)`) rather than getting it from `cached`, being the one block endpoint that is not cached.

Two tests hold the seam, one on each side of it, because neither side can see the other: `TestSourceIsAskedInTheReadersLanguage` (app) records what language each `Source` call was made in — a fake `Source` has nothing translated to render, so the plumbing is invisible in the response — and `TestAppSectionsAreTranslated` (main) drives the real `appSource` and asserts the Russian labels, values and market periods, since the app package's own tests never see main's words.

**`tools/i18n-html` is what keeps the copies in step**, and CI runs it:

```
i18n-html ./app/
app.html: es matches (354 elements)
app.html: ru matches (354 elements)
```

For each reference `xxx.html` it finds the `xxx.<lang>.html` beside it, reduces both to the parts a translation must reproduce exactly, and compares those as text. The reduction keeps **tags, their attributes and the `{{...}}` actions**, and drops what a translator is meant to rewrite: the text between tags, and the values of the attributes a reader sees (`placeholder`, `title`, `alt`, `aria-label`) — where the actions inside are still kept, so `title="{{if .On}}Stop watching{{else}}Watch this{{end}}"` reduces to `title="{{if .On}}{{else}}{{end}}"` and translates freely. Whitespace inside a tag is collapsed, so a longer word may wrap its attributes differently.

Four things about it are deliberate:

- **It is hand-rolled rather than built on an HTML parser.** A parser would have to be taught Go template syntax — `{{define}}` between tags, `{{if}}` inside an attribute value — and `golang.org/x/net/html` would be a dependency for one tool. The scanner treats a `{{...}}` action as atomic *before* it interprets `<` or a quote, which is what makes the template syntax survive.
- **`<script>` and `<style>` bodies are dropped whole**, not scanned. Both carry strings a translation has to rewrite, and a `<` in a script is arithmetic (`i < 3`) or an HTML string being assigned to `innerHTML` — read as a tag, it swallowed everything up to the next `>` and made two genuinely identical pages differ. The cost, stated plainly: markup a script writes is invisible to the check. A missing `<script>` block is still caught, because its tags are.
- **A language tag is exactly two letters** plus an optional region. Three letters are real ISO 639-3 codes, but allowing them makes `app.min.html` read as a translation into Minangkabau and fail the build for a reason nobody would guess. Telegram's own `language_code` is two letters either way.
- **Only the first differing element is reported.** Everything after it is usually the same mistake echoing.

Verified by driving the real pages in headless Chrome at 320, 360 and 390px and measuring every width-bound row — the fee tiers, the Blockchain grid, the Market percentages and the tab bar — in all three languages: **nothing overflows at 360 or 390 in any of them**. At 320 the Market row overflows by 15px *identically in English*, which is the pre-existing case the `max-width: 359px` rule narrows the gaps for; the forced-width probe cannot trigger that media query, so that number says nothing about the translations.

**Rendering fees into `/` makes them public**, because `/` cannot be authenticated — Telegram passes `initData` in the URL *fragment*, which is never sent to the server, so there is nothing to verify on the initial load. That is acceptable only because fee estimates are public network data. Anything per-user (a chat's watches) must **not** be rendered into the page; it belongs behind `/fees`-style endpoints that `requireInitData` protects.

**`initData` validation** (`isValid`) is what stands between this server and anyone who knows the URL. Telegram signs the payload it hands the webview; the page forwards it on every HTMX request as `X-Telegram-Init-Data` (attached via an `htmx:configRequest` listener registered on `document` — not `body`, which does not exist yet in `head` — so the very first request already carries it), and `requireInitData` rejects anything unsigned, tampered, or stale with a 401.

The scheme, which is easy to get subtly wrong:
- secret = `HMAC-SHA256(key: "WebAppData", msg: bot token)` — **not** the Login Widget's `SHA256(token)`; the two look interchangeable and are not
- the signature covers every field except `hash`, sorted by key, joined with newlines
- compare with `hmac.Equal`, never `==`
- `auth_date` must be within `initDataTTL` (24h, a var for tests): a signature is otherwise valid forever, so a payload lifted from a log or a shared link would keep working

`initDataUnsafe` must never be trusted. The shell page at `/` is deliberately *not* behind the check — it carries no data, and the webview must load it before any script can read `initData` at all. Outside Telegram there is no `initData`, so the page says so instead of firing a request guaranteed to 401.

Tests cover the parts that matter: a payload signed with a different token, a tampered `user` field, and a 48h-old `auth_date` are each rejected, and a valid one renders the fragment. The signature was additionally cross-checked against an independent Python implementation, and against the real bot token on the Pi.

### Command dispatch and the "pending argument" pattern

`update()` in `main.go` is the single entry point for every incoming Telegram update: pull `Update.Message`, log it (`logMessage`), split it into a command and argument (`parseCommand`), then switch on the command. `/start`, `/watches`, `/fees`, `/mempool`, `/miners` (see Miner statistics) and `/market` (see The /market command) take no argument and act immediately (`/start` sends a fixed `<b>`-formatted bulleted help listing the commands; `/watches` (`watchesCmd`, renamed off the `watches` package) lists the calling chat's watches — Addresses from `watches.List()` filtered by `chatID`, Transactions from `txwatches.For(chatID)` — and prints each id **un-shortened** inside `<code>…</code>` for Telegram tap-to-copy; ids are `html.EscapeString`'d because address watch ids are arbitrary unvalidated user input, unlike txids).

`/fees` (`fees()`) replies with five fee tiers — Fastest (10-20 min), Half hour, Hour, Economy, Minimum — each in sat/vB with the USD cost of a typical transaction beside it, rendered in an aligned `<pre>` table. Labels deliberately avoid `<`/`>`/`&` so the fixed text needs no HTML-escaping and the `len()`-based padding matches the rendered width.

**It does not use Core's `estimatesmartfee`** — see `fees.go`, which ports mempool.space's algorithm instead. The two answer different questions: Core's estimator is *backward-looking* (how long did transactions at each rate historically take to confirm), deliberately conservative and slow to react, so during a fee spike it keeps quoting yesterday's cheap rates while the transaction sticks. mempool.space is *forward-looking* — it packs the mempool as it stands into the blocks a miner would actually build and reports what those blocks are paying. Measured against the live mainnet node, Core said **1.07 sat/vB** for the next block while the ported algorithm and mempool.space both said **4.00**.

Two stages, ported from mempool.space's `api/mempool-blocks.ts`, `api/common.ts` and `api/fee-api.ts`. First `buildProjectedBlocks` sorts the mempool by effective fee rate and packs it into 4M-weight-unit blocks, then `medianFeeOf` takes each block's "median fee" — which is **not** the median transaction's rate but the weight-weighted average of the middle 0.25% of the block's weight. Then `calculateRecommendedFee` turns the first blocks' medians into tiers, blending each with the tier above it, flooring everything at the node's own `mempoolminfee` purge rate, and enforcing that the tiers never invert.

Two things about that median are counter-intuitive and were both got wrong once before being checked: a block's **unused space counts as its cheapest part**, so a half-full block samples the *cheap* end of its transactions rather than their middle (correctly — you barely need to outbid anything to enter a block that isn't full); and `optimizeMedianFee` returns the floor outright for any block under half full, since that is not evidence of congestion.

The one deliberate approximation is CPFP: mempool.space runs a real getblocktemplate with cluster linearisation, while `effectiveRate` sorts by **ancestor** fee rate (`fees.ancestor / ancestorsize`), which is what Core's own miner maximises and is exactly equal for any transaction with no unconfirmed parents. It can misplace the interior of a long CPFP chain, but the recommendation reads the middle of each block by weight, so a few misplaced members don't move it.

**Verified two ways.** `TestRecommendationMatchesMempoolSpace` replays projected blocks captured from their own `/api/v1/fees/mempool-blocks` through the port and reproduces the recommendation they published at that moment exactly. And against the live node, the full pipeline (36 552 mempool transactions, fetched in ~1s, projected and computed in **3 ms**) matched mempool.space on **all five tiers**. `core == nil` gives the same "not configured" message as `/info`; a mempool read failure degrades to a short note rather than a wrong number.

`/mempool` (`mempoolCmd()`) replies with the mempool's size and transaction count — both cheap from `getmempoolinfo`, rendered with a metric suffix via `metric(f, 1)` ("3.2 M", "6.7 k") — and, when the mempool is small enough to summarize in reasonable time, the summed output **amount** and summed **fees** across every mempool transaction, each in BTC and USD via `btcAmount` (these totals reach thousands of BTC / billions of sats, so BTC not sats; ≥1 BTC shows 2 decimals, a fraction keeps satoshi precision so fees don't round to "0.06"). `metric` is the shared metric-suffix helper `formatBlock`'s difficulty now also routes through. It also shows a `Flow rate` — transactions/sec flowing into the mempool and how that rate is changing (`2.5 tx/sec (+0.5)`): `startMempoolFlow` (from `main()`) polls `getmempoolinfo` every `flowInterval` (10s, var) and feeds each tx count to `updateFlow`, which keeps `flowRate` = Δcount ÷ interval and `flowChange` = Δrate **in memory only** (`flowMu`, never persisted; the goroutine isn't stopped on shutdown, like the rates updater). The rate is **recomputed only when the count rose** — a drop (`delta ≤ 0`) most likely means a block was just mined, which would skew the inflow measurement, so the previous rate/change is kept; the count is still re-baselined so the next rise spans one clean interval. The rate needs 2 samples and the change 3, so both fields are omitted until warm — and the flow line shows even when the totals are skipped, since it's already computed in the background rather than per-command. `mempoolTotals` reads the fees straight from `rawMempoolVerbose` (one `getrawmempool true` call, which also yields the txid list; Core nests each entry's fee under `fees.base`, where btcd had a flat `fee`) and computes the amount by fetching every transaction's outputs **concurrently** (bounded `sem` of 16); individual tx churn between the two passes is tolerated (skipped), but a context timeout returns `ok=false` → `Totals: unavailable`. The totals are gated by `mempoolSummaryLimit` (var, default 20000 txs) — above it the reply shows `Totals: skipped (mempool too large)`, since both the verbose fetch and the per-tx fetches scale with the tx count. Measured on the real node: at ~8500 txs the whole thing is ~4s (verbose ~3s + per-tx amount ~1s); getmempoolinfo alone is ~6ms. The `Total amount` is the sum of all outputs, so it's inflated by change — not "value being transferred".

Commands that take a free-text argument (`/info`, `/watch`, `/unwatch`) share one shape: called with an argument (`/info foo`) they act immediately; called bare (`/info`) they reply asking the user to send the text as a follow-up message and mark that chat "pending" for that command. The next plain-text (non-command) message from a pending chat is then treated as the missing argument.

Pending state is tracked per command with its own package-level `sync.Mutex` + `map[int64]bool` (`pendingInfoMu`/`pendingInfoChats`, `pendingWatchMu`/`pendingWatchChats`, `pendingUnwatchMu`/`pendingUnwatchChats`) — there is no shared/generic pending mechanism, and that's intentional: an earlier pass had the opportunity to unify this and deliberately kept it duplicated per command. Follow that precedent for any new argument-taking command rather than generalizing. `update()`'s `case ""` checks the pending maps in order (info, watch, unwatch), each `return`ing after it handles the follow-up.

All three are implemented the same way, short handler names (`info`, `watchCmd`, `unwatch`) with no wrapper functions around their pending-state maps: the lock/set-or-delete/unlock logic is inlined directly into `info()`/`watchCmd()`/`unwatch()` (setting pending) and into `update()`'s `case ""` (checking and clearing pending). There was an earlier pass where `/info` kept named helper functions (`setPendingInfo`, `takePendingInfo`, `clearPendingInfo`) while `/watch` was already inlined — that asymmetry was deliberately removed by request, so treat the current inlined-everywhere shape as the pattern to extend, not something to re-wrap in helpers.

### The database UI

`dbui/` is a small web interface for inspecting and hand-editing the bbolt file, off by default and started only when `-dbui-listen` is set (e.g. `127.0.0.1:8090`). **It can write any bucket, so it must bind to localhost** — the flag help says so. `main()` calls `dbui.Start(db, addr)` right after `openDB` (it needs the handle) and holds the returned `*http.Server` so `shutdown` can drain it **before** `closeDB`, the same ordering the webhook server uses — a request mid-flight against a closed handle would otherwise error.

The page (embedded via `//go:embed index.html`, so the binary stays self-contained) is three groups of controls above two centred tabs — **Create**, the bucket dropdown and **View**; a prefix field and **Scan**; a key field and **Get**. The grouping is done with spacing alone: `.controls` has a 22px gap and each `.group` a 6px one, so what belongs together reads together without a border or a label. View loads a paginated key/value table into the **Data** tab; Get loads one key's value into an editable textarea in the **Value** tab, and **Put** writes it back. Clicking a Data row fills the key field and the Value textarea and jumps to the Value tab, which is the edit-in-place flow. Each row also carries a **trash icon left of its key** that deletes that key immediately — no confirmation, since this is a local admin tool and a dialog per row would make clearing a bucket unusable. Its handler calls `stopPropagation`, or the click would bubble to the row and open the editor instead; the table then reloads so the pagination flags stay honest. The icon is an inline `<svg>` in a `<template>`, so the page still fetches nothing external. Nine JSON endpoints back it: `/api/buckets`, `/api/view`, `/api/get`, `/api/put`, `/api/delete`, `/api/createbucket`, `/api/clearbucket`, `/api/export` and `/api/import`.

**Create** opens a dialog — a name field and Create/Cancel, the same `.dialog-overlay` the CSV import uses — and `/api/createbucket` reports a name that is already taken as an error rather than a no-op, since bbolt's `CreateBucket` does and a Create that silently did nothing would look like it had worked. The list reloads on success with the new bucket selected.

**Export and import stream**, and neither side ever holds the table. `/api/export` writes CSV straight into the response — the browser saves it through `Content-Disposition`, so the page is not involved at all — and `/api/import` takes the bucket and the strategy as **query** parameters precisely so the body can be the file itself, which `fetch` is handed as a `File` and streams. The client-side `csvEscape`, `parseCSV` and `FileReader` are gone with them.

Four things that shape it:

- **Export sets its headers only after the bucket is known to exist.** Past the first byte there is no status line left to change, so a failure partway can only be logged and the reader gets a truncated file; the alternative is reading the bucket twice to be able to say 500 about a failure nothing recovers from anyway.
- **A bucket name reaches a quoted header value**, and buckets can now be created here under any name, so `filename()` maps anything outside `[A-Za-z0-9._-]` to `_` — a quote would otherwise end the string.
- **Import writes in batches of `importBatch` (1000), so it is not one transaction.** Same trade `tools/csvimport` makes, safe for the same reason: every row is written by key, so an import that fails partway is recovered by running it again. Holding the whole file in one write transaction would put the memory back that streaming just removed.
- **A header row is only skipped when it is the first record** and reads `key,value` (either case), so a file without one is data from its first line.

Measured against the real 120 119-row `active` bucket: the export is **5.5 MB in 57 ms**, and throttled to 300 KB/s the first byte arrives after **1.2 ms** of an 18.4-second download, with the server's RSS flat throughout — it cannot have buffered. Importing that file back took 1.14 s and reproduced the bucket exactly, all 120 119 keys with no differing values.

**Scan** lists the keys under a prefix instead of the whole bucket. The prefix goes through `decodeField` like every other key here, so `hex:000000000000000a` scans a binary-keyed bucket; the listing is a `Seek` to the prefix rather than a walk from the start, and paging stays inside it — `hasNext` must not point at the first key past the prefix, which is what `TestViewPrefix` pins. Which mode the table is in is *not* read from the field: `View` clears it and `Scan` sets it, so Prev/Next stay where they were put and typing changes nothing until Scan is pressed. The page label says `page 1 · prefix "…"`, because a prefix matching nothing otherwise looks like an empty bucket. `tools/bboltwui` runs the same UI as a standalone process against any bbolt file — see its README. It takes bbolt's exclusive lock, so against a running bot it waits for the lock rather than failing, printing nothing at all; run it on a stopped bot or a `-backup` copy.

There was also a **Buckets** tab listing every bucket's key count and size from bbolt's own `Bucket.Stats()`, backed by `/api/bucketstats`; it has been removed along with its handler. Note the surviving `/api/buckets` is a different endpoint — it returns just the bucket *names* that fill the dropdown, and the page cannot work without it.

The one non-obvious piece is binary handling. Most buckets hold JSON or text (miner names, tags) and display directly, but keys and values are also binary in places — big-endian heights in `blocks`/`rates`/`market`, the packed `addrindex`. `encodeField`/`decodeField` render those behind a `hex:` marker and decode a `hex:`-prefixed input back to bytes, so a Put round-trips binary rather than corrupting it (the marker can't collide — no bucket stores a text value beginning `hex:`). Pagination is offset-based (`page*size` skipped on the cursor), which is fine for the small buckets and acceptable for deep pages of `addrindex` that nobody scrolls to. `dbui_test.go` covers the round trips, pagination, the 404s, deletion (including a `hex:` binary key), and the binary encoding; the UI itself was driven in a real browser against a seeded database (View, row-click, edit, Put and delete — each confirmed against the database afterwards — plus the `hex:` display and dark mode).

## Style conventions specific to this repo

These diverge from typical idiomatic Go on purpose (established through explicit instruction over this repo's history) — don't "clean them up":
- Indent with 4 spaces, never tabs — this includes running `gofmt`/`goimports` with a post-process step (or an editor setting) to expand tabs, since Go's own tooling always indents with tabs by default.
- Prefer unexported identifiers even for the main API (`bot`/`newBot`/`send`, not `Bot`/`NewBot`/`SendMessage`) — nothing outside `package main` consumes this code.
- One `import "x"` line per import, never a grouped `import (...)` block.
- `var x = expr()` instead of `x := expr()` wherever Go's grammar allows it. It doesn't allow `var` in an `if`/`for` initializer, and a `var` can't redeclare a name already in scope the way `:=` can (e.g. `req, err := ...` when `err` already exists) — those cases keep `:=`.
- No blank lines inside function bodies; blank lines appear only between top-level declarations.
- Minimal comments: none explaining *what* code does, only rare ones for non-obvious *why*.
- Single-line `if err != nil { return nil, err }` where it fits on one line.
- Avoid introducing a helper function for logic used at only one call site — inline it instead. This is about small pieces of logic, not decomposition: a handler that has grown genuinely large may be split (`info()` was deliberately split into `transaction`/`block`/`address` by explicit request).

## Testing approach

Tests never hit real Telegram or a real `telegram-bot-api` proxy. They live beside the code they cover — `flow_test.go` (command dispatch), `watch_test.go` and `zmq_test.go` (the notifier and the local matcher), `menu_test.go`, `market_test.go`, `fees_test.go`, `buttons_test.go`, `addrstats_test.go`, `blocks_test.go`, `core_test.go`, `db_test.go`, `format_test.go`, `backup_test.go`, `log_test.go` and `shutdown_test.go`, plus each package's own (`addrindex/`, `app/`, `dbui/`, `lru/`, `miners/`, `rates/`, `txwatches/`, `watches/`). They spin up an `httptest.Server` standing in for the Bot API, build a `bot` pointed at it (`newBot("TESTTOKEN", server.URL)`), and drive behavior by calling `update()` directly with hand-built `Update` values — then assert on the outgoing `sendMessage` request bodies the fake server captured (and, in `log_test.go`, on `log` package output captured via `log.SetOutput`). Bitcoin Core is faked the same way: `newFakeCoreServer` (in `core_test.go`) is an `httptest.Server` answering JSON-RPC over plain HTTP, checking basic auth and reporting method errors in the body with HTTP 500 the way Core does. It is much smaller than the btcd fake it replaced — no websocket upgrade, no connection to keep alive, and no server-pushed notifications, because Core has none: tests drive notifications by calling `broadcast`/`processConfirms` directly, which is exactly what `zmq.go` does with a ZMQ frame.

Any test that exercises `/watch`, `/unwatch`, or the notifier must open the database first (`openDB(filepath.Join(t.TempDir(), "watches.db"))` + `defer closeDB()`) — `openDB` also hands the handle to `rates.Init`/`watches.Init`/`miners.Init`/`addrindex.Init`, so their package globals are unusable (nil db → panic) until it runs — and should reset the notification state (`stopNotify`, which also `txwatches.Reset()`s the confirmation map), the local script/outpoint matcher (`resetWatched`) and `core` for isolation, since these are package-global and shared across tests, which run sequentially. The `app` package has the same hazard in its rendered-card caches, so its `handler()` test helper calls `resetCache()` — without it a test would be served the previous test's fixture. The storage packages have their own tests: `watches/watches_test.go` and `rates/rates_test.go` open a temp bbolt file via `Init`, and `txwatches/txwatches_test.go` exercises the in-memory map directly; the price-display tests (`usd`/`amountLine`) live in `format_test.go` in `package main` and seed a rate through `rates.Add`. `TestMessageLogging` redirects the global logger with `log.SetOutput(&buf)` and **must restore it with `defer log.SetOutput(os.Stderr)`, not `log.SetOutput(nil)`** — a nil writer makes every later `log.Printf` (e.g. `logMessage` in any subsequent `update()`-driven test) panic. That was a latent bug that only surfaced once a logging-path test was ordered after it.

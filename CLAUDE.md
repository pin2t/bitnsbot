# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

bitnsbot is a Bitcoin network events notification bot for Telegram. It talks to a **Bitcoin Core** node (it used to target btcd — see The Bitcoin Core client below for what that change cost and bought). It's a single Go binary built almost entirely on the standard library — the exceptions are `go.etcd.io/bbolt` (the embedded KV store holding watches, the block cache, rates, miner stats and the address index) `github.com/go-zeromq/zmq4` (pure Go, no cgo — Core publishes its notifications over ZeroMQ and the standard library has no ZMTP implementation), and `github.com/pin2t/flagex` (the `-config` properties-file parser — see The config file below). Core's RPC is plain HTTP, so it needs nothing beyond `net/http`. It receives updates via a Telegram webhook (not long polling). Alongside the bot, `tools/` holds small standalone commands in the same module (see Tools below).

## Commands

- Build: `go build ./...`
- Run: `go run . -bot-token <token> -webhook-url http://localhost:8080/bot -api-base-url http://localhost:8081`
- Test all: `go test ./...`
- Test one: `go test -run TestWatchFlow -v` (other tests: `TestInfoFlow`, `TestUnwatchFlow`, `TestWatchesFlow`, `TestWatchNotification`, `TestShutdown*`, `TestMessageLogging`, `TestLoggingLevels`, `TestWatchStore*`, `TestRate*`, `TestUSDFormat`, `TestAmountLineUSD`, `TestCore*`, `TestParseTx*`, `TestAddrIndex*`, `TestMenu*`, `TestMarket*`, `TestButtons*`, `TestAddrStats*`). Run the whole suite with `-race` (`go test -race ./...`) — the watch-notification path is concurrent.
- i18n check: `go build -o /tmp/i18n-vet ./tools/i18n-vet/ && /tmp/i18n-vet .` (see Internationalisation below)
- Vet: `go vet ./...`

There is no Makefile or linter config in this repo — `go build`/`go vet`/`go test` plus `i18n-vet` are the only checks available, and are exactly what `.github/workflows/ci.yml` runs on every pull request (on Go 1.26, with `-race -coverprofile`). **`i18n-vet` runs in CI**, so a new translated string with no translation fails the build. `gofmt -l .` will flag files as unformatted by design; see Style below before "fixing" that.

Flags (all in `main.go`): `-config` (path to a `name=value` properties file to load flag values from — see The config file below), `-verbose` (log level 0/1/2 — see Logging below), `-bot-token` (Telegram bot token, required), `-listen` (address this bot's webhook server binds to), `-webhook-path`, `-webhook-url` (the URL registered via `setWebhook`), `-api-base-url` (Bot API server to call), `-secret-token` (optional), `-register-webhook` (set false to skip calling `setWebhook` on startup), `-db` (path to the bbolt watches database, default `watches.db`), `-core-url`/`-core-user`/`-core-pass`/`-core-cookie` (Bitcoin Core's JSON-RPC endpoint and credentials — either user/pass or the `.cookie` file Core writes into its data directory; leaving `-core-url` empty skips connecting to the node entirely), `-core-zmq` (comma-separated ZMQ endpoints publishing `hashblock` and `rawtx` — see The ZMQ notification path below), `-core-rest` (base URL of Core's REST interface, which the address index builds from; empty disables indexing), `-backup`/`-backup-interval`/`-backup-script` (periodic database copies; empty `-backup` disables them — see Database backups below), `-log-no-ts` (omit the date/time prefix from each log line, for journald which timestamps them itself), `-dbui-listen` (address for the database admin web UI, empty disables it — see The database UI below), `-history-file` (path to a JSON file of historical BTC/USD rates in blockchain.info's chart format, so the rates backfill can load from disk instead of the network).

## Deployment (scripts/)

`scripts/` holds the Raspberry Pi / systemd continuous-deployment helpers (`install.sh`, `update.sh`, `uninstall.sh`, `README.md`) — not part of the Go build. The runtime package is self-contained under `/opt/bitnsbot` (`bitnsbot` binary, `bitnsbot.conf`, `bitnsbot.db`); the source checkout stays where cloned (default `/home/pi/bitnsbot`). `install.sh` (run as root) builds+tests **as the checkout's owner** (via `runuser`, non-login shell with explicit `HOME`/`PATH` so `go` is found and captured git output stays clean), installs the binary, writes a systemd unit ordered `After=bitcoind.service` (running as that user), and schedules `/etc/cron.d/bitnsbot` to run `update.sh` every 5 minutes. `update.sh` fetches `origin/master` and acts **only when it is strictly ahead** of the deployed `HEAD` (checked with `git merge-base --is-ancestor` — a plain `HEAD != origin/master` would rebuild-loop whenever the local checkout is ahead); it fast-forwards, rebuilds, runs the full suite, and only on success atomically swaps the binary and restarts — a `flock` prevents overlapping runs. See `scripts/README.md`. The config template it writes is Bitcoin Core-shaped (`core-url`, `core-cookie`, `core-zmq`, `core-rest`) — worth keeping in step with the flag set, since the `-config` parser treats an unknown name as fatal, so a stale template breaks startup rather than degrading. These are validated with `bash -n`, by exercising the git decision logic against throwaway repos, and by booting the emitted template against a real node — every key checked against the binary's actual flags, cookie auth exercised, and a mined block confirmed arriving over ZMQ. The systemd/cron paths can only be verified on the target host.

## Tools (tools/)

`tools/` holds standalone command-line programs that ship with the repo but are no part of the bot: each subdirectory is its own `package main`, so `go build ./...` builds them alongside the bot and `go test ./...` runs their tests.

- `advertise` — announces a Bitcoin node's address to btcd's known peers over the P2P protocol (detailed below).
- `addresses` — scans the chain from genesis to tip and collects every address seen, resuming from its own cursor bucket.
- `top-active` — the same scan, ranking addresses by activity.
- `addrindex-scan` — looks one address up in the `addrindex` and prints what the index holds for it; the direct way to check the index without going through the bot.
- `dbui` — runs the database admin web UI (the `dbui` package) as its own process, so the database can be inspected without the bot running.
- `i18n-vet` — the translation checker CI runs; see Internationalisation below.

`tools/advertise` announces a Bitcoin node's address to the peers btcd already knows. It reads btcd's `peers.json` (the addrmanager dump: `{"Addresses":[{"Addr":"1.2.3.4:8333","LastSuccess":…}, …]}`), and for every **IPv4** peer performs the P2P version/verack handshake and sends a one-entry `addr` message — which is exactly how a node's address spreads through the gossip layer. Flags: `-peers`, `-advertise` (default `178.46.128.227:8333`), `-workers` (64), `-timeout` (10s), `-limit`, `-live`, `-verbose`. IPv6 and `.onion` entries are skipped: those need a working IPv6 route and a Tor proxy respectively.

The wire format is **hand-rolled on the standard library** rather than importing btcd's `wire` package — the whole job is three message types, against a dependency that would pull in a full node's stack. Only what the handshake and the announcement need is implemented, deliberately: `version`, `verack` and `addr`, and nothing else. `message()` builds the envelope (magic, 12-byte null-padded command, length, and the first four bytes of the double SHA-256 as checksum), and `versionPayload`/`addrPayload` build the two payloads out of the shared 26-byte `netAddress` (services, IPv4-mapped IP, port in network order). The two varint-prefixed fields — the user agent's length and the address count — are written as **plain single bytes**, because the multi-byte varint forms start at 0xfd and neither value can reach it; an earlier version carried a general four-branch varint encoder whose other three branches were unreachable. Incoming messages are read only far enough to see the command: `announce` reacts to `version` and `verack` and ignores everything else (`sendaddrv2`, `wtxidrelay`, `sendheaders`, …) without parsing a single payload, and peer checksums are not verified since nothing is decoded. Our version claims **no services and relay=0**, so a peer doesn't start streaming transactions down a connection about to be closed; the advertised address claims NODE_NETWORK|NODE_WITNESS, which is what makes peers keep and relay it. `TestMessageEnvelope` pins the envelope against the canonical empty-`verack` vector (`f9beb4d9…5df6e0e2`), `TestVersionPayload`/`TestAddrPayload` pin the two hand-written payload layouts (including those single-byte length prefixes), and `TestAnnounce` drives the whole exchange against a fake peer that speaks the protocol — including junk (`sendaddrv2`) before its verack, which must be ignored.

**Most of `peers.json` is dead weight**, which is worth knowing before running it: in a real 7.7 MB file of 34288 addresses, 23276 were IPv4, but only **4016 had ever been dialled by btcd and only 463 ever answered** — the rest is unverified gossip. A first run against the file's leading entries reached **0 of 20** peers, all failing at `dial`. `-live` keeps only addresses with a real `LastSuccess`, and over those the same run reached **14 of 25**. So default (all peers) is what the tool was asked for, but `-live` is the flag to use when you want it to finish quickly.

Verified against the live network: 7 of 7 selected peers completed the handshake and took the `addr`, including this repo's own btcd node at its P2P port. A throwaway probe then sent `getaddr` immediately after the `addr` and got healthy `addr` replies back (30003 bytes from the local node — 1000 addresses), confirming peers do not treat the message as malformed and drop the connection.

## Runtime model

The bot is designed to run behind a self-hosted `telegram-bot-api` proxy (https://github.com/tdlib/telegram-bot-api) on localhost, not directly against `https://api.telegram.org`:
- `-api-base-url` defaults to `http://localhost:8081`; `telegram.go`'s `bot.call` builds every outgoing request URL from it.
- The webhook HTTP server is a plain `*http.Server` (via `srv.ListenAndServe` in a goroutine) — no TLS. The local proxy is assumed to own the real HTTPS conversation with Telegram; the hop from proxy to this bot is local/plaintext.
- **Graceful shutdown**: `main()` uses `signal.NotifyContext(…, os.Interrupt, syscall.SIGTERM)` and blocks on the returned context; on SIGINT/SIGTERM it calls `shutdown(srv)`, which tears down **in dependency order — webhook server first, then the store**. That order is load-bearing: `srv.Shutdown` blocks until in-flight webhook handlers drain, and those handlers use the watches database, so closing the server first guarantees no handler is mid-request when the database it depends on is closed. (Core needs no teardown at all: its client is stateless HTTP. Under btcd this step also closed a websocket.) After the first signal `stop()` is called to restore default handling, so a second Ctrl+C during a slow drain force-kills. (Note: the old `defer closeDB()` was dead code — `http.ListenAndServe` blocked forever and only ever returned into a `log.Fatal`, i.e. `os.Exit`, which never runs defers; this feature is the first real cleanup path.)
- Two secrets, both flags: `-bot-token` (required) authenticates outbound Bot API calls. `-secret-token` (optional) is passed to `setWebhook` and then checked against the `X-Telegram-Bot-Api-Secret-Token` header on every incoming request (constant-time compare in `main.go`'s webhook handler) — this is the only thing stopping an arbitrary POST to the webhook path from being treated as a real Telegram update. Since both are flags they can be supplied via the `-config` file; prefer that over the command line for real deployments, since command-line args are visible to other users via `ps`.

## Architecture

The bot lives in `package main` in the repo root; five supporting packages sit in subdirectories (`logging/`, `rates/`, `watches/`, `txwatches/`, `miners/`), each with a small simplified API and its own unexported types. Cross-cutting state that used to be package-`main` globals with compound names (`storeRate`/`lastRate`, `addWatch`/`listWatches`, `addTxWatch`/`txWatches`) now reads as `rates.Add`/`rates.Last`, `watches.Add`/`watches.List`, `txwatches.Add`, etc.

Root (`package main`):
- `telegram.go` — the Bot API client: the unexported `bot` type, `newBot`, and `call`/`send`/`setWebhook` methods, plus the wire types (`Update`, `Message`, `User`, `Chat`) decoded from incoming webhook JSON.
- `db.go` — the bbolt connection: the package-level `var db *bbolt.DB`, `openDB(path)`/`closeDB()`, and the shared `itob` big-endian key helper. `openDB` opens the one file, creates the `blocks` bucket, and hands the same handle to `rates.Init`/`watches.Init`/`miners.Init`/`addrindex.Init` (which own their own buckets) — one file, one handle, **eleven** buckets (`blocks-stat`/`blocks-cursor`, `rates`, `watches`, the rates package's `market`, the miners package's `miners`/`miners-tag`/`miners-stat`/`miners-cursor`, and the addrindex package's `addrindex`/`addrindex-cursor`).
- `core.go` — a `coreConn` for talking to Bitcoin Core's HTTP JSON-RPC API (see below).
- `zmq.go` — the ZMQ subscriber, the local transaction parser, and the watched-script/outpoint matcher that replaces btcd's server-side filter (see below).
- `blocks.go` — the `blocks` bucket: cached per-block info records (`blockInfo`), `computeBlockInfo` (builds a record from Core), the startup backfill goroutine, and `formatBlock` (the `/info` block reply). See Block info cache below.
- `backup.go` — the periodic database backup goroutine (`startBackup`/`backup`). See Database backups below.
- `dbui/` — the localhost database admin web UI (`Start`, plus the list/get/put HTTP handlers and one embedded HTML page). See The database UI below.
- `i18n.go` — the translation tables and the per-chat language lookup (`trans`, `langTrans`, `SetChatLanguage`, `i18n`). See Internationalisation below.
- `lru.go` — `lruCache`, a small generic LRU used to bound the chat→language map.
- `addrindex_source.go` — `restSource`, which builds `addrindex.Block` values from Core's REST interface (see Address indexing).
- `main.go` — flags, the HTTP webhook server, command dispatch (`update`), the `/watch`/`/unwatch`/`/watches` (`watchesCmd`)/`/fees`/`/mempool`/`/miners` handlers, and the mempool flow-rate tracker.
- `notify.go` — the address-watch notification infrastructure (`notification`/`notifyKey`/`notifyChans`, the `notifies` fan-out map, `startNotifyChat`/`stopNotifyChat`/`notifyAddresses`, `broadcast`, `confEstimate`, `startNotify`/`stopNotify`), plus the `watchType` type and `processConfirms` (which formats+sends the transaction-confirmation messages using the `txwatches` package). See Watch notifications below.
- `info.go` — the `/info` command: `info` and its per-kind `transaction`/`block`/`address` handlers plus their helpers (`txInputs`/`fetchInputs`, `blockFeeStats`, `addressHistory`/`addressStats`, `compactAddrs`, …) and the `/info` pending-argument state (see The /info lookup below).
- `format.go` — the shared display formatters `when`/`ago`/`short`/`group`/`sats`/`metric`/`compactBTC`/`timeCompact`/`periodText`/`durationText`, plus `usd`/`amountLine`/`btcAmount` (which read current prices from the `rates` package).

Packages:
- `logging/` — the leveled helpers `Err`/`Warn`/`Status`/`Fatal`/`Info`/`Net`/`Db` and the verbosity gate (`SetVerbosity`, called once from `main`). Everything in every package logs through these (see Logging below).
- `rates/` — BTC/USD exchange-rate history and the 5-minute averaging updater. Public API: `Init(db)`, `Start()`, `Add(usd)`, `Last() (float64, bool)`, `At(t) (float64, bool)` — prices go in and out as plain USD `float64`; the `rateRecord` type is unexported (see Exchange rates below).
- `watches/` — the **address**-watch bbolt store. Public API: `Init(db)`, `Add(chatID, address, alias)`, `Remove(chatID, address) (int, error)`, `List() ([]Watch, error)`, where `Watch{ChatID, Address, Alias}` is the public view and the internal `watchRecord` is not exposed. Only address watches are persisted — transaction watches live in `txwatches`. See The watches store below.
- `txwatches/` — the in-memory one-shot confirmation-watch list (never persisted). Public API: `Add`/`AddAddrConfirm` (register, deduped by chat+addr), `Remove`/`For` (direct `/watch <txid>` entries only), `RemoveAddrConfirms`, `Confirms(txids) []Confirmed` (removes+returns the watches whose txid is in a new block, for the caller to message), `Any`, `Reset`. See Watch notifications below.
- `miners/` — mining-pool attribution and per-miner statistics, DB-backed (`miners` maps coinbase-output address → pool name, `miners-tag` coinbase tag → pool name, `miners-stat` pool name → aggregate, `miners-cursor` the collector's cursor). Public API: `Init(db)`, `Start()` (background definitions refresher), `Name(address) string` (address key lookup, "" when unknown), `Attribute(addresses, coinbaseHex) string` (address then tag, "" when unknown), `StartStats(Source)` (the statistics collector) and `Top(n) []Stat`. `miners.go` holds attribution, `stats.go` the collector. See Block info cache and Miner statistics below.

### Amounts are satoshi

**Every Bitcoin amount and every fee inside the bot is an `int64` of whole satoshi.** `float64` survives in exactly three places, and nowhere else:

1. **The parse structs** in `core.go` and `rates/`, because BTC-as-a-JSON-number is what the wire format is. Nothing downstream keeps it: values are converted on the way in.
2. **Quantities that are genuinely fractional** — fee *rates* in sat/vB (`fees.go`, `notify.go`'s `feeRate`), block difficulty, the miners package's `Work`/`LastWork`/`ConsumptionGW`, mempool flow in tx/sec, and every USD figure (`usd`, `price`, `money`, `change`, the `rates` package).
3. **The final formatting step**, via `toBTC`, when a number is about to be printed with decimals.

`toSat(btc float64) int64` is the one boundary between the two, and `toBTC(sat int64) float64` converts back **for display only, never for arithmetic**. `toBTC` is exact for every real amount: the 21M-coin supply is 2.1e15 satoshi, well inside float64's 2^53 integer range.

The reason is accumulation, not representation. 0.1 BTC has no exact float64 value, so summing outputs, inputs and fees drifts — which is why `addrstats_test.go` used to assert a *range* (`balance > 0.0998 && balance < 0.1`) where it now asserts the exact `9990000`. Integer satoshi is also what the protocol actually uses; BTC is only ever a display unit.

Two things to know when changing this:

- **`feeStats` rounds its average deliberately** — `(total + count/2) / count`, not plain integer division. It used to be `math.Round` of a float mean, and truncating instead would shift the displayed average down by up to a satoshi.
- **The persisted records changed type but kept their JSON keys.** `blockInfo`'s `minFee`/`avgFee`/`maxFee`/`reward`/`total` and the miners package's `reward`/`fees` are now integers. Keeping the keys is what makes the change safe: a record written before this reads as `{"reward":6.25}`, which now **fails to decode** — and `loadBlock` already treats a decode failure as a cache miss and recomputes. Renaming the keys instead would have decoded cleanly to a silent **zero**. Deployment consequence: previously cached blocks are recomputed on demand rather than served from the cache, and miner aggregates restart from the collector's cursor.

### Logging

Everything logs through the `logging` package — never `fmt.Print*` or the `log` package directly. Its verbosity is set once from `-verbose` via `logging.SetVerbosity(*verbose)` in `main()` (after the `-config` file is parsed, so it's also `-config`-settable), which gates emission:
- `logging.Err`/`logging.Warn` and `logging.Status` (lifecycle lines: "listening on …", "shutting down", "connected to Bitcoin Core …") always print — verbosity 0.
- `logging.Info` (verbosity ≥ 1): high-level events — an incoming message (`logMessage`), a reply sent (`send`), a subscription added/removed (`watchCmd`/`unwatch`).
- `logging.Net` and `logging.Db` (verbosity ≥ 2): raw external traffic and storage requests. NET is emitted from `telegram.go`'s `bot.call` (request method + body, response body) and the `rates` package's `fetch` (each price-API GET + response), plus `core.go`'s `call`, which logs each request method + body and the decoded result (the Authorization header is never logged). DB is emitted from each `rates`/`watches` storage function (and `openDB`).
- `logging.Fatal` is `logging.Err` + `os.Exit` for the startup fatals.

Two deliberate redactions in NET logging, both to avoid leaking secrets that a debug log would otherwise capture: the Telegram request URL (which embeds `-bot-token`) is never logged — only the method and JSON body — and the `setWebhook` body is omitted entirely because it carries `-secret-token`. Everything else (including sent message text and Core payloads) is logged verbatim at verbosity 2.

### The config file

`-config <path>` points at a plain `name=value` properties file whose names are flag names (`core-url=http://127.0.0.1:8332`, `listen=:8082`), read by **`flagex.ParseFile`** from `github.com/pin2t/flagex` and called from `main()` right after `flag.Parse()`. This used to be a local `applyConfig` in `config.go`; that file is gone, the logic having been extracted into the external package.

The semantics it provides are the same ones the local version had, and they still matter: values land in the same `*flag.Flag` variables the rest of the code reads (no separate config struct), blank lines and `#` comments are skipped, an unknown or malformed name is a **fatal** error rather than a silent skip, and command-line flags win over the file (precedence CLI > file > flag default). Because it is driven entirely by the flag set, every flag is automatically config-settable and adding a flag needs no per-flag wiring — which is also why a stale `scripts/` config template breaks startup outright instead of degrading.

### The Bitcoin Core client

`newCoreClient(coreConfig{url, user, pass, cookieFile})` builds an HTTP JSON-RPC client for Bitcoin Core. **Core has no websocket interface**, so unlike the btcd client this replaced there is no connection to dial, hold open, supervise or reconnect — every call is an independent `POST`. That deleted a whole subsystem: the `atomic.Pointer` connection swap, the `supervise` ping goroutine, `reapplyBtcdState`, and `close()` are all gone, and `shutdown` no longer has a node connection to tear down.

Authentication is HTTP Basic, from either `-core-user`/`-core-pass` or `-core-cookie`. The cookie file is re-read rather than cached forever because Core rewrites it with a fresh password on every restart and the bot outlives node restarts; a 401 triggers a re-read so the *next* call succeeds instead of failing forever.

Core speaks JSON-RPC 1.0 with positional (array) `params` and reports method errors **in the body with HTTP 500** — a non-200 status is therefore not on its own a failure, and `call` decodes the body either way.

Because there is no connection to fail at startup, `main()` makes one deliberate `getblockcount` right after building the client so a bad URL or bad credentials are loud and immediate rather than surfacing on the first user command. That failure is fatal, matching how the database's open failure is handled.

Wrapped methods: `getBlockCount`, `getBlockHash`, `getBlockHeader`, `getBlockTxids`, `getBlockVerbose`, `getRawTransaction`, `decodeRawTransaction`, `validateAddress`, `getMempoolInfo`, `getMempoolEntry`, `rawMempoolVerbose`, `estimateSmartFee`, `scanTxOutSet`, `waitForBlock`. Add more the same way: a thin method calling `c.call(ctx, "methodname", []interface{}{...}, &result)`.

**Differences from btcd that changed the code**, all verified against a real node rather than taken from documentation:

- **`getblock` verbosity 2 already reports each transaction's `fee`.** This deleted `blockFees` outright — its bounded 16-way prevout fan-out existed *only* because btcd made callers compute fees themselves. `blockFeeStats` now just reads the numbers Core supplies.
- **Core puts the full transactions under `tx`; btcd used `rawtx`.** The exact reverse of the old gotcha, so the `json:"rawtx"` tag is gone.
- **`getrawtransaction` verbosity 2 gives `fee` and per-input `prevout` — but only for *confirmed* transactions.** A mempool transaction has no undo data, so Core omits both. `txInputs` therefore has two paths: confirmed transactions read prevouts inline with no extra calls at all, while mempool ones still fetch each input's previous transaction (`fetchInputs`, the old bounded fan-out) and take the fee from `getmempoolentry`.
- **`validateaddress` returns the address's `scriptPubKey`.** This is what makes local transaction matching possible without the bot ever encoding or decoding an address format — see the ZMQ path below.
- **`estimatesmartfee` reports "no data" in-band**, as `{"errors":[…],"blocks":0}` with HTTP 200 and no RPC error, so `/fees` treats a missing/zero `feerate` as unavailable rather than waiting for a call to fail. It returns BTC/kvB, converted to sat/vB by ×1e5.
- **`getblock` verbosity 1 carries a `coinbase_tx` field** holding the coinbase *input* — so a block's miner tag is available without a second call. `minerSource` does not use it yet: it still fetches the coinbase transaction because it needs the payout addresses and total output, which that field does not carry.
- **Core has no address index at all** — nothing replaces btcd's `searchrawtransactions`. That is why `addrindex/` exists; see Address indexing below.
- **Core has no server-side transaction filter** — nothing replaces `loadtxfilter`. Matching moved into the bot; see the ZMQ path below.

### The ZMQ notification path

btcd pushed `blockconnected` and `relevanttxaccepted` down the same websocket that carried RPC. Core instead publishes over **ZeroMQ**, which needs no broker: Core `zmq_bind()`s and the subscriber dials in, point to point. `zmq.go` subscribes with `github.com/go-zeromq/zmq4` (pure Go, no cgo, verified interoperating with Core's libzmq).

`-core-zmq` takes a **comma-separated list** of endpoints, because Core publishes each topic on whatever address its own `-zmqpub*` option names — one port or several. A SUB socket dials them all, and subscribing to a topic an endpoint never publishes simply yields nothing. Messages arrive as three frames: `[topic][body][sequence number]`, the last a per-topic counter for detecting drops.

Two topics are consumed. `hashblock` replaces `blockconnected`, spawning `processBlock` and `processConfirms` exactly as the old handler did. `rawtx` replaces `relevanttxaccepted` — but with a crucial difference: **btcd filtered server-side and only pushed relevant transactions, while Core pushes every mempool transaction and the filtering is ours.**

That is why the bot keeps its own equivalent of btcd's filter, in `zmq.go`: a set of watched scriptPubKeys and a set of watched outpoints, both guarded by `watchedMu`. And it is why a ZMQ transaction is **parsed locally** by `parseTx` rather than sent to `decoderawtransaction`: on mainnet this path runs several times a second and almost nothing matches, so an RPC round trip per transaction would be pure waste. `parseTx` reads only what matching needs — the inputs' outpoints and the outputs' scripts — stopping before the witness and locktime it has no use for. Only on a match does the expensive path run (`broadcast`, which decodes over RPC and enriches).

Matching never decodes an address: a watched address becomes its scriptPubKey once via `validateaddress`, and outputs are compared as raw script bytes. Inputs match by outpoint, which is the only way a spend is visible at all — a spend names the outpoint it consumes, never the address. `recordOutpoints` extends that set whenever a watched address is paid, the bookkeeping btcd used to do inside its own filter.

`parseTx` is tested against real transactions captured from a node (a segwit spend, a three-output send, a coinbase) asserted against what Core itself reported, and was additionally run against the live mainnet mempool firehose: 40 transactions parsed, 8 cross-checked field-by-field against the node's own decoding, zero failures. Note its contract — it stops at the end of the last output, so truncating the trailing witness/locktime is legitimately *not* an error, which `TestParseTxRejectsGarbage` pins explicitly.

### Address indexing

Bitcoin Core has no address index, so `/info <address>`'s history stats needed one built in-repo. `addrindex/` is that index; its package comment carries the layout rationale, and the measurements behind it are below.

Three existing implementations were read for their on-disk design before writing this one, rather than guessed at:
- **btcd's `addrindex.go`**: a 21-byte address key into a doubling "level" merge scheme (level 0 holds 8 entries, each level twice the last), storing 12-byte `{block ID, offset, length}` pointers into btcd's *own* block files. Compact, but only possible because btcd owns its block storage — we talk to Core over HTTP.
- **Fulcrum**: RocksDB, scripthash-keyed, measured at **133 GB for mainnet in August 2023**. Bigger than the ratio below because it also caches full UTXO details to serve Electrum clients without round-tripping to Core, which this bot does not need — and ruled out as a dependency anyway, being a second service to run and keep in sync.
- **electrs' current backend, `bindex-rs`**: the closest reference, by electrs' own author and built for Core 31. One RocksDB row per touch, keyed `scriptHashPrefix(8) + globalTxNum(4)` with an empty value, covering both the funding and spending sides. Reports ~10% of blockchain size.

The short version: it follows electrs/`bindex-rs` — hash each `scriptPubKey`, keep an 8-byte prefix, record one entry per "touch" (an address in an output, or in a spent input) — but **shards** rather than keying per address, because bbolt is a B+tree with per-key page overhead and no compression, where bindex relies on RocksDB's LSM and Zstd. The key is `shard(2 bytes of the hash) + rangeIndex(4)` and the value is the packed run of every touch in that shard and 1000-block range, each `remainder(6) + heightOffset(2) + txIndex(2)` = 10 bytes.

A first attempt keyed by address, expecting per-key overhead to amortize across repeated touches; measured on real mainnet blocks it did not, because **71% of addresses are touched exactly once and 96% at most twice**. That cost ~133 bytes per address and projected to 150–250 GB. Sharding measures **18.15 bytes/touch** over 900 real blocks, projecting to roughly 85–113 GB, and makes writes **append-only** — each shard-range value is written once and never rewritten, which is what let the write-side history cap go away. History is now complete on disk; only `Lookup` stops early (`maxLookup`) to bound a Telegram reply, flagged with the same trailing `+` the btcd path used.

The backfill reads Core's **REST** interface, not RPC: `/rest/block/<hash>.bin` and `/rest/spenttxouts/<hash>.bin` are binary and need no authentication. Measured on mainnet, block + spent outputs is **1.95 MB in 28 ms**, where `getblock` verbosity 3 for the same block is **13.7 MB** of JSON. This is what makes indexing the whole chain tractable at all — roughly 7 hours at the measured rate. It is enabled by `-core-rest` and runs unattended; until it has a cursor, `/info <address>` reports "unavailable (address index is still building)" rather than presenting an empty history as fact.

**Two measurement traps**, both of which produced confidently wrong numbers before being caught — worth knowing before re-measuring:
- **A small sample is meaningless for a sharded index.** Sharded values only reach their steady-state size once a whole range is in them. Measuring 25-block windows reported *exactly* 16.78 MB for every window regardless of touch count, because the cost was entirely per-key overhead against nearly-empty values.
- **Merging per block instead of per chunk measures a different design.** Calling `merge` once per block rewrites all ~65k shard keys every block: 30.89 bytes/touch and 113s for 900 blocks. The batched merge the backfill actually performs gave 18.15 bytes/touch and 26s over the same blocks.

`rangeBlocks` (1000) is the tuning lever, trading three things at once: the number of keys, how much a lookup must read, and how much memory a backfill chunk holds before flushing. It was not tuned beyond confirming the result lands inside budget.

### The /info lookup

`info()` in `info.go` classifies its (non-empty) argument into exactly one of three kinds, checked **in this order**, and dispatches to the matching per-kind function — `transaction()`, `block()`, or `address()` (one-word names, same convention as `info`/`watch`): the 64-hex-character shape (`isTxid`), then block height (parses as a non-negative base-10 integer via `strconv.ParseInt`), then address (the catch-all). The order matters and is not arbitrary: a 64-character string of all decimal digits (e.g. all zeros) satisfies *both* the txid shape and `ParseInt`, since decimal digits are a subset of hex digits — checking the hex shape first is what disambiguates it correctly. This was a real bug caught by manual testing against a live regtest node, not a hypothetical; don't reorder these checks without re-verifying against a real node.

**A block hash has exactly the same shape as a txid** — 64 hex characters — so `isTxid` matching does *not* settle which one it is, and nothing local can: only the node knows. So the 64-hex branch first asks `getBlockHeader(arg)`, an O(1) index lookup that errors for a hash the node has no block for; on success `/info` dispatches to `block(header.Height)`, on failure to `transaction(arg)`. Going through the **height** rather than formatting the block from its hash is deliberate: it reuses the block cache and guarantees `/info <hash>` returns byte-for-byte what `/info <height>` returns. The cost is one cheap failed lookup on every `/info <txid>`. Verified against the real mainnet node: `/info 00000000000000000000524afad3a4cc1e4e190e1272de721de6cdb4e889f6aa` resolved to height 958835, produced a reply identical to `/info 958835` (which then came straight from the cache), and a txid from that same block still reached the transaction path. `TestInfoFlow` pins the equality; note its fake btcd **must error on an unknown hash** the way a real node does — an earlier leftover fixture returned a header for *any* hash, which made every txid look like a block.

Each per-kind function calls Core directly and replies with a multi-line message: `transaction` via `getRawTransaction` reports Status (confirmed + confirmation count, or unconfirmed/mempool), the confirmation time (`Confirmed:` = the block time via `when` — note the node keeps no broadcast time for a confirmed tx, so the *delay* it took to confirm isn't computable; only the confirmation timestamp is), Block, Amount (summed `Vout[].Value` in whole satoshi, `math.Round(total*1e8)`, space-grouped), Fee, Size, and compact Input/Output address lists. The fee and the input addresses both need each input's prevout, and where those come from depends on whether the transaction is confirmed: Core supplies them **inline** at `getrawtransaction` verbosity 2 for a confirmed transaction, so `txInputs` makes no extra calls at all, while a mempool transaction has no undo data and falls back to `fetchInputs`, which fetches each input's previous transaction concurrently (bounded `sem` of 16 + `WaitGroup`). Either way it returns `(fee, addrs, spent, ok)` — `addrs` in input order for this listing, `spent` summed per address for the watch notifier's outgoing detection (see Watch notifications). A coinbase tx shows `Fee: none (coinbase)` / `Inputs: coinbase (newly generated)`, and any prevout-fetch failure degrades Fee/Inputs to `unavailable`. `compactAddrs` shows at most the first three addresses (each `short`-ened) with a trailing `...` when there are more; an output with no address (OP_RETURN, SegWit commitment) renders `(non-standard)`. An unconfirmed tx omits the Confirmed/Block fields. `block` is **served from the cache** — `block()` calls `loadBlock(height)` and, on a hit, replies with `formatBlock(bi)` without touching btcd; on a miss it computes the record live (`computeBlockInfo`), stores it, and replies. See Block info cache below for the record's fields and how it's populated (backfill goroutine + block notifications). `blockFeeStats()` (used by `computeBlockInfo`) reads each non-coinbase transaction's own `fee`, which Core reports in `getblock` verbosity 2, for the Lowest/Average/Highest — no prevout fetching, unlike the btcd path that had to derive every fee itself; btcd's getblock omits input values, so it gathers the referenced prevout txids and fetches those transactions **concurrently** (a `sync.WaitGroup` over a bounded `sem` channel of 16, results collected under a mutex). A coinbase-only block shows `Fees: none (coinbase only)` (fee distribution effectively requires `--txindex`, same graceful-degradation spirit as the address index — but reward and reward+fees come from the coinbase alone, so they show regardless). And `address` via `validateAddress` (type derived from `IsWitness`/`IsScript`) plus **on-chain history stats** from the bot's own `addrindex` (Core has no address index — see Address indexing). `addressHistory` looks the address's scriptPubKey up in the index, which returns `(height, txIndex)` touches rather than txids — that is what lets it store 10 bytes per touch — then resolves them: each distinct height's txid list via `getBlockTxids`, then each transaction at verbosity 2, both stages concurrent and bounded. `addressStats` then sums, over those transactions: **Balance** (received − sent), **Total received**, **Total sent**, **Total flow**, **Total fees** (read straight off each transaction's own `fee`, since Core computes it), plus the **Transactions** count and the **First/Last tx** times. Amounts render via `compactBTC`, times via `timeCompact`, and the **Activity period** via `periodText`. Hitting `addrTxLimit` (10000) yields partial stats, flagged by a trailing `+` on the transaction count, exactly as the btcd path flagged its own cap. Until the index has been built at all, the reply says `Activity: unavailable (address index is still building)` rather than presenting an empty history as fact. All three messages put a blank line after their header line (`Transaction 32e43e...870b16` / `Block #100` / `Address 1A1zP1...DivfNa`) and space-pad the field labels so values start in one column per message (the pad width is per-message, computed from its longest label — `Confirmed:` for a confirmed transaction, `Reward + fees:` for a cached block, `Activity period:` for addresses). The field block — but not the header — is wrapped in `<pre>...</pre>` so Telegram renders it monospace and the alignment actually holds. To make that work, `bot.send` in `telegram.go` always sets `parse_mode: "HTML"` on every outgoing message, which imposes an escaping obligation: any user-derived text echoed into a reply must go through `html.EscapeString` (Telegram rejects messages with an unescaped `<` that isn't a supported tag). The two echo sites — `watchCmd()`'s confirmation and the invalid-address message — do this; txids skip it because `isTxid` guarantees pure hex, and a validated address is base58/bech32, also HTML-safe. Confirmed-transaction and block times are both rendered by `when(unix)`: relative ("2 days ago", pluralized by `ago`) when within the last 3 months, lowercase absolute ("14 november 2023 22:13", `strings.ToLower` over Go's "2 January 2006 15:04" layout) when older. Txids, block hashes, and addresses are printed shortened by `short(s)` ("32e43e...870b16": first 6 + "..." + last 6, applied only when the string is longer than 15 characters) — except the "doesn't look like a valid Bitcoin address" echo, which keeps the full input because the address branch is the catch-all and that text isn't known to be an address at all. ### Watch notifications

There are **two kinds** of watch with **different delivery models**. An **address** watch (`/watch <address>`) is persisted and, whenever a transaction *pays* the address **or spends from it**, sends a mempool notification (via btcd's `relevanttxaccepted`) **and then a second "confirmed" notification** — with how long it took — once that transaction is mined. Both directions are covered: an incoming payment reports the `Amount`, and an outgoing one reports what left (`Sent`), what returned as change (`Change back`) and the resulting `Net` move, so the message answers "how did this address change" either way (see Detecting spends below). A **transaction** watch (`/watch <txid>`) is a one-shot: it fires once, when that transaction *confirms* (is mined into a block). Both "confirmed" notifications run through the same `blockconnected` → `processConfirms` path (see Transaction watches below); the mempool notification is the address-watch fan-out only.

The **address**-watch delivery model is **one goroutine per watch** fed by a broadcast channel fan-out (there is deliberately no address→chats map — an earlier version used `watchersByAddr` and was replaced by this at explicit request):
- **Watchers**: each address watch becomes an entry in the package-level `notifies map[notifyKey]notifyChans` (keyed by `notifyKey{chat, typ, id}`, guarded by `notifyMu`), where `notifyChans{ch, stop}` holds a `chan notification` and a stop channel. `startNotifyChat` inserts the entry and launches a goroutine that `select`s on `ch` and `stop`, messaging its chat only for notifications matching its own address — on **either** side, `notification.received[addr]` or `notification.sent[addr]`, whichever is present (both are, for a spend that returns change). `ch` is **never closed** (so a broadcast can always send without panicking); a watcher is terminated by closing `stop`. `stopNotifyChat(chat, typ, id)` closes+drops one entry (chatID-scoped like the store's `Remove`); `stopNotify` (from `shutdown` and test setup) closes them all and also `txwatches.Reset()`s the confirmation map. Only address watches live here now — transaction-confirmation watches moved to the `txwatches` package — so `notifyKey.typ` is effectively always `watchTypeAddress`.
- **Subscription** (address watches only): `watchCmd()` calls `startNotifyChat` and then `seedOutpoints([addr])`. Under btcd this step also loaded the address into btcd's connection-wide filter; **Core has no such filter**, so there is nothing node-side to load — `seedOutpoints` registers the address's scriptPubKey and current UTXOs with the bot's own matcher instead (see Detecting spends below). On startup `startNotify(bot)` re-creates a watcher per `watches.List()` record and seeds them all, so watches survive restarts. If the node isn't configured the watch is still stored/started — it just won't fire until a restart with a node.
- **Broadcast**: a `rawtx` ZMQ frame reaches `onRawTx`, which parses it locally and drops it unless it touches a watched script or outpoint — almost every mempool transaction is dropped here, without any I/O. Only on a match does it spawn `go broadcast(txHex)`. `broadcast` calls `decodeRawTransaction`, builds one `notification{txid, received: addr→summed Vout value, sent: addr→summed input prevout value}`, and non-blocking-sends it to *every* watcher's channel; each watcher then filters. `received` comes straight off the decoded outputs; `sent` cannot, because a decoded transaction's inputs are bare txid:vout refs carrying no addresses — it comes from `txInputs`. It also calls `recordOutpoints` so the outputs this transaction creates for watched addresses are recognised when later spent. Before fanning out it **enriches** the notification (best-effort): the fee and `vsize` come from **`getmempoolentry`**, not from the transaction — this is a mempool transaction, so it has no undo data and Core reports neither fee nor prevout for it at verbosity 2 — and `confEstimate` buckets the resulting sat/vB rate against `estimatesmartfee`'s 2- and 6-block targets into `~10-20 min` / `~1h` / `2h+`. The **address** notification shows Fee / Fee rate / Confirms below Tx / Amount; any fetch failure just leaves them off. Right after sending it, the watcher calls `txwatches.AddAddrConfirm(...)` to register a one-shot confirmation watch, so the same transaction being mined later produces the follow-up "confirmed" message. A `hashblock` frame spawns `go processBlock(hash)` and `go processConfirms(bot, hash)`. The channel sends are non-blocking (`select`/`default`) so one slow or already-stopped watcher can't stall the fan-out.

**Deduplicating sightings.** Core publishes a transaction on `rawtx` **twice** — once when it enters the mempool and again when it is mined — so a watched payment used to produce three messages: the mempool notification, the confirmation, and then a second "New transaction" from the mined republish (recognisable because it lacked the Fee/Fee rate/Confirms lines, the transaction having left the mempool by then). Verified against a real node: sighting #1 reports `confirmations=0` and is in the mempool, sighting #2 reports `confirmations=1` and is not, and both `rawtx` frames arrive *before* `hashblock`.

`broadcast` therefore keeps a `notified` map of txids (48h TTL, swept on insert) and returns early on a repeat. Deduplicating on the **txid** rather than simply skipping confirmed transactions is deliberate: a transaction whose first sighting is already mined — a coinbase paying a watched address, or anything that arrived while the bot was down — has no earlier notification to duplicate and must still fire. It also collapses rebroadcasts. Only transactions that already matched a watch reach this map, so it stays small. `stopNotify` clears it, as tests depend on that isolation.

**Detecting spends (why outpoints are seeded).** A spend names only the outpoint it consumes — never the address — so recognising one means already knowing which outpoints a watched address owns. This was true under btcd too, but the mechanics have inverted. btcd kept the outpoint set inside its *own* filter, learning an address's outpoints only by watching payments arrive while the filter was loaded; the bot had to replay an address's whole history (`addressTxs`, oldest-first) to derive the set and push it in with `loadTxFilter`. Core has no filter, so **the set lives in the bot** (`watchedOutpoints` in `zmq.go`) — and Core answers the question directly.

`seedOutpoints(addrs)` calls `validateaddress` for each address (registering its scriptPubKey for output matching) and then one **`scantxoutset`** covering every address at once, seeding an outpoint per returned UTXO. That is both a smaller job than the old history replay and an exact one: the old approach's caveat — that a capped history loses the *newest* transactions, which is exactly where live UTXOs are — is simply gone. It is called from `watchCmd` and `startNotify`, and runs in a **background goroutine** because the scan walks the whole UTXO set and takes minutes on mainnet. There is no longer a reconnect path to re-seed from: HTTP is stateless and the ZMQ subscriber resubscribes itself.

**Transaction watches / confirmations** (`txwatches` package + `processConfirms` in `notify.go`): confirmations for **both** watch kinds are served from the `txwatches` package's in-memory map (keyed by txid; **not** persisted, so pending confirmations are forgotten on restart — accepted by design). `/watch <txid>` calls `txwatches.Add(txid, chat, alias)` (a **direct** entry, `addr==""`); a watched address's incoming tx calls `txwatches.AddAddrConfirm(txid, chat, addr, alias)` from the watcher goroutine (an **address-derived** entry; see Broadcast above). Neither is added to btcd's `loadtxfilter` — that filter matches addresses/outpoints and `relevanttxaccepted` is mempool-acceptance only, so there is no first-class per-txid confirmation trigger. Instead confirmation is detected off the `blockconnected` notification the bot already receives for the block cache: `processConfirms(bot, hash)` (in `notify.go`) early-returns unless `txwatches.Any()`, otherwise fetches the new block's txids via the cheap `getBlockTxids` (getblock verbosity 1) and hands them to `txwatches.Confirms(txids)`, which removes and returns every matching watch as a `Confirmed{Txid, ChatID, Alias, Addr, WatchedAt}`; `processConfirms` then formats+sends each. The message depends on `Addr`: a direct watch gets `🔔 Watched transaction <short> (alias) was confirmed in block #N after <elapsed>`; an address-derived one gets `🔔 Transaction <short(txid)> on watched address <short(addr)> (alias) was confirmed in block #N after <elapsed>`; both carry buttons for the txid, the address and the **block height**, so the block it landed in is one tap from an `/info`, where `elapsed = durationText(now − WatchedAt)` (a `format.go` helper; "12 min" / "2 h 5 min"), which for the address kind is the time from first mempool sighting to confirmation. Registration dedups on (txid, chat, addr) so a re-broadcast can't queue two messages; `txwatches.For`/`txwatches.Remove` (backing `/watches` and `/unwatch <txid>`) act on **direct** entries only, and unwatching an **address** also calls `txwatches.RemoveAddrConfirms` so no confirmation arrives after the user stopped watching. This reuses the very block push the cache already consumes — no new subscription, and it works for any txid without encoding it into a filter. (The old `/watch <txid>` "was accepted to the mempool" message is gone; it was effectively dead, since a txid was never in the filter and so `relevanttxaccepted` only matched a watched txid by coincidence.)

`/unwatch <arg>` reverses a watch. For a **txid** (`isTxid(arg)`) it just drops the in-memory watch via `txwatches.Remove(arg, chatID)` (chat-scoped) — no store, no filter. For an **address** it is `watches.Remove(chatID, arg)` to delete the persisted record(s), then `stopNotifyChat` to terminate the watcher goroutine, then `txwatches.RemoveAddrConfirms(arg, chatID)` to drop any pending confirmation watches for that address, then `unwatchScripts(arg)` to drop the address's scriptPubKey and outpoints from the local matcher. That last step is an optimization — the real guarantee that notifications stop is that the watcher goroutine is gone. (Under btcd this rebuilt the node-side filter with `loadTxFilter`; there is no node-side filter now.) If nothing matched (`watches.Remove` returned 0, or `txwatches.Remove` returned 0) the user is told they weren't watching it.

**Verification status after the Core migration.** The btcd-era end-to-end runs (a real signed regtest payment driving `/watch` → notification → fan-out to two chats; both confirmation paths against mainnet; the outgoing/spend path against a real mempool transaction) all exercised btcd's push model and **do not carry over** — the transport, the filter and the fee source have all changed. What has been verified under Core: the client and every read command against the live mainnet node (`/fees`, `/mempool`, `/info` by height and by block hash, block-cache backfill), ZMQ delivery from a node publishing each topic on its own port, and `parseTx` against the live mainnet mempool firehose (40 transactions, 8 cross-checked field-by-field against the node's own decoding, zero failures). **The whole path has now been driven end-to-end against a real Core node**: watching a fresh regtest address, paying it and mining the block produced exactly the two intended messages (mempool notification, then confirmation in block #104 after 5 sec). It is also covered by the suite (`TestWatchNotification`, `TestSpendNotification`, `TestSpendWithChangeNotification`, `TestSeedOutpoints`, `TestTxConfirmation`, `TestAddrConfirmation`, `TestBroadcastDedups`, `TestConfirmationLinksBlock`).

In the suite the notification tests no longer wait for a server push — there isn't one. They call `broadcast(txHex)` or `processConfirms(bot, hash)` directly, which is exactly what `zmq.go` does with a frame, against `newFakeCoreServer` (plain HTTP; the websocket fake is gone). Note the shared `awaitNotification` helper registers its teardown with `t.Cleanup`, not `defer`: a deferred `stopNotify` would run before the caller's assertions and `txwatches.Reset()` away the confirmation watch under test. Keep the suite green under `go test -race` — the notification paths are the codebase's only concurrent ones (the broadcast/per-watch goroutines, the ZMQ receive loop, and `processConfirms` reading the `txwatches` map under its mutex).

### The watches store

The bbolt connection is a plain package-level `var db *bbolt.DB` (in `db.go`), opened once in `main()` via `openDB(-db path)` and closed during graceful shutdown (`closeDB`, see Runtime model). `openDB` opens the one file, creates the `blocks` bucket, and hands the same handle to `rates.Init(db)`/`watches.Init(db)`/`miners.Init(db)` so those packages share it — one file, one handle, four buckets. **Every bucket-owning package must be Init'd in `openDB`, and forgetting one fails silently**: those packages guard their operations on a nil handle, so the package quietly does nothing rather than erroring. The address index shipped that way once — it fetched and parsed the chain over REST while storing none of it, logging progress the whole time — so `addrindex.merge` now returns an error on a nil handle instead of no-oping, and `TestOpenDBBuckets` pins the full set of eleven. Address-watch storage lives in the `watches` package (`Add`/`List`/`Remove`); there is no `watchStore` struct, and the internal `watchRecord` isn't exposed — `List` returns a minimal public `Watch{ChatID, Address, Alias}`.

`/watch <target> [alias]` records the watch — an **address** watch via `watches.Add(chatID, address, alias)` (persisted as an internal `watchRecord{CreatedAt, ChatID, WatchID, Alias}` under an auto-incrementing key, `bbolt.Bucket.NextSequence` + big-endian encoding), a **transaction** watch via `txwatches.Add` into the in-memory map instead (not persisted; see Watch notifications). `watchCmd()` in `main.go` splits `arg` on the first space into the **target** (first token) and an optional **alias** (the remainder, trimmed) — a bare `/watch` prompts for both together in one follow-up message — then classifies the target via `isTxid` (exactly 64 hex characters → transaction, anything else → address) — a heuristic, not real validation, good enough to route the watch. The alias is echoed in the confirmation, appended in parens to the notification header (`…watched address bc1q…dayd2g (John)`), and shown in `/watches`; it's `html.EscapeString`'d at every display site since it's arbitrary user text. `watches.List()` (used by `startNotify`, `/watches`) returns every stored watch; `watches.Remove(chatID, address)` deletes every record matching **both** fields and returns the count — the `chatID` half is the security scoping that stops one chat from removing another chat's watch, and the count lets `/unwatch` distinguish "removed" from "you weren't watching that". It collects keys during a `ForEach` and deletes them after, because bbolt forbids mutating a bucket mid-iteration. Only address watches are persisted, so the record carries no type field (the `Watch` JSON key is kept for compatibility with records written before the package split).

**A chat is capped at `maxSubscriptionsPerChat` (500)**, counted across both kinds together (`watches.Count(chat)` plus `len(txwatches.For(chat))`). `watchCmd` checks the count before storing and refuses past the limit with a message telling the user to unwatch something first, logging the rejection at INFO. The cap exists because each address watch costs a live goroutine and a channel in the notification fan-out, and every one of them is woken for every matching transaction — an unbounded chat could quietly make the fan-out the most expensive thing the bot does.

### Database backups

`-backup <path>` turns on periodic backups: `main()` calls `startBackup(path, interval, script)` right after `openDB`, which runs a goroutine copying the whole database to `path` every `-backup-interval` (default 24h) and then running `-backup-script` (default empty = nothing runs). `backup.go` holds it.

- **The copy** is `tx.CopyFile` inside a `db.View` read transaction, so it is a consistent snapshot of every bucket taken *without stopping the bot* — bbolt allows one writer alongside many readers, so nothing blocks while it copies.
- **It lands on `<path>.tmp` and is renamed into place.** `CopyFile` writes its destination directly, so a failure partway (a full disk) would otherwise leave a truncated file exactly where the last good backup was. On any error the temp file is removed and the previous backup is left untouched (`TestBackupKeepsPreviousOnFailure` blocks the temp path with a directory to force this).
- **The first copy happens at startup, not one interval later** — but only when the destination is missing or already older than one interval. This matters because of the deployment setup: `scripts/update.sh` checks for new commits every 5 minutes and restarts the service on each one, so a pure ticker could be reset by a redeploy before a 24h backup ever fires. The destination file's own mtime is the record of when the last backup ran, so this needs no extra state.
- **The script** runs via `sh -c`, so `-backup-script` can be either a plain path to an executable script or an inline command. The backup's path reaches it both ways — as `$1` and as `$BACKUP_FILE` in the environment — so `/opt/bitnsbot/upload.sh` and `rclone copy "$1" remote:` both work. Its combined output is logged (INFO on success, ERR on failure); a failing script is never fatal. It is bounded by `backupScriptTimeout` (30 min, a package var for tests) because a script that hangs would wedge the goroutine and silently stop every later backup — and making that bound actually hold takes more than a context deadline. The script gets its **own process group** (`SysProcAttr.Setpgid`) and a `cmd.Cancel` that kills the **group**, plus `cmd.WaitDelay` as a backstop. Killing only the shell is not enough: anything it leaves running — a backgrounded upload, a child outliving it — inherits the output pipe, and `CombinedOutput` blocks until every writer to that pipe is gone, so the timeout would expire while the goroutine stayed stuck for as long as the child ran. That is not hypothetical; it is what made `TestBackupScriptTimeout` hang in CI (a `sleep` surviving the shell), and the test now pins both halves — that `backup` returns at the timeout, *and* that the backgrounded child is dead afterwards (with `WaitDelay` alone the first passes and the second fails). Note `Setpgid` is unix-only, which is fine for a bot that targets Linux and macOS.
- Successful backups log at **status** level (verbosity 0) with the path, size and duration, so an operator can confirm backups are happening without raising verbosity.

`backup_test.go` covers all of it against a real bbolt file, reopening each backup independently to prove it is a valid database holding the seeded watch (not merely a file of the right size). Verified for real by running the built binary with `-backup-interval 2s` and a logging script: the startup copy plus one per tick, the script invoked each time with the right path, and the resulting snapshot — taken while the rates backfill was actively writing — passed bbolt's own `tx.Check()` with all seven buckets intact (5815 rate records, 218 miner addresses, 201 tags).

### Block info cache

`/info <height>` is served from a cache (the `blocks-stat` bucket) so building a block's record happens in the background, not in the user's request. (Under btcd the expensive part was computing every transaction's fee from its prevouts; Core reports fees itself, so what remains is one `getblock` at verbosity 2 — still worth caching for a full mainnet block, but no longer a fan-out.) `blocks.go` holds one JSON `blockInfo` per height (big-endian key via `itob`, reusing the rates/watches idiom): height, hash, time, size, tx count, miner, `FeesOK` + fee min/avg/max (BTC), tx-size min/avg/max (bytes), reward, and total (reward + fees = the coinbase output). `computeBlockInfo(hash)` builds a record from one `getBlockVerbose` (verbosity 2 → all txs with sizes, vins, vouts) with every transaction's fee already included, so no prevout fetching happens at all; reward comes from `subsidy(height)` (50 BTC, halving every 210000 blocks) and total from summing the coinbase outputs, so reward/total never need prevouts — only the fee distribution does. Amounts render in satoshi via `sats()`/`group()` (`group(int64)` is the shared space-thousands helper `sats` now routes through), sizes via `group`. Confirmations and the old header-only path are gone; `formatBlock` builds the aligned `<pre>` block from label/value pairs.

Three things populate the cache, all funneling through `computeBlockInfo` + `storeBlock`:
- **On-demand**: a `/info` cache miss computes and stores the block (so an old, uncached block is slow once, then instant).
- **New blocks**: a `hashblock` ZMQ frame becomes `go processBlock(newTipHash)` (see The ZMQ notification path). Under btcd this needed a `notifyBlocks` subscription on the connection; Core publishes unconditionally, so there is nothing to subscribe to and nothing to re-establish after a restart.
- **The collector**: `startBlockCache()` (launched from `main()`) runs `collectBlocks()` immediately and then every `blockCacheInterval` (10 min, a var). This is **cursor-driven, not a fixed-depth backfill** — the earlier version walked back a `blockBackfillDepth` of 50 blocks from the tip and stopped. `blocks-cursor` holds the last processed height under the key `cursor`; a run resumes at the next height, and with **no cursor at all it starts from genesis**, so a fresh install fills in the whole chain over successive ticks rather than only recent history. `flushBlocks` writes a batch and advances the cursor in one transaction, so an interrupted catch-up resumes from the last flushed batch. `storeBlock`/`loadBlock` are nil-`db` guarded, so block lookups still work (compute-only, no caching) in tests that don't open a db.

**Miner attribution** (`miners` package): the `miners` bucket maps each pool's coinbase output address to its name and `miners-tag` maps each pool's coinbase **tag** (the marker pools write into the coinbase scriptSig, e.g. `Mined by AntPool`, `/Foundry USA Pool/`) to the same. `miners.Attribute(addresses, coinbaseHex)` is the single attribution entry point used by both `computeBlockInfo` and the stats collector: it tries every coinbase output address as an exact key lookup first, then falls back to scanning the tag bucket for a tag contained in the (hex-decoded) coinbase script, returning "" when neither matches — callers turn that into "Unknown" (`computeBlockInfo`) or skip the block (the collector).

Both halves of that are load-bearing, and both were established by measurement against the real mainnet node over the same 100 blocks:
- **Every** coinbase address must be tried, not just the first: modern coinbases carry several outputs and the pool's payout isn't reliably output 0. First-address-only attributed **8**/100.
- The **tag** fallback carries most of the attribution: the big pools rotate payout addresses far faster than `pools-v2.json` lists them, so address-only (all addresses) still attributed only **25**/100 and missed *every* major pool — the misses were AntPool, Foundry USA, F2Pool and MARA, each of which names itself in its coinbase tag. With tags: **98**/100, and the ranking matches the real network (Foundry 31%, AntPool 22%, F2Pool 12%). Tag matching is plain **substring** matching, not regex — of the 201 tags in the real file exactly one contains a regex metacharacter and it is a literal `$`. Tags are scanned from the database (a couple hundred rows per block), not from an in-memory copy, so the DB-backed design holds. The shortest tags are 4 bytes (`Kano`, `emcd`, `HHTT`, `EMC `), so a false positive on random coinbase bytes is possible in principle; this is the same heuristic mempool itself ships.

`miners.Start()` (from `main()`, before the block cache) keeps both buckets fresh: an initial fetch of mempool's `pools-v2.json` **only when the address bucket is empty** (a fresh install) — a populated bucket survives restarts, so the definitions are not re-downloaded every start — then a refresh every 24h (`updateInterval`, a package var for tests). `update()` only ever `Put`s the file's addresses and tags, never deletes: the source only adds, so old entries stay valid and no full re-sync is needed. `sourceURL` is also a package var for tests. The real file currently holds 171 pools, 218 addresses and 201 tags. One caveat of the async refresh: on a *fresh* install the initial fetch races the block-cache backfill, so a few of the first-backfilled blocks may cache "Unknown" until re-computed; a populated bucket (any later restart) has no race.

### Miner statistics

`miners/stats.go` keeps a running per-pool aggregate in the `miners-stat` bucket, **keyed by pool name** — so every address and every tag belonging to one pool combines into a single record — and `/miners` prints the top 10 from it. The stored `stat` (unexported) is `Blocks`, `Reward` (BTC, subsidy + fees = the whole coinbase output), `Fees` (BTC), `Work` (Σ difficulty × 2^32, the expected hashes) and `LastWork` (the work of that pool's most recent block).

`StartStats(src)` (from `main()`, only when the node is configured) runs `collect` immediately and then every `statInterval` (10 min, a var for tests). The `miners` package can't reach Core — that connection is package `main`'s — so the chain data is injected through the small `Source` interface (`Tip`, `Block`), implemented by `minerSource` in `blocks.go`: per height a `getBlockHash`, a `getBlockTxids` (verbosity 1 → height, **difficulty**, txids — `coreBlockTxids.Difficulty` carries it) and a `getRawTransaction` of the coinbase, giving every payout address, the coinbase script (for the tag) and the total output; fees are that total minus `subsidy(height)`.

- **Cursor**: `miners-cursor` holds one JSON `cursor{Start, Last}` under the key `cursor` — `Start` is the first tracked height (the window the consumption share is computed over), `Last` the last processed. A run resumes at `Last+1`; on a fresh install it starts at `tip − initialWindow + 1` (1000, a var), so `/miners` has about a week of history without walking from genesis.
- **Chunking**: a gap wider than `chunkSize` (1000) is processed in chunks — each chunk aggregates into an in-memory `map[name]*stat` and is then merged into the bucket by `flush` in **one** transaction that also advances the cursor, so catching up thousands of blocks doesn't build one giant transaction and a crash mid-catch-up resumes from the last flushed chunk. `Blocks`/`Reward`/`Fees`/`Work` accumulate; `LastWork` is overwritten (chunks run oldest-first, so the newest write wins).
- **Waiting for the definitions**: `collect` early-returns while the address bucket is still `empty()`, so a fresh install doesn't spend its whole initial window on blocks nothing can be attributed to — it starts once `miners.Start()`'s first fetch lands.
- **A failed block fetch abandons the run** (no flush, cursor untouched) so the next tick retries the same range. Skipping the block and flushing anyway would step the cursor over it and drop it from the aggregate permanently — and a btcd restart mid-catch-up fails *every* block in the chunk, not one. The cost is that a genuinely unfetchable block stalls the collector, which is at least loud: the same warning every 10 minutes.
- A block whose miner can't be attributed (`Attribute` returns "") is skipped rather than counted under "Unknown", so the shares below are shares of the *attributed* blocks. Blocks reorged out after being counted stay counted — not worth correcting in an aggregate this coarse.

**The power estimate.** `Top(n)` returns `Stat{Name, Blocks, Reward, Fees, ConsumptionGW}`, sorted by blocks descending and **tie-broken by name** so a tied list is stable between calls. Consumption is the pool's share of the window's blocks × the *current* network hashrate × an assumed hardware efficiency:

    ConsumptionGW = (Blocks / (Last−Start+1)) × (LastWork / 600) × joulesPerHash / 1e9

`LastWork / 600` is the current network hashrate (that block's difficulty × 2^32 over the 10-minute target), which is why the record keeps `LastWork` at all: it carries the difficulty **in force now**, where dividing the accumulated `Work` by the window's seconds would average in every past difficulty epoch. `joulesPerHash` is `1e-11` — **the most modern mining hardware**, the latest hydro-cooled ASICs at ~10 J/TH (Antminer S23-class). Real fleets mix in older machines, so this is deliberately a lower bound: the "if they ran today's best gear" figure. Note `LastWork` alone can't rank miners (it's network difficulty, near-identical for everyone) — the block share is what differentiates them.

`/miners` (`minersCmd` in `main.go`) sends `Top(10)` as a plain numbered list — `1. AntPool. 22 blocks mined, reward 69.14 BTC, fees 0.39 BTC, consumption 2 GW` — with `trimNum` (a `format.go` helper: fixed decimals, trailing zeros trimmed) at 2 decimals for BTC and 1 for GW, and a singular "1 block". An empty bucket replies "No miner statistics yet — still collecting."

Verified against the real mainnet node over 100 blocks (throwaway probe, not in the suite): 98 attributed across 10 pools in ~7s, Foundry USA 31 blocks / 2.8 GW down to Braiins 1 block / 0.1 GW, the ten summing to 8.9 GW against a 9.1 GW whole-network figure at that difficulty — self-consistent, and about half of published real-world estimates, as the best-gear assumption implies. In the suite, `miners/stats_test.go` drives `collect` through a fake `Source`: `TestCollectStats` (aggregation by name across two addresses of one pool, plus a payout that isn't output 0), `TestTopConsumption` (the formula, pinned so that an accumulated-`Work` version would fail), `TestCollectChunks` (a chunk is flushed to the database before the next begins, asserted from inside the source's next fetch), `TestCollectResumes` (only new heights are fetched, stats accumulate, the window grows), `TestCollectRetriesOnError` (a failed fetch leaves the cursor and the bucket untouched, and the retry picks up the whole range) and `TestCollectWaitsForAddresses`. `TestMinersFlow` in `flow_test.go` covers the command's exact rendering by seeding the buckets directly.

### The /market command

`/market` (`marketCmd` in `main.go`) reports the current price, market capitalisation and 24h volume, then how the price has moved over 24h, 1w, 1m, 3m, 1y and 5y.

**The changes come from the bot's own rate history, not from a market API.** The `rates` package already holds a daily series back to 2009 plus live 5-minute samples, so `rates.At(now − period)` answers any period without a second dependency, and the figures stay consistent with the USD values shown everywhere else. A period whose baseline falls outside `rates`' tolerance is simply omitted rather than shown as zero — on a fresh install the older rows appear once the backfill lands.

Capitalisation and volume have no local source, so the rates updater fetches them from CoinGecko's free no-auth endpoint (`marketURL`, a package var for tests — one call returns price, cap and volume) **on its existing 5-minute tick** and stores them in the `market` bucket. `/market` reads `rates.LastMarket()`, so like every other command it answers from the database: no third-party call sits between the user and their reply, and an API that is down or rate-limiting costs a slightly stale figure rather than a failed command. Records are keyed by timestamp like the rate series, so the newest is simply the bucket's last key. Until the first snapshot lands those two fields read `unavailable` and the price falls back to `rates.Last()`.

Two formatters exist for this command specifically, both in `format.go`:
- `money` renders large dollar figures as markets quote them — `$1.33 T`, `$31.91 B`. Deliberately **not** `metric`, which is SI and says `G` where finance says `B`; a market cap in gigadollars reads as a units error.
- `price` keeps cents with comma-grouped thousands (`$66,223.00`), where `usd` drops them from $100 up. Cents are noise on a transaction amount and the point on a price quote.

`change(now, then)` renders both the absolute and percentage move, always signed. Note the percentage is measured against the **earlier** price, so the same absolute move reads differently in each direction — `TestChange` pins that asymmetry, since it looks like a bug otherwise.

### Exchange rates

The `rates` package keeps a BTC/USD price history in the `rates` bucket (same db file, via `rates.Init(db)` called from `openDB`), so `/info` and notifications can show a rough fiat value. Each internal `rateRecord{Time, USD}` (unexported; the value is always USD) is stored under its `Time.Unix()` big-endian key, so keys sort chronologically. `rates.Start()` (launched from `main()` right after `openDB`) backfills the daily history once (see next paragraph), fetches a current rate immediately, then refreshes every 5 minutes: the internal `update()` hits all price `sources` (CoinGecko, Coinbase, blockchain.info — free, no-auth GETs), **averages the ones that succeed** (a failed source is just skipped; if all fail nothing is stored), and writes one averaged record via `rates.Add(usd)`. The updater goroutine isn't explicitly stopped on shutdown — `main()` returns microseconds after `closeDB`, so a write-after-close is effectively impossible. Each source has a `parse` func tested against real API payloads (blockchain.info returns *every* fiat — we pluck `USD.last` out of it); `sources` is a package var so tests point it at `httptest` servers.

**Historical backfill:** so `/info` on an *old* transaction can show USD from around its block time (not just today's rate), the internal `backfill()` loads the whole daily series once. It's a no-op when the store already holds deep history — `hasHistory()` is true when the oldest sample is older than `historyHorizon` (3y), which live updates alone can't produce on a fresh bot, cleanly distinguishing "backfilled" from "just started". Otherwise it GETs blockchain.info's `market-price` chart (`historyURL`, `timespan=all` — the entire daily series back to 2009 in one no-auth request), parses it with `parseHistory` (skipping the zero-price pre-market days), and writes every day in **one** transaction via `storeRates` (per-record `db.Update`s would be thousands of fsyncs). Backfilled records land at daily 00:00-UTC timestamps, so they never collide with the live `time.Now()` samples. Verified once against the real endpoint (6402 daily samples, 2009→today); `historyURL` is a package var so tests point it at an `httptest` server, and `TestBackfillRates` also asserts the `hasHistory` guard by counting HTTP hits across two calls.

Two reads, **both DB-only, never online**: `rates.Last()` (cursor `Last()` — the newest sample) and `rates.At(t)` (the sample nearest `t` via `Seek`+`Prev`/`Last`, or not-found if the closest is more than the internal `tolerance` = 36h away). That tolerance is deliberately wider than a day so the daily-granularity backfill (samples at 00:00 UTC) still matches a transaction at *any* time of day — with a 1h tolerance `At` missed almost every daily sample and fell through to today's rate, defeating the backfill; live 5-min samples still match far more tightly. Both return the price as a plain `float64` and `(0, false)` when `db == nil` or nothing is stored, so USD is silently omitted in tests that don't open a db — USD is best-effort enrichment, not a hard dependency. `amountLine(btc, at, current)` (in `format.go`) renders `"<sat> sats (≈ $usd)"`, appending the USD part only when a rate is available: `current=true` uses `rates.Last()` (mempool `/info` and **new-transaction notifications**, which have no confirmed time = "now"), `current=false` uses `rates.At(at)` (a confirmed transaction's block time) **but falls back to `rates.Last()` when `At` finds nothing**. With the daily backfill in place `At` resolves almost any historical tx to its period's rate; the `Last()` fallback is the safety net for a tx in a genuine gap. USD only vanishes entirely when there is *no* stored rate at all. `usd(btc, rate)` (also `format.go`) drops cents from $100 up (`"$90,000"`, comma-grouped whole dollars, rounded) and keeps them below $100 (`"$58.23"`), on the logic that cents are noise on large amounts but the whole point on small ones. Both `usd` and `group` split the **sign** off before doing any of that, because the outgoing-watch `Net` line is the one place they see a negative and both used to mangle it — `group` counted back from the end of the whole string and produced `"- 100 010 000"`, `usd` took the below-$100 branch for any negative and produced `"$-29450.00"` (`TestNegativeAmounts` pins both). Only transaction *amounts* get USD — blocks and addresses have no amount.

### Clickable ids

Every shortened id a reply shows — a txid, block hash or address — also appears as an **inline-keyboard button** under the message, labelled with the same shortened form and carrying the full id as its `callback_data`. Tapping one runs `/info` on it, so browsing from a notification to the transaction to one of its addresses is a sequence of taps.

Buttons rather than links in the text, for a concrete reason: **Telegram does not parse entities inside `<pre>`**, and every reply's aligned field block is `<pre>`. A link there would render as literal text, so making ids clickable inline would mean giving up the column alignment. A button lives outside the message text, so both work at once.

There is also no way to do what one might first reach for — putting `/info <id>` into the user's input field. `switch_inline_query_current_chat` inserts `@botname <query>` (inline mode, not commands), `copy_text` only reaches the clipboard, and tapping a `/info` command in message text sends the command *without* its argument. A `t.me/<bot>?start=<id>` deep link would send a real message and the ids all fit its 64-character limit, but it needs the `<pre>` blocks gone and its behaviour for an already-started bot is undocumented.

`callback_data` is capped at 64 bytes, which a txid hits **exactly**, so the id travels bare — no type prefix, because `info()` classifies its argument anyway. `buttonRows` (in `telegram.go`) drops duplicates, empties, the `(non-standard)` placeholder that unnamed outputs render as, and anything over the limit; it lays buttons out two per row and stops at `maxButtons` (8) so a busy transaction doesn't bury its own message. Call sites pass ids through `sendLinked`, and pass only what the text actually displays — `transaction()` truncates its input/output lists to `shownAddrs`, the same cap `compactAddrs` uses for the text, so there is never a button for an address hidden behind the trailing `...`.

`update()` routes an incoming `CallbackQuery` to `callback()`, which answers the query first — Telegram spins the button until it is acknowledged, so that must happen regardless of what the lookup does — and then calls `info()` with the data.

### Internationalisation

Every user-facing string goes through `i18n(chat)`, which returns a `trans` (a `map[string]string` from English source string to translated string) for that chat's language, or **nil for English** — `trans.String`/`trans.Sprintf` fall back to the original string when the map is nil or the key is missing, so English is the default by construction and needs no table.

`langTrans` in `i18n.go` holds one map per language; **ru** and **es** exist today. The chat's language comes from Telegram itself: `update()` calls `SetChatLanguage(chat, msg.From.LanguageCode)` on every incoming message and callback, so it follows the user's client setting with no command to set it. `chatLangs` is an **LRU bounded to 10000** entries (`lru.go`), not a plain map — a bot that anyone can message would otherwise accumulate an entry per one-off chat forever.

**`tools/i18n-vet` enforces coverage, and it runs in CI.** It walks every `.go` file, finds each `i18n(…).String("…")` / `i18n(…).Sprintf("…", …)` call, and checks that the string appears in *every* translation section of `i18n.go` — sections being delimited by `// i18n-vet:translation <lang>` … `// i18n-vet:end translation` comments — with the same format verbs in the same order. A new translated string therefore fails the build until every language has it.

The one thing to know before refactoring: **it extracts only string literals** (`*ast.BasicLit`) passed directly to those calls. Moving a translated string into a variable, a slice or a constant silently removes it from the tool's reach — no error, just no coverage. See The command menu for a case where that trade was made deliberately and covered by a test instead.

### The command menu

The menu Telegram shows beside the input field is registered with **`setMyCommands`** (`bot.setCommands` in `telegram.go`), called by `registerMenu` in `main.go` at startup.

**`/start` and the menu are driven off one list**, the package-level `commands` slice of `{name, line}` — that is what makes "the menu lists the same commands as `/start`" a property of the code rather than a convention someone has to remember. `start()` loops over it emitting `i18n(chat).String(c.line)`, and the menu takes each description from the same line via `menuDescription`, which cuts at the `" — "` separator and drops the trailing newline. Keeping the **whole `/start` line** as the translation key (rather than storing the description separately) reuses the existing ru and es translations untouched instead of re-keying and re-translating them.

The cost is that `i18n-vet` no longer sees those nine strings, since they are no longer literals at an `i18n(…)` call site (see Internationalisation). `TestCommandLinesTranslated` covers exactly that ground instead: every line in `commands` must have a translation in every language of `langTrans`. `TestMenuCommandsWithinTelegramLimits` additionally pins that no description comes out empty — which is what a translation using a different dash would silently produce — and that none exceeds Telegram's 256-byte cap, since **one bad entry makes Telegram reject the whole call** and leaves the menu empty.

Registration is **one call per language**: Telegram stores a separate list per `language_code` and falls back to the list registered without one, so English goes up with an empty code and each entry of `langTrans` gets its own. Failures are logged and skipped, never fatal — the menu is a convenience and the bot runs fine without it.

It sits **inside the `-register-webhook` block**. `setMyCommands` is global to the bot token, so a second instance started with `-register-webhook=false` (which already means "do not touch the live bot's Telegram-side state") would otherwise overwrite the live bot's menu.

### Command dispatch and the "pending argument" pattern

`update()` in `main.go` is the single entry point for every incoming Telegram update: pull `Update.Message`, log it (`logMessage`), split it into a command and argument (`parseCommand`), then switch on the command. `/start`, `/watches`, `/fees`, `/mempool`, `/miners` (see Miner statistics) and `/market` (see The /market command) take no argument and act immediately (`/start` sends a fixed `<b>`-formatted bulleted help listing the commands; `/watches` (`watchesCmd`, renamed off the `watches` package) lists the calling chat's watches — Addresses from `watches.List()` filtered by `chatID`, Transactions from `txwatches.For(chatID)` — and prints each id **un-shortened** inside `<code>…</code>` for Telegram tap-to-copy; ids are `html.EscapeString`'d because address watch ids are arbitrary unvalidated user input, unlike txids).

`/fees` (`fees()`) replies with five fee tiers — Fastest (10-20 min), Half hour, Hour, Economy, Minimum — each in sat/vB with the USD cost of a typical transaction beside it, rendered in an aligned `<pre>` table. Labels deliberately avoid `<`/`>`/`&` so the fixed text needs no HTML-escaping and the `len()`-based padding matches the rendered width.

**It does not use Core's `estimatesmartfee`** — see `fees.go`, which ports mempool.space's algorithm instead. The two answer different questions: Core's estimator is *backward-looking* (how long did transactions at each rate historically take to confirm), deliberately conservative and slow to react, so during a fee spike it keeps quoting yesterday's cheap rates while the transaction sticks. mempool.space is *forward-looking* — it packs the mempool as it stands into the blocks a miner would actually build and reports what those blocks are paying. Measured against the live mainnet node, Core said **1.07 sat/vB** for the next block while the ported algorithm and mempool.space both said **4.00**.

Two stages, ported from mempool.space's `api/mempool-blocks.ts`, `api/common.ts` and `api/fee-api.ts`. First `buildProjectedBlocks` sorts the mempool by effective fee rate and packs it into 4M-weight-unit blocks, then `medianFeeOf` takes each block's "median fee" — which is **not** the median transaction's rate but the weight-weighted average of the middle 0.25% of the block's weight. Then `calculateRecommendedFee` turns the first blocks' medians into tiers, blending each with the tier above it, flooring everything at the node's own `mempoolminfee` purge rate, and enforcing that the tiers never invert.

Two things about that median are counter-intuitive and were both got wrong once before being checked: a block's **unused space counts as its cheapest part**, so a half-full block samples the *cheap* end of its transactions rather than their middle (correctly — you barely need to outbid anything to enter a block that isn't full); and `optimizeMedianFee` returns the floor outright for any block under half full, since that is not evidence of congestion.

The one deliberate approximation is CPFP: mempool.space runs a real getblocktemplate with cluster linearisation, while `effectiveRate` sorts by **ancestor** fee rate (`fees.ancestor / ancestorsize`), which is what Core's own miner maximises and is exactly equal for any transaction with no unconfirmed parents. It can misplace the interior of a long CPFP chain, but the recommendation reads the middle of each block by weight, so a few misplaced members don't move it.

**Verified two ways.** `TestRecommendationMatchesMempoolSpace` replays projected blocks captured from their own `/api/v1/fees/mempool-blocks` through the port and reproduces the recommendation they published at that moment exactly. And against the live node, the full pipeline (36 552 mempool transactions, fetched in ~1s, projected and computed in **3 ms**) matched mempool.space on **all five tiers**. `core == nil` gives the same "not configured" message as `/info`; a mempool read failure degrades to a short note rather than a wrong number.

`/mempool` (`mempoolCmd()`) replies with the mempool's size and transaction count — both cheap from `getmempoolinfo`, rendered with a metric suffix via `metric(f, 1)` ("3.2 M", "6.7 k") — and, when the mempool is small enough to summarize in reasonable time, the summed output **amount** and summed **fees** across every mempool transaction, each in BTC and USD via `btcAmount` (these totals reach thousands of BTC / billions of sats, so BTC not sats; ≥1 BTC shows 2 decimals, a fraction keeps satoshi precision so fees don't round to "0.06"). `metric` is the shared metric-suffix helper `formatBlock`'s difficulty now also routes through. It also shows a `Flow rate` — transactions/sec flowing into the mempool and how that rate is changing (`2.5 tx/sec (+0.5)`): `startMempoolFlow` (from `main()`) polls `getmempoolinfo` every `flowInterval` (10s, var) and feeds each tx count to `updateFlow`, which keeps `flowRate` = Δcount ÷ interval and `flowChange` = Δrate **in memory only** (`flowMu`, never persisted; the goroutine isn't stopped on shutdown, like the rates updater). The rate is **recomputed only when the count rose** — a drop (`delta ≤ 0`) most likely means a block was just mined, which would skew the inflow measurement, so the previous rate/change is kept; the count is still re-baselined so the next rise spans one clean interval. The rate needs 2 samples and the change 3, so both fields are omitted until warm — and the flow line shows even when the totals are skipped, since it's already computed in the background rather than per-command. `mempoolTotals` reads the fees straight from `rawMempoolVerbose` (one `getrawmempool true` call, which also yields the txid list; Core nests each entry's fee under `fees.base`, where btcd had a flat `fee`) and computes the amount by fetching every transaction's outputs **concurrently** (bounded `sem` of 16); individual tx churn between the two passes is tolerated (skipped), but a context timeout returns `ok=false` → `Totals: unavailable`. The totals are gated by `mempoolSummaryLimit` (var, default 20000 txs) — above it the reply shows `Totals: skipped (mempool too large)`, since both the verbose fetch and the per-tx fetches scale with the tx count. Measured on the real node: at ~8500 txs the whole thing is ~4s (verbose ~3s + per-tx amount ~1s); getmempoolinfo alone is ~6ms. The `Total amount` is the sum of all outputs, so it's inflated by change — not "value being transferred".

Commands that take a free-text argument (`/info`, `/watch`, `/unwatch`) share one shape: called with an argument (`/info foo`) they act immediately; called bare (`/info`) they reply asking the user to send the text as a follow-up message and mark that chat "pending" for that command. The next plain-text (non-command) message from a pending chat is then treated as the missing argument.

Pending state is tracked per command with its own package-level `sync.Mutex` + `map[int64]bool` (`pendingInfoMu`/`pendingInfoChats`, `pendingWatchMu`/`pendingWatchChats`, `pendingUnwatchMu`/`pendingUnwatchChats`) — there is no shared/generic pending mechanism, and that's intentional: an earlier pass had the opportunity to unify this and deliberately kept it duplicated per command. Follow that precedent for any new argument-taking command rather than generalizing. `update()`'s `case ""` checks the pending maps in order (info, watch, unwatch), each `return`ing after it handles the follow-up.

All three are implemented the same way, short handler names (`info`, `watchCmd`, `unwatch`) with no wrapper functions around their pending-state maps: the lock/set-or-delete/unlock logic is inlined directly into `info()`/`watchCmd()`/`unwatch()` (setting pending) and into `update()`'s `case ""` (checking and clearing pending). There was an earlier pass where `/info` kept named helper functions (`setPendingInfo`, `takePendingInfo`, `clearPendingInfo`) while `/watch` was already inlined — that asymmetry was deliberately removed by request, so treat the current inlined-everywhere shape as the pattern to extend, not something to re-wrap in helpers.

### The database UI

`dbui/` is a small web interface for inspecting and hand-editing the bbolt file, off by default and started only when `-dbui-listen` is set (e.g. `127.0.0.1:8090`). **It can write any bucket, so it must bind to localhost** — the flag help says so. `main()` calls `dbui.Start(db, addr)` right after `openDB` (it needs the handle) and holds the returned `*http.Server` so `shutdown` can drain it **before** `closeDB`, the same ordering the webhook server uses — a request mid-flight against a closed handle would otherwise error.

The page (embedded via `//go:embed index.html`, so the binary stays self-contained) is four controls above two centred tabs: a bucket dropdown, **View**, a key field and **Get**. View loads a paginated key/value table into the **Data** tab; Get loads one key's value into an editable textarea in the **Value** tab, and **Put** writes it back. Clicking a Data row fills the key field and the Value textarea and jumps to the Value tab, which is the edit-in-place flow. Each row also carries a **trash icon left of its key** that deletes that key immediately — no confirmation, since this is a local admin tool and a dialog per row would make clearing a bucket unusable. Its handler calls `stopPropagation`, or the click would bubble to the row and open the editor instead; the table then reloads so the pagination flags stay honest. The icon is an inline `<svg>` in a `<template>`, so the page still fetches nothing external. Nine JSON endpoints back it: `/api/buckets`, `/api/bucketstats`, `/api/view`, `/api/get`, `/api/put`, `/api/delete`, `/api/clearbucket`, `/api/export` and `/api/import`. A **Buckets** tab lists every bucket with its key count and size from bbolt's own `Bucket.Stats()`, which is the cheap way to see where the database's bytes actually went. `tools/dbui` runs the same UI as a standalone process against a database file.

The one non-obvious piece is binary handling. Most buckets hold JSON or text (miner names, tags) and display directly, but keys and values are also binary in places — big-endian heights in `blocks`/`rates`/`market`, the packed `addrindex`. `encodeField`/`decodeField` render those behind a `hex:` marker and decode a `hex:`-prefixed input back to bytes, so a Put round-trips binary rather than corrupting it (the marker can't collide — no bucket stores a text value beginning `hex:`). Pagination is offset-based (`page*size` skipped on the cursor), which is fine for the small buckets and acceptable for deep pages of `addrindex` that nobody scrolls to. `dbui_test.go` covers the round trips, pagination, the 404s, deletion (including a `hex:` binary key), and the binary encoding; the UI itself was driven in a real browser against a seeded database (View, row-click, edit, Put and delete — each confirmed against the database afterwards — plus the `hex:` display and dark mode).

## Style conventions specific to this repo

These diverge from typical idiomatic Go on purpose (established through explicit instruction over this repo's history) — don't "clean them up":
- Indent with 4 spaces, never tabs — this includes running `gofmt`/`goimports` with a post-process step (or an editor setting) to expand tabs, since Go's own tooling always indents with tabs by default.
- Prefer unexported identifiers even for the main API (`bot`/`newBot`/`send`, not `Bot`/`NewBot`/`SendMessage`) — nothing outside `package main` consumes this code.
- One `import "x"` line per import, never a grouped `import (...)` block.
- `var x = expr()` instead of `x := expr()` wherever Go's grammar allows it. It doesn't allow `var` in an `if`/`for` initializer, and a `var` can't redeclare a name already in scope the way `:=` can (e.g. `req, err := ...` when `err` already exists) — those cases keep `:=`.
- No blank lines inside function bodies; blank lines appear only between top-level declarations.
- Minimal comments: none explaining *what* code does, only rare ones for non-obvious *why*.
- Single-line `if err != nil { return nil, err }` where it fits on one line.
- Avoid introducing a helper function for logic used at only one call site — inline it instead. This is about small pieces of logic, not decomposition: a handler that has grown genuinely large may be split (`info()` was deliberately split into `transaction`/`block`/`address` by explicit request).

## Testing approach

Tests never hit real Telegram or a real `telegram-bot-api` proxy. They live beside the code they cover — `flow_test.go` (command dispatch), `watch_test.go` and `zmq_test.go` (the notifier and the local matcher), `menu_test.go`, `market_test.go`, `fees_test.go`, `buttons_test.go`, `addrstats_test.go`, `blocks_test.go`, `core_test.go`, `db_test.go`, `format_test.go`, `backup_test.go`, `log_test.go` and `shutdown_test.go`, plus each package's own (`addrindex/`, `dbui/`, `miners/`, `rates/`, `txwatches/`, `watches/`). They spin up an `httptest.Server` standing in for the Bot API, build a `bot` pointed at it (`newBot("TESTTOKEN", server.URL)`), and drive behavior by calling `update()` directly with hand-built `Update` values — then assert on the outgoing `sendMessage` request bodies the fake server captured (and, in `log_test.go`, on `log` package output captured via `log.SetOutput`). Bitcoin Core is faked the same way: `newFakeCoreServer` (in `core_test.go`) is an `httptest.Server` answering JSON-RPC over plain HTTP, checking basic auth and reporting method errors in the body with HTTP 500 the way Core does. It is much smaller than the btcd fake it replaced — no websocket upgrade, no connection to keep alive, and no server-pushed notifications, because Core has none: tests drive notifications by calling `broadcast`/`processConfirms` directly, which is exactly what `zmq.go` does with a ZMQ frame.

Any test that exercises `/watch`, `/unwatch`, or the notifier must open the database first (`openDB(filepath.Join(t.TempDir(), "watches.db"))` + `defer closeDB()`) — `openDB` also hands the handle to `rates.Init`/`watches.Init`/`miners.Init`/`addrindex.Init`, so their package globals are unusable (nil db → panic) until it runs — and should reset the notification state (`stopNotify`, which also `txwatches.Reset()`s the confirmation map), the local script/outpoint matcher (`resetWatched`) and `core` for isolation, since these are package-global and shared across tests, which run sequentially. The storage packages have their own tests: `watches/watches_test.go` and `rates/rates_test.go` open a temp bbolt file via `Init`, and `txwatches/txwatches_test.go` exercises the in-memory map directly; the price-display tests (`usd`/`amountLine`) live in `format_test.go` in `package main` and seed a rate through `rates.Add`. `TestMessageLogging` redirects the global logger with `log.SetOutput(&buf)` and **must restore it with `defer log.SetOutput(os.Stderr)`, not `log.SetOutput(nil)`** — a nil writer makes every later `log.Printf` (e.g. `logMessage` in any subsequent `update()`-driven test) panic. That was a latent bug that only surfaced once a logging-path test was ordered after it.

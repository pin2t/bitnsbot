# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

bitnsbot is a Bitcoin network events notification bot for Telegram. It's a single Go binary built almost entirely on the standard library — the exceptions are `go.etcd.io/bbolt` (embedded KV store, for persisting watches) and, for talking to a `btcd` node, `github.com/gorilla/websocket` + `github.com/sourcegraph/jsonrpc2` (no other option exists in the standard library for any of these). It receives updates via a Telegram webhook (not long polling).

## Commands

- Build: `go build ./...`
- Run: `go run . -bot-token <token> -webhook-url http://localhost:8080/bot -api-base-url http://localhost:8081`
- Test all: `go test ./...`
- Test one: `go test -run TestWatchFlow -v` (other tests: `TestInfoFlow`, `TestUnwatchFlow`, `TestWatchesFlow`, `TestWatchNotification`, `TestShutdown*`, `TestMessageLogging`, `TestLoggingLevels`, `TestWatchStore*`, `TestRate*`, `TestUSDFormat`, `TestUpdateRatesAverages`, `TestAmountLineUSD`, `TestConfig`, `TestBtcd*`). Run the whole suite with `-race` (`go test -race ./...`) — the watch-notification path is concurrent.
- Vet: `go vet ./...`

There is no Makefile or linter config in this repo — `go build`/`go vet`/`go test` are the only checks available (and are exactly what `.github/workflows/ci.yml` runs on every pull request, on Go 1.26). `gofmt -l .` will flag files as unformatted by design; see Style below before "fixing" that.

Flags (all in `main.go`): `-config` (path to a `name=value` properties file to load flag values from — see The config file below), `-verbose` (log level 0/1/2 — see Logging below), `-bot-token` (Telegram bot token, required), `-listen` (address this bot's webhook server binds to), `-webhook-path`, `-webhook-url` (the URL registered via `setWebhook`), `-api-base-url` (Bot API server to call), `-secret-token` (optional), `-register-webhook` (set false to skip calling `setWebhook` on startup), `-db` (path to the bbolt watches database, default `watches.db`), `-btcd-url`/`-btcd-user`/`-btcd-pass`/`-btcd-cert`/`-btcd-insecure-tls` (btcd RPC connection; leaving `-btcd-url` empty skips connecting to btcd entirely).

## Runtime model

The bot is designed to run behind a self-hosted `telegram-bot-api` proxy (https://github.com/tdlib/telegram-bot-api) on localhost, not directly against `https://api.telegram.org`:
- `-api-base-url` defaults to `http://localhost:8081`; `telegram.go`'s `bot.call` builds every outgoing request URL from it.
- The webhook HTTP server is a plain `*http.Server` (via `srv.ListenAndServe` in a goroutine) — no TLS. The local proxy is assumed to own the real HTTPS conversation with Telegram; the hop from proxy to this bot is local/plaintext.
- **Graceful shutdown**: `main()` uses `signal.NotifyContext(…, os.Interrupt, syscall.SIGTERM)` and blocks on the returned context; on SIGINT/SIGTERM it calls `shutdown(srv)`, which tears down **in dependency order — webhook server first, then btcd, then the store**. That order is load-bearing: `srv.Shutdown` blocks until in-flight webhook handlers drain, and those handlers use the watches database and `btcd`, so closing the server first guarantees no handler is mid-request when the connections it depends on are closed. After the first signal `stop()` is called to restore default handling, so a second Ctrl+C during a slow drain force-kills. (Note: the old `defer closeDB()`/`defer btcd.close()` were dead code — `http.ListenAndServe` blocked forever and only ever returned into a `log.Fatal`, i.e. `os.Exit`, which never runs defers; this feature is the first real cleanup path.)
- Two secrets, both flags: `-bot-token` (required) authenticates outbound Bot API calls. `-secret-token` (optional) is passed to `setWebhook` and then checked against the `X-Telegram-Bot-Api-Secret-Token` header on every incoming request (constant-time compare in `main.go`'s webhook handler) — this is the only thing stopping an arbitrary POST to the webhook path from being treated as a real Telegram update. Since both are flags they can be supplied via the `-config` file; prefer that over the command line for real deployments, since command-line args are visible to other users via `ps`.

## Architecture

Eight source files, all `package main`:
- `telegram.go` — the Bot API client: the unexported `bot` type, `newBot`, and `call`/`send`/`setWebhook` methods, plus the wire types (`Update`, `Message`, `User`, `Chat`) decoded from incoming webhook JSON.
- `db.go` — the bbolt connection: the package-level `var db *bbolt.DB` and `openDB(path)`/`closeDB()` (opening also creates the `watches`, `rates`, and `blocks` buckets). This is the only place the connection lifecycle lives.
- `watches.go` — the watch storage functions (`addWatch`/`listWatches`/`removeWatch`) operating on the global `db`, plus the `watchRecord`/`watchType` types and the `watches` bucket name. One JSON-encoded `watchRecord` per watch under an auto-incrementing key (`bbolt.Bucket.NextSequence` + big-endian encoding, the standard bbolt idiom for ordered keys). See The watches store below.
- `rates.go` — BTC/USD exchange-rate history in the `rates` bucket, plus the 5-minute updater goroutine that averages three free price APIs (see Exchange rates below).
- `btcd.go` — a `btcdClient` for talking to a `btcd` node's JSON-RPC-over-websocket API (see below).
- `blocks.go` — the `blocks` bucket: cached per-block info records (`blockInfo`), `computeBlockInfo` (builds a record from btcd), the startup backfill goroutine, and `formatBlock` (the `/info` block reply). See Block info cache below.
- `pools.go` — mining-pool attribution: fetches mempool's `pools-v2.json` and maps a block's coinbase to its miner (see Block info cache below).
- `config.go` — `applyConfig`, a tiny `name=value` properties-file parser that sets flags from a `-config` file (see below).
- `logging.go` — leveled logging helpers and the `-verbose` gate (see Logging below).
- `main.go` — flags, the HTTP webhook server, and all command handling/dispatch.

### Logging

Everything logs through the helpers in `logging.go` — never `fmt.Print*` or the `log` package directly (both are considered raw and shouldn't reappear in `main.go`/`telegram.go`/`btcd.go`/`watches.go`). The package var `verbosity` (set from `-verbose` in `main()`, so it's also `-config`-settable) gates emission:
- `logErr`/`logWarn` and `logStatus` (lifecycle lines: "listening on …", "shutting down", "connected to btcd …") always print — verbosity 0.
- `logInfo` (verbosity ≥ 1): high-level events — an incoming message (`logMessage`), a reply sent (`send`), a subscription added/removed (`watch`/`unwatch`).
- `logNet` and `logDb` (verbosity ≥ 2): raw external traffic and storage requests. NET is emitted from `telegram.go`'s `bot.call` (request method + body, response body) and `rates.go`'s `fetchRate` (each price-API GET + response), plus `btcd.go` via `jsonrpc2.OnSend`/`OnRecv` hooks that are **only registered when `verbosity >= 2`** (zero overhead otherwise; `verbosity` is set before `dialBtcd` runs). DB is emitted from each watch/rate function (and `openDB`).
- `logFatal` is `logErr` + `os.Exit` for the startup fatals.

Two deliberate redactions in NET logging, both to avoid leaking secrets that a debug log would otherwise capture: the Telegram request URL (which embeds `-bot-token`) is never logged — only the method and JSON body — and the `setWebhook` body is omitted entirely because it carries `-secret-token`. Everything else (including sent message text and btcd payloads) is logged verbatim at verbosity 2.

### The config file

`-config <path>` points at a plain `name=value` properties file whose names are flag names (`btcd-url=wss://localhost:1234/ws`, `listen=:8082`). `applyConfig` (in `config.go`) is called from `main()` immediately after `flag.Parse()`: it reads the file and calls `flag.Set` for each line, so config values land in the same `*flag.Flag` variables the rest of the code already reads — no separate config struct. Blank lines and `#` comments are skipped; names and values are whitespace-trimmed; an unknown name or a malformed (no `=`) line is a fatal error with `path:line` context. Command-line flags win over the file: `applyConfig` first records which flags were already set on the command line via `flag.Visit` and skips those, so precedence is CLI > file > flag default. Because it's driven entirely by the flag set, every flag is automatically config-settable and no per-flag wiring is needed when flags are added.

### The btcd RPC client

`dialBtcd(ctx, btcdConfig{url, user, pass, certFile, insecureTLS}, handler)` dials `btcdConfig.url` with `github.com/gorilla/websocket` (HTTP Basic Auth header for credentials, matching btcd's preferred auth method over the websocket-only `authenticate` RPC command), then wraps the resulting `*websocket.Conn` in `github.com/sourcegraph/jsonrpc2/websocket`'s `ObjectStream` and hands that to `jsonrpc2.NewConn` to get a `*jsonrpc2.Conn`. TLS is only configured when `url` starts with `wss://` (production btcd is TLS-by-default with a self-signed `rpc.cert`; local regtest/dev nodes are commonly run with `--notls` and a plain `ws://` URL, which is what this repo's manual testing used).

**Reconnection**: `btcdClient` is a long-lived handle whose underlying `*jsonrpc2.Conn` lives in an `atomic.Pointer`, so a reconnect swaps the connection *in place* — every `btcd.foo()` call site (each does `c.conn.Load().Call(...)`) keeps working against the same `*btcdClient`, so neither the package `var btcd` nor its ~20 call sites (nor the tests that assign `btcd`) need to change. `supervise(reapply)` (started from `main()` after the initial dial) runs a goroutine that pings (`getblockcount`) every `btcdPingInterval` (10s; a package var so tests shrink it); on failure it `reconnect()`s — `dialConn` a fresh connection, `Swap` it in, close the old one — retrying each tick while btcd is down, and on success calls `reapply`. That callback is `reapplyBtcdState` (in `main.go`): re-`notifyBlocks` for the block cache and re-`loadTxFilter` for the watched addresses, since those subscriptions live on the connection and die with it. `close()` stops the goroutine (`stopOnce`-guarded `close(c.stop)`) and closes the current connection; a reconnect racing shutdown is handled by re-checking `c.stop` after the dial (discarding the new conn if stopping). `dialConn` is the extracted single-connection dialer; `dialBtcd` wraps it into a client. Verified against a real regtest node by killing btcd mid-run: block notifications stall, the supervisor logs reconnect attempts until btcd returns, then reconnects, reapplies, and notifications resume.

btcd/bitcoind's JSON-RPC dialect predates JSON-RPC 2.0 and always uses positional (array) `params`, never named/object params — every method call in `btcd.go` passes `[]interface{}{...}` as the params argument for this reason. Confirmed against btcd source (`btcjson.RPCVersion.IsValid()` accepts both `"1.0"` and `"2.0"`) that sending `"jsonrpc":"2.0"` (what `sourcegraph/jsonrpc2` always sends) doesn't get rejected.

Only a handful of RPC methods are wrapped as typed methods so far (`getBlockCount`, `getRawTransaction`, `getBlockHash`, `getBlockVerbose`, `validateAddress`, `searchRawTransactions`, `decodeRawTransaction`, `loadTxFilter`, `notifyBlocks`, `estimateFee`) — enough to cover `/watch`, `/info`, and `/fees`'s needs, not the full btcd API surface. (`getBlockVerbose` at verbosity 2 supplies everything the block cache needs — height, time, size, difficulty, and every tx with its size, vin, and vout — so the old `getBlockHeader` wrapper was dropped.) Add more the same way: a thin method on `btcdClient` that calls `c.conn.Call(ctx, "methodname", []interface{}{...}, &result)`. One btcd-specific gotcha (caught against a real regtest node): `getblock` at verbosity 2 returns the full transactions under the JSON key **`rawtx`**, not `tx` (`tx` carries only txids, at verbosity 1) — Bitcoin Core uses `tx` for both, so `btcdVerboseBlock.Tx` is tagged `json:"rawtx"`.

Server-pushed notifications (e.g. `blockconnected`, `relevanttxaccepted` — see `/Users/pin/code/btcd/docs/json_rpc_api.md` for the full list) are delivered to whatever `jsonrpc2.Handler` is passed into `dialBtcd`.

`main()` dials btcd (if `-btcd-url` is set; empty means skip it entirely) right after opening the watches store and before registering the Telegram webhook or starting to listen — the package-level `var btcd *btcdClient` holds the connection, and a dial failure is fatal (matches how the database's open failure is handled). The handler passed in is `notifier` (see Watch notifications below). After `startNotify`/`startBlockCache`, `main()` calls `btcd.supervise(reapplyBtcdState)` to start the reconnection watchdog (see Reconnection above); graceful shutdown's `btcd.close()` both stops that goroutine and closes the connection.

`btcd_test.go` fakes the btcd server with an in-process `httptest.Server` + `websocket.Upgrader` (same philosophy as the Telegram tests — no real btcd node needed to run `go test`). It was additionally verified once, manually, against a real locally-built `btcd --regtest --notls` node; that was throwaway verification, not something reflected in the checked-in tests.

### The /info lookup

`info()` in `main.go` classifies its (non-empty) argument into exactly one of three kinds, checked **in this order**, and dispatches to the matching per-kind function — `transaction()`, `block()`, or `address()` (one-word names, same convention as `info`/`watch`): transaction (`isTxid`: exactly 64 hex characters), then block height (parses as a non-negative base-10 integer via `strconv.ParseInt`), then address (the catch-all). The order matters and is not arbitrary: a 64-character string of all decimal digits (e.g. all zeros) satisfies *both* the txid shape and `ParseInt`, since decimal digits are a subset of hex digits — checking txid first is what disambiguates it correctly. This was a real bug caught by manual testing against a live regtest node, not a hypothetical; don't reorder these checks without re-verifying against a real node.

Each per-kind function calls btcd directly and replies with a multi-line message: `transaction` via `getRawTransaction` reports Status (confirmed + confirmation count, or unconfirmed/mempool), the confirmation time (`Confirmed:` = the block time via `when` — note btcd keeps no broadcast time for a confirmed tx, so the *delay* it took to confirm isn't computable; only the confirmation timestamp is), Block, Amount (summed `Vout[].Value` in whole satoshi, `math.Round(total*1e8)`, space-grouped), Fee, Size, and compact Input/Output address lists. The fee (Σ input prevout values − Σ output values) and the input addresses both need each input's prevout, which `getrawtransaction` omits, so `txInputs` fetches the prevout transactions **concurrently** (same bounded-`sem`-of-16 + `WaitGroup` pattern as `blockFees`); a coinbase tx shows `Fee: none (coinbase)` / `Inputs: coinbase (newly generated)`, and any prevout-fetch failure degrades Fee/Inputs to `unavailable` (so this too effectively wants `--txindex`). `compactAddrs` shows at most the first three addresses (each `short`-ened) with a trailing `...` when there are more; an output with no address (OP_RETURN, SegWit commitment) renders `(non-standard)`. An unconfirmed tx omits the Confirmed/Block fields. `block` is **served from the cache** — `block()` calls `loadBlock(height)` and, on a hit, replies with `formatBlock(bi)` without touching btcd; on a miss it computes the record live (`computeBlockInfo`), stores it, and replies. See Block info cache below for the record's fields and how it's populated (backfill goroutine + block notifications). `blockFees()` (used by `computeBlockInfo`) computes each non-coinbase tx's fee as Σ(input prevout values) − Σ(output values) for the Lowest/Average/Highest; btcd's getblock omits input values, so it gathers the referenced prevout txids and fetches those transactions **concurrently** (a `sync.WaitGroup` over a bounded `sem` channel of 16, results collected under a mutex). If any prevout fetch fails (txindex disabled, or a genuinely missing prevout) the record's `FeesOK` is false and the reply shows `Fees: unavailable`; a coinbase-only block shows `Fees: none (coinbase only)` (fee distribution effectively requires `--txindex`, same graceful-degradation spirit as `searchRawTransactions`/`--addrindex` — but reward and reward+fees come from the coinbase alone, so they show regardless). And `address` via `validateAddress` (type derived from `IsWitness`/`IsScript`) plus a best-effort `searchRawTransactions` call for recent activity. All three messages put a blank line after their header line (`Transaction 32e43e...870b16` / `Block #100` / `Address 1A1zP1...DivfNa`) and space-pad the field labels so values start in one column per message (the pad width is per-message, computed from its longest label — `Confirmed:` for a confirmed transaction, `Reward + fees:` for a cached block, `Recent activity:` for addresses). The field block — but not the header — is wrapped in `<pre>...</pre>` so Telegram renders it monospace and the alignment actually holds. To make that work, `bot.send` in `telegram.go` always sets `parse_mode: "HTML"` on every outgoing message, which imposes an escaping obligation: any user-derived text echoed into a reply must go through `html.EscapeString` (Telegram rejects messages with an unescaped `<` that isn't a supported tag). The two echo sites — `watch()`'s confirmation and the invalid-address message — do this; txids skip it because `isTxid` guarantees pure hex, and a validated address is base58/bech32, also HTML-safe. Confirmed-transaction and block times are both rendered by `when(unix)`: relative ("2 days ago", pluralized by `ago`) when within the last 3 months, lowercase absolute ("14 november 2023 22:13", `strings.ToLower` over Go's "2 January 2006 15:04" layout) when older. Txids, block hashes, and addresses are printed shortened by `short(s)` ("32e43e...870b16": first 6 + "..." + last 6, applied only when the string is longer than 15 characters) — except the "doesn't look like a valid Bitcoin address" echo, which keeps the full input because the address branch is the catch-all and that text isn't known to be an address at all. The `searchRawTransactions` call requires btcd's `--addrindex` flag; if it errors for any reason (index disabled, still catching up, etc.) `address()` doesn't fail the whole reply, it just reports activity as unavailable — this is deliberate graceful degradation, not a TODO to fix by making it fail loudly.

If the package-level `btcd` is `nil` (not configured via `-btcd-url`), `info()` replies with a fixed "not configured" message instead of dispatching — every kind depends on btcd, so this is checked once up front.

`isTxid` (shared with `watch()`), `when`/`ago`/`short` (shared across the per-kind formatters), and `satoshi` (shared with the watch notifier — `math.Round(btc*1e8)` to whole satoshi with space-grouped thousands) are real multi-call-site helpers. The per-kind functions themselves are single-call-site — they exist because `info()` had grown too big and splitting it was explicitly requested, not as license to extract small single-use helpers.

### Watch notifications

`/watch <address>` doesn't just persist the watch — it subscribes for live btcd notifications so the chat is messaged when a transaction pays that address. The delivery model is **one goroutine per watch** fed by a broadcast channel fan-out (there is deliberately no address→chats map — an earlier version used `watchersByAddr` and was replaced by this at explicit request):
- **Watchers**: each persisted watch becomes a `watcher{chatID, watchType, watchID, ch, stop}` in the package-level `watchers []*watcher` slice (guarded by `watchersMu`). `startWatcher` appends one and launches `w.run`, which `select`s on `ch` (a buffered `chan notification`) and `stop`. A watcher messages its chat only for the notifications matching *its own* `watchID` — address watchers key into `notification.received[addr]`, transaction watchers compare `notification.txid`. `ch` is **never closed** (so a broadcast can always send to it without panicking); a watcher is terminated by closing `stop`, which its `select` observes. `stopWatchers(chatID, watchID)` closes+drops the matching watchers (chatID-scoped like the store's `remove`); `stopAllWatchers` (called from `shutdown` and test setup) closes them all.
- **Subscription**: `watch()` calls `startWatcher` for every watch, and for address watches also `btcd.loadTxFilter(reload=false, [addr], nil)` so btcd's connection-wide filter includes the address (`loadTxFilter` is what makes btcd emit `relevanttxaccepted` at all — without it there are no notifications). `watchedAddresses()` is recomputed from the slice for the reload calls. On startup `restoreWatches(bot)` re-creates a watcher per stored record and reloads the filter once, so watches survive restarts. If btcd isn't configured the watch is still stored/started — it just won't fire until a btcd-connected restart.
- **Broadcast**: `notifier.Handle` switches on the notification method — `relevanttxaccepted` (watch fan-out, below) and `blockconnected` (block cache — spawns `go cacheBlockHash(hash)` from the new tip's hash; see Block info cache). Both spawn goroutines for the same read-loop-deadlock reason. For `relevanttxaccepted` (carrying the raw serialized tx hex, *not* which filtered address matched) it spawns `go broadcast(txHex)`. `broadcast` calls `decodeRawTransaction`, builds one `notification{txid, received: addr→summed Vout value}` (matching on **output/receiving addresses only** — inputs are txid:vout refs without addresses in the decoded form), and non-blocking-sends it to *every* watcher's channel; each watcher then filters. Before fanning out it **enriches** the notification (best-effort): `getRawTransaction` for the mempool tx's `vsize` + `txInputs` for its fee (Σ input prevouts − Σ outputs), `feeRate` = fee ÷ vsize in sat/vB, and `confEstimate` buckets that rate against `estimatefee`'s 2- and 6-block targets into `~10-20 min` / `~1h` / `2h+`. The **address** notification (`startNotifyChat`) shows Fee / Fee rate / Confirms below Tx / Amount; any fetch failure just leaves them off (`feeOK` stays false and the message falls back to Tx + Amount). Spawning the goroutine inside `Handle` (rather than wrapping in `jsonrpc2.AsyncHandler`) is what avoids the deadlock: `jsonrpc2` calls `Handle` synchronously in its single read-loop goroutine (conn.go's `readMessages`), so the `decoderawtransaction` `conn.Call` must run off that goroutine or it waits forever for a response the blocked loop can't read. The channel sends are non-blocking (`select`/`default`) so one slow or already-stopped watcher can't stall the fan-out.

`/unwatch <arg>` reverses a watch: `removeWatch(chatID, arg)` (scoped to the chat) deletes the persisted record(s), then `stopWatchers(chatID, arg)` terminates the corresponding goroutines, and for address watches `loadTxFilter(reload=true, watchedAddresses(), nil)` rebuilds btcd's filter from the addresses that still have watchers. That filter rebuild is an optimization — the real guarantee that notifications stop is that the watcher goroutine is gone, so no channel receives the broadcast for it. txid unwatches skip the filter rebuild (transaction watches were never in the filter). If nothing matched (`removed == 0`) the user is told they weren't watching it.

The whole path (`/watch` → real signed payment → `relevanttxaccepted` → broadcast → per-watch goroutine → Telegram message) was verified end-to-end against a real `btcd --regtest --txindex` node, including fan-out to two chats watching the same address (throwaway verification; `watch_test.go`'s `TestWatchNotification` covers the same path with a fake btcd server that pushes the notification). Keep the suite green under `go test -race` — this is the codebase's only concurrent path (the broadcast goroutine and per-watch goroutines touching the `watchers` slice and sending Telegram messages).

### The watches store

The bbolt connection is a plain package-level `var db *bbolt.DB` (in `db.go`), opened once in `main()` via `openDB(-db path)` and closed during graceful shutdown (`closeDB`, see Runtime model) — not threaded through parameters, consistent with how this codebase handles cross-cutting state (`btcd`, the pending-argument maps, etc.). The watch operations are package functions in `watches.go` that use that global `db`; there is no `watchStore` struct.

`/watch <target> [alias]` persists a `watchRecord{CreatedAt, ChatID, Type, WatchID, Alias}` via `addWatch`. `watchCmd()` in `main.go` splits `arg` on the first space into the **target** (first token) and an optional **alias** (the remainder, trimmed) — a bare `/watch` prompts for both together in the one follow-up message (deliberately not a second pending step for the alias), then classifies the target via `isTxid` (exactly 64 hex characters → `watchTypeTransaction`, anything else → `watchTypeAddress`) — a heuristic, not real address/txid validation (no checksum verification), good enough to route the record but not to guarantee the input is well-formed. The alias is echoed in the `/watch` confirmation, appended in parens to the notification header (`…watched address bc1q…dayd2g (John)`), and shown in the `/watches` listing; it's `html.EscapeString`'d at every display site since it's arbitrary user text. The other two functions are `listWatches()` (used by `restoreWatches`, `/watches`, `/unwatch`) and `removeWatch(chatID, watchID)` (for `/unwatch`); no update. `removeWatch` deletes every record matching **both** fields and returns the count — the `chatID` half is the security scoping that stops one chat from removing another chat's watch, and the count lets `/unwatch` distinguish "removed" from "you weren't watching that". It collects keys during a `ForEach` and deletes them after, because bbolt forbids mutating a bucket mid-iteration.

### Block info cache

`/info <height>` is served from a cache (the `blocks` bucket) so the expensive per-block fee computation happens in the background, not in the user's request. `blocks.go` holds one JSON `blockInfo` per height (big-endian key via `itob`, reusing the rates/watches idiom): height, hash, time, size, tx count, miner, `FeesOK` + fee min/avg/max (BTC), tx-size min/avg/max (bytes), reward, and total (reward + fees = the coinbase output). `computeBlockInfo(hash)` builds a record from one `getBlockVerbose` (verbosity 2 → all txs with sizes, vins, vouts) plus the concurrent prevout fetches `blockFees` needs; reward comes from `subsidy(height)` (50 BTC, halving every 210000 blocks) and total from summing the coinbase outputs, so reward/total never need prevouts — only the fee distribution does. Amounts render in satoshi via `satoshi()`/`group()` (`group(int64)` is the shared space-thousands helper `satoshi` now routes through), sizes via `group`. Confirmations and the old header-only path are gone; `formatBlock` builds the aligned `<pre>` block from label/value pairs.

Three things populate the cache, all funneling through `computeBlockInfo` + `storeBlock`:
- **On-demand**: a `/info` cache miss computes and stores the block (so an old, uncached block is slow once, then instant).
- **New blocks**: `main()`'s block-cache startup subscribes via `notifyBlocks`, and `notifier.Handle` turns each `blockconnected` notification into `go cacheBlockHash(newTipHash)`. Verified against a real regtest node that btcd actually sends the legacy `blockconnected` (`[hash, height, time]`), not only `filteredblockconnected`.
- **Backfill**: `startBlockCache()` (launched from `main()`) loads the mining pools, subscribes to blocks, then walks back from the tip caching `blockBackfillDepth` (var, default 50) recent blocks, skipping any already cached — so history is available immediately and the heavy pass runs once (idempotent across restarts). `storeBlock`/`loadBlock` are nil-`db` guarded, so block lookups still work (compute-only, no caching) in tests that don't open a db.

**Miner attribution** (`pools.go`): `loadPools()` GETs mempool's `pools-v2.json` (a list of `{name, addresses, tags}`) into an address→name map and a `[]{tag,name}` list (`poolsURL` is a package var for tests; the maps are guarded by `poolsMu`). `minerName(coinbaseScriptHex, coinbaseAddrs)` returns the pool whose address matches a coinbase output, else whose tag substring appears in the hex-decoded coinbase script, else "Unknown". Verified against the real mainnet node: 218 addresses / 201 tags loaded, correctly attributing recent blocks to SpiderPool, Foundry USA, ViaBTC, etc. Pools load once at startup and aren't refreshed (definitions change slowly; a restart re-fetches).

### Exchange rates

`rates.go` keeps a BTC/USD price history in the `rates` bucket (same db file), so `/info` and notifications can show a rough fiat value. Each `rateRecord{Time, Source, USD}` is stored under its `Time.Unix()` big-endian key (reusing `itob`), so keys sort chronologically. `startRatesUpdater()` (launched from `main()` right after `openDB`) backfills the daily history once (see next paragraph), fetches a current rate immediately, then refreshes every 5 minutes: `updateRates()` hits all `rateSources` (CoinGecko, Coinbase, blockchain.info — free, no-auth GETs), **averages the ones that succeed** (a failed source is just skipped; if all fail nothing is stored), and writes one averaged record. The updater goroutine isn't explicitly stopped on shutdown — `main()` returns microseconds after `closeDB`, so a write-after-close is effectively impossible; not worth a stop channel. Each source has a `parse` func tested against real API payloads (blockchain.info returns *every* fiat — we pluck `USD.last` out of it); `rateSources` is a package var so tests point it at `httptest` servers.

**Historical backfill:** so `/info` on an *old* transaction can show USD from around its block time (not just today's rate), `backfillRates()` loads the whole daily series once. It's a no-op when the store already holds deep history — `hasRateHistory()` is true when the oldest sample is older than `rateHistoryHorizon` (3y), which live updates alone can't produce on a fresh bot, cleanly distinguishing "backfilled" from "just started". Otherwise it GETs blockchain.info's `market-price` chart (`rateHistoryURL`, `timespan=all` — the entire daily series back to 2009 in one no-auth request), parses it with `parseRateHistory` (skipping the zero-price pre-market days), and writes every day in **one** transaction via `storeRates` (per-record `db.Update`s would be thousands of fsyncs). Backfilled records carry source `blockchain.info/history` at daily 00:00-UTC timestamps, so they never collide with the live `time.Now()` samples. Verified once against the real endpoint (6402 daily samples, 2009→today); `rateHistoryURL` is a package var so tests point it at an `httptest` server, and `TestBackfillRates` also asserts the `hasRateHistory` guard by counting HTTP hits across two calls.

Two reads, **both DB-only, never online**: `lastRate()` (cursor `Last()` — the newest sample) and `rateAt(t)` (the sample nearest `t` via `Seek`+`Prev`/`Last`, or not-found if the closest is more than `rateTolerance` = 36h away). That tolerance is deliberately wider than a day so the daily-granularity backfill (samples at 00:00 UTC) still matches a transaction at *any* time of day — with a 1h tolerance `rateAt` missed almost every daily sample and fell through to today's rate, defeating the backfill; live 5-min samples still match far more tightly. Both return `(record, false)` when `db == nil` so USD is silently omitted in tests that don't open a db — USD is best-effort enrichment, not a hard dependency. `amountLine(btc, at, current)` renders `"<sat> sats (≈ $usd)"`, appending the USD part only when a rate is available: `current=true` uses `lastRate()` (mempool `/info` and **new-transaction notifications**, which have no confirmed time = "now"), `current=false` uses `rateAt(at)` (a confirmed transaction's block time) **but falls back to `lastRate()` when `rateAt` finds nothing**. With the daily backfill in place `rateAt` resolves almost any historical tx to its period's rate; the `lastRate()` fallback is the safety net for a tx in a genuine gap (a stretch we never recorded), showing today's rate rather than no USD at all. USD only vanishes entirely when there is *no* stored rate at all — the empty-history case that was the reported "`/info <txid>` shows no USD" bug, which the backfill fixes. `usd(btc, rate)` drops cents from $100 up (`"$90,000"`, comma-grouped whole dollars, rounded) and keeps them below $100 (`"$58.23"`), on the logic that cents are noise on large amounts but the whole point on small ones. Only transaction *amounts* get USD — blocks and addresses have no amount.

### Command dispatch and the "pending argument" pattern

`update()` in `main.go` is the single entry point for every incoming Telegram update: pull `Update.Message`, log it (`logMessage`), split it into a command and argument (`parseCommand`), then switch on the command. `/start`, `/watches`, and `/fees` take no argument and act immediately (`/start` sends a fixed `<b>`-formatted bulleted help listing the commands; `/watches` lists the calling chat's watches — filters `listWatches()` by `chatID`, groups into Addresses/Transactions, and prints each id **un-shortened** inside `<code>…</code>` for Telegram tap-to-copy; ids are `html.EscapeString`'d because address-type watch ids are arbitrary unvalidated user input, unlike txids).

`/fees` (`fees()`) replies with current network fee estimates for three confirmation speeds — Fast (10-20 min → 2-block target), Medium (~1h → 6 blocks), Slow (2h+ → 12 blocks) — via btcd's `estimatefee`. The three per-tier `estimatefee` calls are fired **concurrently** (one goroutine each, joined by a `sync.WaitGroup`, each writing its own index of a `results` slice so there's no shared-state race — verified under `-race`), multiplexed over the single jsonrpc2 connection, so the reply waits on the slowest call instead of the sum. btcd returns **BTC/kB** (its help text says "satoshis" but the handler returns `float64(BtcPerKilobyte)`, confirmed against source); `fees()` converts to sat/vB by ×1e5 and renders an aligned `<pre>` table. Two graceful-degradation paths, both verified: `btcd == nil` → the same "not configured" message as `/info`; and btcd's estimator returns `not enough blocks have been observed` until the node has seen enough mempool activity (so a per-tier failure shows `n/a`, and all-failed collapses to a short "not available yet" note — this is what a fresh/regtest node returns, confirmed by real-node E2E). Labels deliberately avoid `<`/`>`/`&` (e.g. "2h+" not ">2h") so the fixed field text needs no HTML-escaping and the `len()`-based column padding matches the rendered width.

Commands that take a free-text argument (`/info`, `/watch`, `/unwatch`) share one shape: called with an argument (`/info foo`) they act immediately; called bare (`/info`) they reply asking the user to send the text as a follow-up message and mark that chat "pending" for that command. The next plain-text (non-command) message from a pending chat is then treated as the missing argument.

Pending state is tracked per command with its own package-level `sync.Mutex` + `map[int64]bool` (`pendingInfoMu`/`pendingInfoChats`, `pendingWatchMu`/`pendingWatchChats`, `pendingUnwatchMu`/`pendingUnwatchChats`) — there is no shared/generic pending mechanism, and that's intentional: an earlier pass had the opportunity to unify this and deliberately kept it duplicated per command. Follow that precedent for any new argument-taking command rather than generalizing. `update()`'s `case ""` checks the pending maps in order (info, watch, unwatch), each `return`ing after it handles the follow-up.

All three are implemented the same way, one-word handler names (`info`, `watch`, `unwatch`) with no wrapper functions around their pending-state maps: the lock/set-or-delete/unlock logic is inlined directly into `info()`/`watch()`/`unwatch()` (setting pending) and into `update()`'s `case ""` (checking and clearing pending). There was an earlier pass where `/info` kept named helper functions (`setPendingInfo`, `takePendingInfo`, `clearPendingInfo`) while `/watch` was already inlined — that asymmetry was deliberately removed by request, so treat the current inlined-everywhere shape as the pattern to extend, not something to re-wrap in helpers.

## Style conventions specific to this repo

These diverge from typical idiomatic Go on purpose (established through explicit instruction over this repo's history) — don't "clean them up":
- Indent with 4 spaces, never tabs — this includes running `gofmt`/`goimports` with a post-process step (or an editor setting) to expand tabs, since Go's own tooling always indents with tabs by default.
- Prefer unexported identifiers even for the main API (`bot`/`newBot`/`send`, not `Bot`/`NewBot`/`SendMessage`) — nothing outside `package main` consumes this code.
- One `import "x"` line per import, never a grouped `import (...)` block.
- `var x = expr()` instead of `x := expr()` wherever Go's grammar allows it. It doesn't allow `var` in an `if`/`for` initializer, and a `var` can't redeclare a name already in scope the way `:=` can (e.g. `req, err := ...` when `err` already exists) — those cases keep `:=`.
- No blank lines inside function bodies; blank lines appear only between top-level declarations.
- Minimal comments: none explaining *what* code does, only rare ones for non-obvious *why*.
- Single-line `if err != nil { return nil, err }` where it fits on one line.
- Avoid introducing a helper function for logic used at only one call site — inline it instead. This is about small pieces of logic, not decomposition: a handler that has grown genuinely large may be split (`info()` was deliberately split into `transaction`/`block`/`address` by explicit request).

## Testing approach

Tests (`flow_test.go`, `log_test.go`) never hit real Telegram or a real `telegram-bot-api` proxy. They spin up an `httptest.Server` standing in for the Bot API, build a `bot` pointed at it (`newBot("TESTTOKEN", server.URL)`), and drive behavior by calling `update()` directly with hand-built `Update` values — then assert on the outgoing `sendMessage` request bodies the fake server captured (and, in `log_test.go`, on `log` package output captured via `log.SetOutput`).

Any test that exercises `/watch`, `/unwatch`, or the notifier must open the database first (`openDB(filepath.Join(t.TempDir(), "watches.db"))` + `defer closeDB()`) since the watch functions dereference the global `db` unconditionally — there's no nil check — and should reset the notification state and `btcd` for isolation, since these are package-global and shared across tests, which run sequentially. `watches_test.go` tests the `addWatch`/`listWatches`/`removeWatch` functions directly against a temp bbolt file. `TestMessageLogging` redirects the global logger with `log.SetOutput(&buf)` and **must restore it with `defer log.SetOutput(os.Stderr)`, not `log.SetOutput(nil)`** — a nil writer makes every later `log.Printf` (e.g. `logMessage` in any subsequent `update()`-driven test) panic. That was a latent bug that only surfaced once a logging-path test was ordered after it.
